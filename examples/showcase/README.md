# MyP-M-A 能力演示用例

这里提供五个可以直接阅读或复制复测的合成用例，分别对应 `/review`、`/idea`、`/prd`、`/acceptance` 和 `/prompt`。

这些文件用于说明 MyP-M-A **应如何处理不同阶段的问题**，不是模型跑分，也不冒充真实项目成果。场景、用户、数据、路径和产品均为虚构；“代表性交付”是经过人工整理的示范节选。正式质量证据仍以仓库中的评测记录为准。

## 一眼看懂

| 用例 | 用户真正需要的判断 | 主要展示能力 | 不应该发生 |
| --- | --- | --- | --- |
| [01 项目评审](01-review-project-map.md) | 项目现在是什么样，哪里需要处理 | 项目地图、意图/实现/验证对照、证据化分流 | 看到问题就直接写新 PRD |
| [02 想法验证](02-idea-value-test.md) | 问题是真的吗，AI 方案值得做吗 | 数据口径、问题与方案分离、压力测试、最小实验 | 用评分或少量反馈证明需求成立 |
| [03 正式 PRD](03-prd-async-export.md) | 异步导出应该怎样完整落地 | 前后端、状态机、权限、数据库、失败链路和验收 | 只描述一个“导出”按钮 |
| [04 发布验收](04-acceptance-release-gate.md) | 候选包是否真的可以发布 | 产物身份、证据四态、失败注入、人工补证和发布判断 | 用自动测试替代真实 GUI 与异常路径 |
| [05 下一步提示词](05-prompt-handoff.md) | 怎样把结论交给下一轮 Agent | 事实继承、范围、验证、授权和停止条件 | 把整段历史重新复述一遍 |

## 推荐演示顺序

1. 先看 `/review`，理解 MyP-M-A 为什么先建立地图。
2. 再看 `/idea`，观察它如何拒绝为预设方案找理由。
3. 用 `/prd` 检查完整性和开发可承接程度。
4. 用 `/acceptance` 看它是否敢于保留“待验证”和阻止发布。
5. 最后看 `/prompt` 如何在不丢事实的前提下压缩交接。

## 复测方式

打开任一用例，将“给 Agent 的输入”代码块复制到已安装 MyP-M-A 的新任务中。复测时重点检查文件末尾的“可复测检查点”，不要只比较篇幅或措辞。

结果可能随宿主、模型、工具可用性和上下文变化。正确性、证据、完整性和可执行性优先于回答是否更短。
