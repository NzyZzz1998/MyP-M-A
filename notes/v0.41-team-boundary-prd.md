# MyP-M-A v0.41 团队协作边界与自适应交付 PRD

## 1. 版本判断

- 类型：正式推进型内部治理 PRD。
- 版本目标：解决企业工作场景中 PRD 默认越过产品经理职责、文档复杂度由工程细节主导的问题。
- 稳定回退：`v0.40.0` / `3bdae56862b6740986f2b1fb4981cb058e73a9b8`；v0.41 开发起点为 `2f96b36cd1005489d8c6a442cac12fcd9a243868`。
- 范围保护：不新增入口、PM 框架或外部工具硬依赖；不削弱个人 Vibe Coding 场景已经验证的完整交付能力。

## 2. 问题与证据

用户在工作电脑真实使用时反馈：输出“太复杂”，且“没有准确的产品经理边界”。审计确认当前 `/prd` 默认要求物理数据库字段、接口、测试接缝、高保真 HTML 和开发承接，未区分团队产品经理与独立 Vibe Coding 所有者。

## 3. 目标与非目标

### 目标

1. 用同一组入口支持团队产品经理和 Vibe Coding 两类交付。
2. 团队场景默认保留完整产品合同，但不替研发、设计、测试决定物理实现。
3. Vibe Coding 场景继续覆盖原型、逻辑 API/schema、开发计划、进度、验证和发布承接。
4. 双模式必须保留同一事实、范围、数字、状态和验收语义。

### 非目标

- 不新增 `/team-prd` 或 `/vibe-prd`。
- 不删除现有深度合同。
- 不把团队 PRD 简化成只有背景、目标和功能列表的空模板。
- 不用字符数下降替代行为证据。

## 4. 功能需求

### FR-001 模式解析

新增内部 `delivery_mode=auto|team_pm|vibe_coding`。显式指定优先；组织协作或意图不明默认 `team_pm`；只有明确要求同一 Agent 继续实现时进入 `vibe_coding`。正式输出显示解析结果。

### FR-002 产品经理职责边界

团队模式由产品经理负责问题、用户、目标、范围、业务流程、规则、状态语义、数据含义、权限语义、指标、验收、依赖和风险；物理 schema、SQL、端点、框架、代码文件、测试实现、CI 和部署交由下游角色确认。

### FR-003 双模板交付

团队模式使用产品核心模板，按协作面写影响和承接清单；Vibe Coding 模式继续使用工程增强模板。两者共享上游事实与产品验收。

### FR-004 原型责任

团队有设计角色时，产品经理定义流程、状态和设计验收，原型可作为设计交付依赖；用户要求代做或无设计角色时再生成高保真原型。Vibe Coding 模式保持既有高保真门禁。

### FR-005 开发承接授权

团队模式完整 PRD 默认停在团队评审点，只有明确要求才生成 `dev_plan/progress/dev_log`。Vibe Coding 模式保持“确认后可进入开发承接”。

### FR-006 跨入口继承

`/review`、`/idea`、`/acceptance`、`/prompt` 保留模式，防止交接后静默升级工程深度。用户明确要求代码评审、实际验收或实施时仍可执行对应动作。

## 5. 影响范围

- 运行时：`SKILL.md`、`references/work-mode-boundary.md`。
- 入口：`references/prd.md`、`references/review.md`、`references/acceptance.md`、`references/prompt.md`、`references/development-handoff.md`。
- 模板：新增 `templates/prd-team-template.md`，保留 `templates/prd-template.md` 为全流程模板。
- 评测：新增团队默认、显式全流程、事实等价、原型责任和开发承接边界用例。
- 校验：新增 v0.41 自测并纳入 Strict。
- 状态：README、CHANGELOG、roadmap、backlog、progress、dev log。

## 6. 实施批次与回退

1. M0：冻结 v0.40 tag 与用户问题；失败时回退到 `v0.40.0` / `3bdae568`，开发起点另记为 `2f96b36`。
2. M1：新增模式合同和团队模板；可单独删除新增文件回退。
3. M2：改 `/prd` 与开发承接；失败时只回退入口差量。
4. M3：扩展 review/acceptance/prompt 继承；失败时保留 PRD 试点。
5. M4：新增静态与行为评测；任何事实保真回退都停止晋升。
6. M5：独立验收与状态收口。

## 7. 开发前验收

- AC-001：公司 PRD 请求且未提实现时解析为 `team_pm`。
- AC-002：模糊请求默认 `team_pm` 并允许显式切换。
- AC-003：个人项目只有在明确继续实现时解析为 `vibe_coding`。
- AC-004：团队 PRD 不补造物理 schema、SQL、代码文件、测试命令、CI 或部署脚本。
- AC-005：团队 PRD 仍完整覆盖流程、规则、异常、权限、指标、影响和验收。
- AC-006：Vibe Coding 仍能交付逻辑 API/schema、原型和开发承接。
- AC-007：同题双模式的用户、范围、数字、状态和验收事实一致。
- AC-008：团队有设计角色时不强制 PM 生成高保真 HTML。
- AC-009：团队模式未经授权不自动生成开发承接。
- AC-010：`/prompt` 保留模式且不静默升级。
- AC-011：Strict、上下文预算、UTF-8、JSON、PowerShell 和 `git diff --check` 通过。
- AC-012：定向 A/B 无事实、范围或验收回退后才可晋升 Stable。
