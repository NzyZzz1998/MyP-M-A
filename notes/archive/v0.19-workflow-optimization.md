# MyP-M-A v0.19 流程优化

## 来源

v0.18 在 QuickRec、LetsMakeMoney 和 PCbuild 的连续使用中暴露了五类流程摩擦：

- 评测快照位于 Skill 扫描根目录，出现多个同名 `Mypm` 入口。
- PRD 完成后继续实施时仍可能沿用 `/prd`，导致重复规划。
- 多轮 Acceptance 需要反复提醒不要重测已通过项。
- 个人项目被统一真人测试门禁卡在开发前，Agent 模拟与真人证据边界又不够明确。
- 下一阶段提示词重复项目文档，长度持续膨胀。

## 本轮改动

1. 将 `mypm-workspace` 迁移到 `codex_home/skill-evals/mypm-workspace`，正式扫描根目录只保留一个 Skill manifest。
2. 新增 `references/workflow-control.md`，集中定义阶段、批次、门禁、验证层级、证据继承和发布面。
3. PRD 加入 L0-L4 验证层级选择，低风险个人项目不再机械要求开发前真人测试。
4. 开发承接完成后明确进入实施阶段；已有 PRD/dev plan/progress 时按任务 ID 执行。
5. Acceptance 继承仍有效证据，只重开受影响项目。
6. 下一阶段提示词提供精简执行、完整审计、人工验证三档，默认精简。
7. 新增 eval 35-39 防止上述能力回退。

## 验证边界

已完成 eval 35-39 的单次定向 A/B：v0.18 为29/40（72.5%），v0.19 为34/40（85.0%），五个用例各提升1项。证据继承达到8/8；实施阶段识别仍只有5/8，是下一轮最优先修正项。

每版每个用例只运行1次，不能据此声称低方差稳定或全面优于 v0.18；v0.18 仍作为完整行为基线。原始工作区已按临时产物策略清理，长期结果统一记录在 `notes/evaluation-history.md`。

## 第一轮定向修正

根据 A/B 失分补充：

- 实施阶段必须列出 PRD/dev plan/progress 事实源，明确不重写 PRD，并说明 progress/dev log 去向。
- L0+L1 进入 MVP 增加“低风险 + 用户明确授权”条件。
- 精简提示词也必须保留 commit/push/tag/Release 停止边界，以及结论/阻塞/下一步汇报。
- Acceptance 分别判断 tag、Release、远端推送和仓库可见性，并等待明确授权。

修复后首轮回归：eval 35 为7/8、eval 37 为7/8、eval 38 为8/8、eval 39 为8/8。剩余两项改为结构化字段：实施输出固定“事实源”，分层验证固定“进入开发授权”。

最终发现子 Agent 会继承真实 `E:\codex` 工作区，导致部分评测读取真实项目；相关 iteration-6/7 样本已排除。加入纯文本隔离约束后，eval 35 和37均为9/9。结合 eval 36、38、39 的最新有效结果，五项定向能力为42/42；每项仍只有一次有效运行，不代表低方差稳定。

入口层新增单一 UI 元数据和无命令自动分流；eval 40/41 分别验证项目材料进入 `/review`、实现证据进入 `/acceptance`。
