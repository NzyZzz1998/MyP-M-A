# /prd 真实试跑记录

本文记录 MyP-M-A `/prd` 在真实项目中的试跑反馈，用于后续改进 skill。它不是项目正式 PRD 本体，而是对 `/prd` 工作流输出质量的复盘。

## QuickRec Diagnostic Export PRD

时间：2026-07-09

输入概况：

- 项目：`E:\codex\QuickRec`
- 来源：`doc/mypm-idea-pool-2026-07-08.md` 中的 `IDEA-003`。
- 需求：诊断日志 / 错误导出能力。
- 背景：QuickRec 在录制失败、音频异常、FFmpeg 异常、保存失败、窗口捕获异常时，需要更轻量的本地排障信息导出能力。

### 第一轮输出表现

第一轮 `/prd` 没有直接生成完整 PRD，而是先完成：

- PRD 类型判断。
- 候选方案探索。
- 推荐方案。
- 关键澄清问题。

判断结果：

- 类型：正式推进型 PRD。
- 限制：必须收敛为最小版本。
- 理由：`IDEA-003` 已有中等证据支撑，来自历史故障、日志、v1.4 稳定性目标和当前代码现状；但缺少外部用户规模证据，不能做复杂诊断中心。

候选方案：

- 方案 1：最小复制方案，只做“复制诊断信息”和“打开日志目录”。
- 方案 2：标准导出方案，在方案 1 基础上增加“导出诊断文件”。
- 方案 3：诊断面板方案，做独立诊断窗口。

推荐方案：

- 推荐方案 2：标准导出方案。
- 理由：比纯复制更利于排查真实问题，又没有升级成复杂诊断中心。

### 做得好的地方

- 没有急着写完整 PRD，符合 `/prd` 先澄清、再收敛、再成文的要求。
- PRD 类型判断准确：不是原型验证型，也不是大而全正式需求，而是“小而确定”的正式推进型需求。
- 三个方案梯度合理：最小、推荐、过大，方便用户做取舍。
- 推荐方案符合当前证据和项目阶段：既满足排障需要，又保持 Lite/Full 可共用的轻量能力。
- 澄清问题聚焦在会影响 PRD 的关键决策：产品线、入口、导出格式、隐私边界。

### 暴露的问题

- 提问可以更分阶段。第一轮一次问了 4 个问题，虽然不多，但 `/prd` 理想状态应优先先问最影响方向的问题，例如“落在哪条产品线和版本里”。
- 方案阶段缺少显式优先级与版本范围，例如 P1、进入 Full v1.4.x 后续版本、延后项和不做项。
- 候选方案影响范围还可以更工程化，例如每个方案会影响 UI、日志落盘、文件导出、配置、打包、测试中的哪些部分。
- 澄清问题缺少“当前日志落盘能力是否稳定”的确认。诊断导出依赖稳定日志来源，如果没有稳定日志文件，PRD 需要先把日志落盘纳入范围。

### 用户确认结果

用户选择：

- 方案：方案 2，标准导出方案。
- 产品线 / 版本：Full v1.4.x 后续版本。
- 导出位置：默认在视频存储路径下新建诊断文件夹存放。
- 配置能力：导出位置可自定义。
- 隐私边界：当前诊断只保存在本地，无需脱敏。

这些确认会影响完整 PRD：

- 需求不进入 Lite v0.1 最小增强，而是进入 Full v1.4.x 后续版本。
- UI 入口和配置范围可以比 Lite 更完整，但仍不应升级成复杂诊断中心。
- 需要新增或复用“诊断文件夹路径”配置项，默认值基于视频保存路径。
- 需要定义导出文件命名、目录结构、覆盖/保留策略和失败处理。
- 因用户明确本地保存且无需脱敏，PRD 不应强制默认脱敏；但仍应在风险中提示如果未来支持上传/分享，需要重新定义脱敏规则。

### 拟改进方向

- 在 `references/prd.md` 中考虑补充：方案探索阶段应同时给出推荐优先级、版本范围、延后项和不做项。
- 考虑补充“提问分阶段”规则：先问最影响方向的问题，再根据回答继续问实现和体验细节。
- 考虑补充“候选方案影响范围预估”规则：每个方案至少简述影响 UI、数据/配置、日志、文件、测试中的哪些部分。
- 对诊断/导出类需求，PRD 澄清问题应默认包含：
  - 现有日志是否稳定落盘。
  - 导出文件放在哪里。
  - 是否需要用户自定义目录。
  - 是否需要脱敏。
  - 是否只本地保存，还是未来可能上传/分享。

### 完整 PRD 输出复盘

完整 PRD 文件：

- `E:\codex\QuickRec\doc\PRD-diagnostic-export-v1.4.x.md`

用户反馈：

- 用户明确表示这版 PRD 很满意，认为效果远好于之前单独使用 superpower 的体验。
- 用户认为单个功能 PRD 能做到这种深度“出乎意料”。

完整 PRD 做得好的地方：

- 范围控制清楚：Full v1.4.x 后续版本，未扩散到 Lite，也未扩成诊断中心。
- 影响范围完整：覆盖 UI、状态、录制核心、日志系统、配置、打包发布、权限安全、既有体验保护。
- 开发前验收口径合格：包含验收目标、验收标准、日志/人工检查、通过标准和不通过处理。
- 原型图可用：设置页和托盘菜单低保真线框能指导开发。
- 功能链路清晰：复制、打开目录、导出、目录配置、失败反馈、取消/关闭行为都有说明。
- 非目标明确：云上传、复杂诊断中心、自动修复、隐私收集被排除。
- 关键判断准确：将“日志文件持久化”定为 P0，说明模型理解到导出能力的前置基础。

完整 PRD 暴露的小问题：

- `.txt` 与 `.zip` 导出格式需要更明确。PRD 最终落为 `.txt` 合理，但应说明 `.zip` 是否为后续增强。
- “无需脱敏”和“不收集隐私信息”存在轻微表述张力。更准确的说法应是：不主动采集视频/音频/截图内容，仅记录本地排障必要信息，首版因不上传不自动发送所以无需脱敏。
- 设置页诊断目录的保存/取消链路可以更细：保存才生效、取消不保存、未保存时导出使用旧目录还是输入框目录。
- 日志保留策略需要收敛：首版到底不做自动清理，只导出最近 100 行，还是实现默认 7 天清理。

后续可沉淀为 `/prd` 规则：

- 对导出类需求，必须明确文件格式的首版范围和后续增强。
- 对本地诊断/日志类需求，隐私边界要区分“本地记录”“自动上传”“用户主动分享”。
- 涉及设置项时，必须写清保存、取消、关闭、未保存状态下触发动作的行为。
- 涉及日志保留或文件留存时，必须明确首版是否做清理策略，避免“有配置项但行为不确定”。
