# MyP-M-A Skill 路线图

本文是 MyP-M-A 自身的产品路线图，用于规划后续优化顺序。它不是用户项目的 PRD，也不是正式 skill 使用说明。

## 当前定位

MyP-M-A 的目标不是做一个模板集合，而是做一个中文优先的个人产品经理助理，帮助用户完成：

- 发现问题与判断价值：`/idea`
- 项目理解与评审：`/review`
- 收敛方案与定义需求：`/prd`
- 开发完成后的验收与发布收口：`/acceptance`
- PRD 后的开发承接：`dev_plan_vx.x.md`、`progress_vx.x.md`、`dev_log_vx.x.md`

当前阶段判断：已经从“能用”进入“需要稳定泛化”的阶段。下一阶段重点不应继续增加入口，而应验证和打磨现有入口。

## 下一阶段

### R3. 稳定性验证

优先级：P0

目标：证明新规则不仅适用于 QuickRec 和 LetsMakeMoney，也能处理更多产品形态。

建议验证场景：

1. 后端 + 数据库项目
   - 目标：验证 `data-analysis.md` 是否能正确识别表、字段、接口、迁移、数据兼容。
   - 重点入口：`/review`、`/idea`、`/prd`

2. 数据驱动需求
   - 目标：验证 `/idea` 是否会主动做数据分析，而不是只靠用户描述。
   - 输入材料：日志、表格、Issue、用户反馈、数据库样本。

3. 复杂版本级 PRD
   - 目标：验证 `/prd` 是否会分轮提问、区分方案收敛版和完整可开发 PRD。
   - 重点检查：高保真原型、影响范围、开发前验收。

4. 需要人工补证的验收
   - 目标：验证 `/acceptance` 是否会输出手动验证文档，而不是误判通过。
   - 典型对象：桌面托盘、硬件、权限、真实账号、真实设备。

完成标准：

- 至少完成 3 个非 QuickRec / LMM 的试跑案例。
- 每个主入口至少有一次真实使用记录。
- 发现的问题更新到 backlog。

### R4. Eval 与防回退

优先级：P0

目标：让 skill 的关键能力可回归检查。

建议 eval：

- `/idea`：输入模糊需求和少量数据，期望输出数据缺口、场景压力测试、评分阈值。
- `/idea`：输入多个候选需求，期望输出需求池文件和版本主线。
- `/prd`：输入方案收敛需求，期望不会直接进入 dev plan。
- `/prd`：输入 UI 体验版本，期望要求高保真原型。
- `/acceptance`：输入部分通过验收，期望不允许发布。
- `/acceptance`：输入无法自动化验证的托盘/硬件项，期望输出手动验证文档。
- 通用：输出必须中文，不能出现乱码。

完成标准：

- `evals/evals.json` 覆盖上述主要场景。
- 至少能用人工检查方式确认新规则没有明显回退。

## 中期阶段

### R5. 后端与数据库能力增强

优先级：P1

目标：让 MyP-M-A 在有完整后端架构的项目中更好用。

计划内容：

- 增强数据库分析规则：schema、迁移、索引、字段兼容、权限、软删除、多租户。
- 增强 API 影响范围：接口字段、错误码、鉴权、幂等、分页、缓存、超时。
- 增强数据产品需求：报表、筛选、导出、指标口径、漏斗、分群。
- 增强数据库构筑建议边界：什么时候只写 PRD，什么时候需要技术设计或 spike。

完成标准：

- 能基于一个后端项目输出包含数据库字段级影响范围的 PRD。
- 能识别“前端写死 / 配置文件 / 后端接口 / 数据库查询”的方案差异。

### R6. 原型与 UI 体验能力增强

优先级：P1

目标：让 UI/体验类 PRD 更稳定地产出高保真原型和组件级要求。

计划内容：

- 明确何时调用 UI/UX 或 frontend-design 类 skill。
- 增强高保真原型输出要求：页面、状态、控件、交互、空态、错误态、保存态。
- 增强原型验收：截图对比、响应式、文本不溢出、控件风格一致。
- 建立 UI polish 类需求的 PRD 示例。

完成标准：

- 对设置页、面板、菜单、向导、表单类需求能稳定输出可执行原型要求。
- 不再只给低保真线框就进入开发承接。

### R7. 下一阶段提示词产品化

优先级：P1

目标：把“下一阶段提示词”从规则变成稳定交付体验。

计划内容：

- 每个入口固定输出下一阶段建议。
- 根据当前结论自动选择 `/idea`、`/prd`、开发承接、`/acceptance`、手动验证、发布收口提示词。
- 研究是否新增独立提示词入口。

候选入口：

- `/next`：根据当前产物生成下一阶段提示词。
- `/handoff`：生成给另一个窗口或 agent 的交接提示词。
- `/prompt`：仅生成可复制提示词，不做额外分析。

暂不决定新增入口，先继续观察真实使用。

完成标准：

- 用户在任一阶段结束后，都能直接拿到下一步提示词。
- 不会把“下一步建议”写成泛泛建议。

## 后期阶段

### R8. Skill 产品化收口

优先级：P2

目标：让 MyP-M-A 更适合长期维护和发布。

计划内容：

- 整理 notes 体积，区分正式 reference、模板、试跑记录、归档资料。
- 检查是否需要 `agents/openai.yaml`。
- 优化 `SKILL.md` description，提高触发准确性。
- 建立 release notes / changelog。
- 打包或发布到 GitHub 仓库。

完成标准：

- 正式 skill 包中只保留必要资源。
- 过程性 notes 有归档策略。
- GitHub 仓库结构清晰。

### R9. 多项目样例库

优先级：P2

目标：积累 MyP-M-A 的真实使用样例，让它不断变好。

计划内容：

- QuickRec 案例：完整链路样例。
- LetsMakeMoney 案例：桌面应用、UI polish、验收补证样例。
- 后端数据库项目样例：待补。
- Web SaaS / 管理后台样例：待补。
- 移动端或跨端产品样例：待补。

完成标准：

- 每类项目都有输入、输出、问题、修正点。
- 新规则来自真实案例，而不是凭空扩写。

## 暂不做

- 不新增大量入口，避免 MyP-M-A 变成命令森林。
- 不强制每次都跑复杂数据分析，小项目保持轻量。
- 不把外部工具触发写死，保持“需要证据时调用”的弹性。
- 不把 MyP-M-A 做成通用开发 agent，它主要负责产品判断、需求定义、承接与验收。
- 不把所有 PM 框架都塞进 skill，只吸收对用户真实工作流有用的部分。

## 推荐下一步

当前最值得推进：

1. 先提交当前非验证优化。
2. 选择一个新项目或构造一个后端 + 数据库样例，跑 R3 稳定性验证。
3. 根据验证结果补第一批 eval。

如果用户暂时不想跑验证，则可以先做：

- 清理 notes 体积。
- 建立 `evals` 草案。
- 准备 GitHub 发布说明。
