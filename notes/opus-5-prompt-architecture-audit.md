# Opus 5 提示词架构审计

## 文档状态

- 用途：研究样本与 MyP-M-A 差距分析。
- 结论级别：候选优化，不是运行时规范。
- 当前基线：MyP-M-A v0.25.0。
- 本轮不修改 `SKILL.md`、reference、模板或 eval。
- 未经评测验证的模式不得直接进入正式 Skill。

## 样本架构

公开样本大体由六层构成：

1. **基础行为层**
   - 产品身份、默认帮助立场、拒绝边界、语气、时效性和纠错方式。
2. **长期记忆层**
   - 文件分类、读写顺序、事实来源、隐私过滤、删除、去重、并发版本和应用边界。
3. **工具合同层**
   - 工具用途、调用条件、禁止条件、参数结构、调用后动作和失败处理。
4. **能力路由层**
   - 搜索、连接器、文件、Computer Use、可视化、Artifact 和研究模式之间的选择。
5. **证据与输出层**
   - 搜索引用、版权、文件交付、视觉输出和用户可见反馈。
6. **动态上下文层**
   - 当前日期、用户资料、记忆目录、可用工具、可用 Skill 和运行环境。

较长副本中，长期记忆和工具定义占据大部分篇幅。它并不是一段单纯的“角色提示词”，而是产品行为、工具协议、隐私政策和动态运行配置的组合。

## 与 MyP-M-A 的差距矩阵

| 维度 | MyP-M-A v0.25 | Opus 5 样本/官方建议 | 判断 |
| --- | --- | --- | --- |
| 模块加载 | `SKILL.md` 作为路由层，reference 渐进加载 | 大型产品提示包含多个模块和动态块 | MyP-M-A 当前方式更适合 Skill，不应改回单体长提示 |
| 入口路由 | `/review`、`/idea`、`/prd`、`/acceptance` 与 `/prompt` 隔离 | 工具和产品能力有明确触发/禁止条件 | 已具备基础，可加强工具级合同 |
| 证据控制 | 区分已确认、待验证、证据失效与门禁状态 | 强调搜索、引用、时效和失败降级 | 已较成熟，缺口主要在“当前信息自动取证” |
| 长期记忆 | 有 `auto/suggest/off`、仓库核对、冲突清单和写后确认 | 强调只保存有明确来源的事实、读前检查、去重、隐私和删除语义 | MyP-M-A 证据闸门更强，但记忆条目来源标签还不够明确 |
| 工具合同 | 以阶段和工具类型定义最小工具、降级与授权 | 单个工具常包含“何时用、何时不用、调用后做什么、失败怎么办” | 可引入统一五段式工具合同，但不能把全部工具说明塞进核心 |
| 提示词生成 | L1/L2/L3、事实源、授权、停止点、压缩检查 | 官方要求显式控制可见回复长度、任务范围和 Agent 数量 | 缺少接收模型/运行时校准和明确 Agent 预算 |
| 验证 | 要求关键验证、证据和失败处理 | 官方指出 Opus 5 会主动自检，重复要求复核会造成过度验证 | 应区分“交付证据”与“反复 double-check” |
| 子 Agent | 仅在工具编排中要求并发条件和停止条件 | 官方建议只在独立大任务中委派，并设置确定性上限 | 应补默认预算、完成后关闭和长尾回收规则 |
| 输出长度 | 控制生成提示词自身长度 | 官方区分聊天回复长度与写入文档长度 | 可增加接收任务的输出档位，不与提示词字符预算混用 |
| 当前信息 | 工具策略要求需要证据时调用 | 样本对时效性问题使用明确搜索触发规则 | 可补“时间敏感事实优先查证”，避免凭旧上下文判断 |

## 值得验证的候选优化

### P0：先做定向评测

#### O5-01 接收运行时校准

在 `/prompt` 内增加可选内部字段 `recipient_profile`：

- 默认：`generic`
- 用户明确目标模型或运行环境时：记录模型、工具能力和上下文限制
- 未知时不猜测，不在正文中堆模型名称

仅在行为差异会影响执行时装配，例如：

- Opus 5：限制回复长度、任务范围和子 Agent 数量；避免重复自检指令。
- 无工具模型：不得生成依赖工具才能完成的事实结论。
- 新线程：引用正式事实源或交接材料，不假设共享上下文。

#### O5-02 交付证据替代重复验证

保留：

- 必须运行的测试、日志、截图、哈希和验收证据。
- 失败时的停止、恢复和降级规则。

删除或避免：

- “再检查一遍”“反复确认”“让子 Agent 二次复核”等没有新增证据的重复要求。
- 同一测试在提示词多个模块中重复出现。

目标不是减少验证，而是让每个验证动作只执行一次，并产出可审计证据。

#### O5-03 子 Agent 预算与生命周期

建议默认规则：

- 简单任务：`0` 个子 Agent。
- 单条独立调查：最多 `1` 个。
- 多条真正独立且可并行的工作：默认最多 `3` 个。
- 用户没有明确要求时，不用子 Agent 单独复核主 Agent 已完成的同一工作。
- 子 Agent 完成、失败或超过长尾阈值后立即关闭或回收。
- 评测任务单独声明模型、并发数、最长等待和失败重试模型。

#### O5-04 Memory 来源与新鲜度

在长期项目记忆中明确区分：

- `user-decision`：用户明确作出的决定。
- `repo-fact`：仓库正式文件或 Git 状态支持的事实。
- `verified-result`：工具实际验证得到的结果。
- `preference`：用户长期偏好。

不写入：

- 仅由模型推断的结论。
- 未落盘草稿、临时状态和无法追溯来源的“已完成”。

每条阶段状态至少带正式来源或可回到项目文件的路径；版本变化后旧状态标记为过期或被替代。

### P1：P0 稳定后再考虑

#### O5-05 五段式工具合同

只为本轮选中的关键工具装配：

1. `USE`：何时调用。
2. `SKIP`：何时不用。
3. `BEFORE`：调用前核对什么。
4. `AFTER`：结果如何进入证据和下一步。
5. `FAIL`：失败时如何重试、降级或停止。

该合同放在 `references/tooling.md`，不复制到每个入口。

#### O5-06 输出档位双轨制

区分：

- **提示词长度**：现有 L1/L2/L3。
- **接收任务的交付长度**：简短回报、标准报告、审计报告。

用户没有要求长文时，不因项目材料多就生成冗长完成报告；正式 PRD、审计和验收文件仍按内容完整性决定长度。

#### O5-07 当前信息查证

产品价格、版本、法规、模型能力、依赖版本、远端仓库状态和发布状态等可能变化的事实，优先读取当前来源。无法查证时标记时间点和待验证，不使用 Memory 或旧文档静默补全。

### P2：暂不进入运行时

- 在长任务中维护紧凑的当前状态胶囊，减少反复读取无关历史。
- 为真正独立的大型工作提供 writer-verifier 模式，但默认关闭。
- 对不同模型维护轻量适配说明；只有真实 A/B 证明有收益才保留。

## 明确不采用

- 不复制公开样本的原文、安全规则、商业推荐或产品宣传。
- 不把所有工具 schema 写进 `SKILL.md`。
- 不因上下文窗口更大而取消渐进加载。
- 不隐藏 MyP-M-A 的 Memory 读写结果；项目状态需要可审计。
- 不保存用户未明确表达的心理、健康、身份或其他敏感推断。
- 不把未经官方确认的提取样本当成规范事实。
- 不添加与四个主入口无关的新命令。

## 定向评测方案

### 新增候选用例

1. **模型已知的短实施提示词**
   - 输入明确指定 Opus 5。
   - 期望限制范围、回复长度和子 Agent 数量。
   - 不出现重复自检要求。
2. **简单任务的子 Agent 控制**
   - 期望使用 0 个子 Agent，不把复核自动委派。
3. **三条独立调查**
   - 期望最多 3 个子 Agent，声明关闭和长尾策略。
4. **Memory 阶段收尾**
   - 只保存用户决策、仓库事实、验证结果和下一步。
   - 不保存模型推断或临时排查。
5. **时间敏感产品判断**
   - 期望先查当前官方来源，无法查证时降级。
6. **Acceptance 证据闭环**
   - 仍要求真实测试、日志和产物身份。
   - 不要求无新增价值的重复验证。

### 评分维度

- 入口和阶段正确性。
- 事实来源与 Memory 来源正确性。
- 任务范围是否稳定。
- 关键证据是否闭合。
- 子 Agent 数量、生命周期和长尾处理。
- 提示词字符数与接收任务输出长度。
- 工具失败时是否正确降级。
- 是否全中文、无乱码、无模型或项目事实幻觉。

### A/B 策略

1. 以 v0.25.0 作为冻结基线。
2. 先运行 6 条定向用例，新旧版本各 1 次。
3. 有差异、失败或不稳定的用例补到各 3 次。
4. 定向通过后只回归受影响稳定用例和挑战用例。
5. 稳定集与挑战集继续分开汇报，不合并为一个总质量分。
6. 只有质量不回退且长度、工具调用或 Agent 成本至少一项改善，才进入下一版本。

## 当前结论

Opus 5 样本最有价值的部分不是长提示词本身，而是把记忆、工具、路由、证据和失败处理写成明确合同。MyP-M-A 继续保留更适合 Skill 的渐进加载架构，只引入接收运行时校准、证据去重、子 Agent 预算和 Memory 来源标签。

## 实施与验证结果

- 6 条新增定向 A/B：v0.25 为 46/48，v0.26 为 48/48，输出缩短 25.4%。
- 20 条受影响稳定用例：统一 Luna 评分由 154/160 提升到 155/160；定向修复后无回退。
- 3 条受影响挑战用例：两版均为 24/24。
- 首轮候选曾因把无证据风险带入 Memory 建议、未逐轨汇报和未标注附件 verified-source 失败；均按失败样本收紧合同后单项复验通过。
- 当前结论：四项小改动具备正式进入 v0.26 的证据；未照搬公开样本中的单体长提示词、平台内部路由或专属工具协议。
