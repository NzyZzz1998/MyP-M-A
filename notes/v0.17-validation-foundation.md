# v0.17 Validation Foundation

日期：2026-07-09

本文记录 MyP-M-A `v0.17.0` 的验证基础设施补强。它不是新的产品入口，也不是用户项目文档，而是为了让 MyP-M-A 从“能用”进入“可回归、可泛化、可长期维护”。

## 目标

`v0.17.0` 的目标是补齐三类基础设施：

- 真实验收案例：沉淀 QuickRec 和 LetsMakeMoney 的 `/acceptance` 经验。
- Eval 基线：用一组轻量用例防止关键能力回退。
- Memory 实测模板：验证 Basic Memory 接入是否能恢复上下文，且不会记录过多临时过程。

## 本轮完成

### 1. Acceptance 真实试跑记录补强

更新：

- `notes/acceptance-real-run-notes.md`

新增 LetsMakeMoney v0.5 acceptance 与 bugfix 收口案例，覆盖：

- 部分通过不能发布。
- Computer Use 无法覆盖托盘通知区时需要人工补证。
- 保存失败反馈属于发布阻塞 bug。
- 语义日志不足可以进入发布前 bugfix。
- bugfix 后应定向复验失败路径、成功路径、无变化路径和点击穿透保护。
- 用户澄清验收语义时，先判断是需求变化、PRD 漏洞还是实现状态问题。

### 2. Eval 基线补强

更新：

- `evals/evals.json`

版本更新为：

- `0.17.0`

新增用例：

- `idea_data_driven_evidence_gap`
- `idea_version_pool_dependency_and_scope`
- `prd_convergence_not_dev_handoff`
- `prd_ui_requires_high_fidelity_prototype`
- `acceptance_partial_pass_blocks_release`
- `acceptance_manual_verification_required`
- `memory_suggestion_boundary`

这些用例覆盖：

- `/idea` 是否会主动处理数据证据和证据缺口。
- 版本型需求池是否输出主线、依赖、三档范围和分流。
- `/prd` 是否区分方案收敛版和完整可开发 PRD。
- UI/体验类 PRD 是否要求高保真原型同步。
- `/acceptance` 是否避免把部分通过误判为可发布。
- `/acceptance` 是否在工具覆盖不足时输出手动验证文档。
- Memory 建议是否只保存长期有用内容，不保存完整聊天或临时过程。

### 3. Memory 实测记录模板

新增：

- `templates/memory-validation-template.md`

模板用于记录：

- 写入前上下文。
- 使用的 memory skill。
- 写入提示词。
- 写入后 note 检查。
- 新线程恢复测试。
- 是否需要 `memory-reflect`、`memory-defrag` 或 `memory-schema`。

## 下一步建议

优先顺序：

1. 真实执行一次 Memory 测试：用 `memory-capture` 保存本轮 MyP-M-A 状态，再新线程用 `memory-continue` 恢复。
2. 选择一个后端 + 数据库项目，跑 `/review -> /idea -> /prd`，验证字段级影响范围和数据分析能力。
3. 将 `evals/evals.json` 进入正式 eval 流程，生成可人工 review 的结果。

## 成功标准

- MyP-M-A 不再只依赖 QuickRec / LetsMakeMoney 两类桌面项目经验。
- 关键能力有可回归检查，不靠聊天记忆判断是否变好。
- Memory 接入能恢复上下文，但不制造重复、臃肿或敏感记忆。
