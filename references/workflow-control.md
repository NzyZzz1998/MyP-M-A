# 阶段、门禁与证据控制

本文件用于控制多阶段项目的推进方式。目标是减少重复规划、重复验收和过度门禁，让每轮只处理当前阶段真正需要解决的问题。

## 阶段识别

开始工作前先根据已有产物判断阶段，不要求用户记住更多命令：

| 阶段 | 识别信号 | 本轮职责 |
| --- | --- | --- |
| 发现与价值判断 | 想法、反馈、候选需求、问题线索 | 进入 `/idea` |
| 方案收敛 | 有方向但范围、方案或关键决策未定 | 继续 `/prd` 提问和取舍 |
| 完整需求定义 | 方案已定，需要完整链路、影响范围和验收口径 | 完成可开发 PRD |
| 增量修订 | 已有有效方案，本轮修改范围明确 | 按 `references/prd.md` 更新受影响部分，继承未变决定，不重开整轮规划 |
| 开发承接 | PRD 已确认，需要 dev plan/progress | 只拆实施计划，不改需求 |
| 实施 | 已有 PRD、dev plan、progress，用户要求继续任务或里程碑 | 按当前批次执行，不重写 PRD |
| Bugfix 收口 | 验收或实现发现明确缺陷 | 复现、修复、定向回归，不扩大版本 |
| 实际验收 | 有锁定实现或候选产物 | 进入 `/acceptance` |
| 发布收口 | 本轮要求发布收口，且对应 Acceptance 已通过 | 同步事实、发布材料并等待各项外部写操作授权 |

如果用户沿用 `/prd` 继续实施，先说明真实子阶段，再按实施处理。不要因为入口文字仍是 `/prd` 就重新生成 PRD。只有需求契约、范围或验收标准确实变化时才回写 PRD，并记录变化原因。

输出匹配本轮委托：状态核对或摘要不自动扩为发布判断、手动验收文档或开发计划；发现相关风险仍说明依据、影响和最小建议，确证阻塞与未确认建议分开。正式 PRD、Review、验收不设通用长度上限；去重不得删业务规则、异常、权限、数字口径、历史限制或验收标准。摘要可引用可访问的完整材料，不能把省略项声称为已完成。

实施阶段开头用一小段“执行基线”固定四件事，不要只在正文间接提到：

- 当前阶段是实施，不是重新定义需求。
- 使用明确字段 `事实源：PRD；dev plan；progress`，列出实际路径或文件名。
- 本轮只处理指定任务 ID；没有契约变化时不重写 PRD。
- 完成后更新 progress；实现过程进入 dev log，缺陷进入 bugfix log。

在声称执行或完成前，确认项目路径和上述事实源真实可访问。缺少时输出“实施输入阻塞”，列出需要的项目路径和文件；不得虚构仓库状态、提交、产物哈希、测试或任务完成情况。

## 实施批次

大型版本按里程碑或强关联任务分批推进。默认一轮只处理一个里程碑；用户已授权完成整个迭代时，当前门禁闭合后继续下一批，不把批次结束当成新授权要求。用户要求“先提问”“只评审”或撤回授权时，停止受影响写入，不能沿用历史许可越界。批次必须写清：

- 本轮目标和任务 ID。
- 依赖的正式文档。
- 允许修改的范围。
- 验证和完成条件。
- 停止点与下一批条件。

任务多不等于提示词要逐项复述。已有 dev plan/progress 时引用文件和任务 ID 即可；只有高风险或文档未覆盖的新增约束才展开。同对象同范围已有授权持续有效，未知实现细节可先取证；真正改变范围、核心行为、安全或外部副作用才请求新决定。若 Skill 要求与用户意图冲突，引用适用规则说明处理，不静默扩大权限。

## 门禁状态

完成状态对应当前交付物。仅交付修订文稿时，记录“文稿已交付；文件落盘未执行，由维护者承接”；正文中的拟更新状态不能冒充磁盘状态。实际写入后再以工具结果及回读记录文件完成；用户只要求文稿时不额外要求落盘才能完成本轮。

多材料按 `references/traceability.md` 分别记录写入、回读和适用验证结果；部分完成不得汇总成“全部同步”。一份材料缺失或工具不可用时，说明原因并继续可独立完成的授权项，不清零已有有效结果。

任务执行、门禁证据与验收结论分别记录，沿用已有词表，不相互代替：

- 任务执行：`未开始 / 进行中 / 待验收 / 已完成 / 阻塞`，回答工作做到哪一步；脚本完成不等于数据处理完成。
- 门禁证据：按下面状态记录，并标记 `新测 / 继承通过 / 证据失效` 等证据关系。
- 验收结论：`通过 / 部分通过 / 未通过 / 待验证`，按对象与验收范围判断。

门禁证据状态含义：

- `未开始`：尚未执行该项验证。
- `进行中`：正在收集或验证证据。
- `部分通过`：已有证据通过，但覆盖不完整或仍有明确遗留项。
- `通过`：完成标准和证据均闭合。
- `未通过`：证据显示不符合标准。
- `阻塞`：无法继续，必须先满足前置条件。
- `待补证`：实现可能正确，但当前缺少必要证据。
- `暂不验证`：用户明确延后验证；不能写成通过。
- `已接受风险`：用户明确接受已知风险；记录适用范围和截止条件，不能伪装为风险消失。

三者无需同值：实现任务已完成可以同时有设备证据待补、验收待验证；不能把任务勾选或静态通过直接写成运行验收通过。

同时标记门禁影响面：开发、Beta、正式发布、特定产物、源码公开或发布后观察。一个安装器门禁不应自动否定源码或便携包，除非版本范围明确要求所有面同时完成。

## 验证层级

根据风险、阶段和证据成本选择层级，不机械要求所有项目在开发前完成真人测试：

| 层级 | 证据 | 适用判断 |
| --- | --- | --- |
| L0 | 静态审查、契约、规则、文档 | 低风险和前置完整性 |
| L1 | 独立 Agent 走查、角色模拟、红队和异常路径 | 早期原型预检；必须标记为模拟证据 |
| L2 | 开发者或产品负责人真实操作、自动化、日志和截图 | 可运行 MVP、桌面工具、内部 Beta |
| L3 | 真实目标用户或真实设备/账号验证 | 高认知风险、外部 Beta、关键体验 |
| L4 | 发布后指标、反馈、故障和留存 | 真实市场效果与持续迭代 |

选择层级时考虑：误判后果、操作可逆性、用户认知风险、数据/权限风险、发布范围和招募成本。个人早期项目通常可以在低风险前提成立且用户明确授权后，用 L0+L1 进入 MVP 开发，用 L2 进入候选验收；L3 可阻塞公开 Beta，而不必阻塞所有实现。支付、隐私、医疗、安全、不可逆数据操作等高风险场景不得用 Agent 模拟替代真实验证。

当结论允许进入 MVP 时，单独写 `进入开发授权：已获得 / 未获得`。用户只是讨论方案或允许 Agent 预检，不等于授权实际开发；未获得时停在建议和授权确认点。

Agent 模拟不能产出真实完成率、真实困惑率、真实用户原话或真实市场认可。合成输入不等于模拟执行：真实程序在受控数据上执行并有直接证据，可判限定功能通过，但不证明正式数据准入、生产表现或真实付款。批量数据治理可以使用独立采集、独立复核、独立批准审计，但必须保留来源、角色和异常清单。

确定性重复任务优先用脚本；建议先做受控小样本，核对结果后再批量，不逐条调用模型。分别报告脚本、样本、实际处理和写回的状态/数量；明确未执行才记 0，未知写待核对。只读或未授权时仅给建议，不执行，也不把样本建议升级为新增发布门禁。

验证范围匹配本轮变更；已有有效检查完成后不无因重复。新改动、失败或未解决风险才扩大，明确的独立验收与发布门禁照常执行。只读或可逆准备可在已有授权内完成，不为假想风险新增全套合规流程。

## 证据继承

后续验收先读取上一轮结果，为每项标记：

- `新测`：本轮首次执行。
- `继承通过`：原证据仍有效，本轮无需重复。
- `证据失效`：相关对象变化，必须重测。
- `待补证`：仍缺工具、环境或人工证据。

证据至少记录：任务/验收 ID、对象、范围、分支、HEAD、dirty 状态、产物路径与 SHA256（如适用）、证据路径、结论、验证时间和失效条件。

以下变化通常使相关证据失效：

- 相关业务代码、native、配置契约或依赖变化。
- 候选产物重新构建且哈希变化。
- 测试环境、权限、数据库 schema 或关键数据变化。
- 原证据对象路径或版本身份不一致。
- 新发现证明原测试没有覆盖真实链路。

纯文档变化、无关模块变化或未影响目标产物的修改，不应自动要求整轮重测。只重开受影响项，并说明影响分析。

## 发布面拆分

发布判断按实际产品拆分，至少检查：

- 源码仓库是否可公开。
- 便携包是否可发布。
- 安装器/商店包是否可发布。
- 当前版本是否可发布。
- 是否可创建 tag、Release 或修改仓库可见性。

分别给结论和阻塞项，避免用一个笼统的“可发布”掩盖不同产物的状态。外部写操作仍等待用户授权。

发布收口必须单独回答：当前是否允许创建 tag、创建或上传 Release、推送远端以及修改仓库可见性。没有明确授权时一律写“暂不执行”，即使源码或某个产物已经通过。
