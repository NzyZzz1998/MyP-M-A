# /acceptance 入口工作流

`/acceptance` 用于开发完成后的实际验收、发布判断和上线观察。它对照 `/prd` 或用户给定标准核验真实结果，不重新判断需求价值，也不把开发前计划冒充证据。

继承上游 `delivery_mode`。`team_pm` 汇总各角色真实证据并给产品验收/发布建议；未授权工程操作时，不代写或执行构建、迁移、CI、部署脚本。授权实际验收后可调用最小工具，模式不削弱证据要求。

- 续测按“对象 + 原状态 + 证据来源”继承时间、失效条件和责任人；历史未提供写“未提供”。上游明确通过且未给变化时直接继承，不新增“重读全部证据”门禁。仅身份或相关代码、依赖、配置、数据、环境、产物变化、冲突或过期使证据定向失效，其余保留。`失败`、`待补证`、`暂不验证`、`已接受风险`、`待负责人决定` 不得弱化；状态只凭同对象新证据、责任人决定或授权动作迁移。
- “权限变化”等对象不明的证据须保留原词并标待确认，不得替换成目录 ACL、角色或租户权限。
- 不固定生成上一轮状态，不把模板占位当事实。单列“工具与证据来源”，写实际调用、不可用能力及日志、配置、截图、测试、数据和产物；只列路径不算工具说明。
- 跨 Web、Desktop、Data/API、Release 轨道只形成一个汇总结论。证据冲突先核对版本、哈希、时间、环境与缓存，不按多数票放行。
- 测试、CI 或状态文件的 `PASS` 只是声明；须读取其引用证据。placeholder、模拟执行、空文件或不可读证据不能判通过。synthetic/mock 输入不等于模拟执行：真实程序在受控输入上执行且有直接证据，可判对应功能通过；不得据此外推正式数据准入、生产表现、真实用户或真实付款。
- 日志只证明事件被记录，代码审查只证明实现路径存在。“没有越权/泄露/副作用”“旧文件未覆盖”等负向结果必须有同一候选对象的前后状态、明确自动化断言或等价实证。

- 部分通过或发布前列明前置条件及失败处理，分别判断源码、便携包、安装器/商店包、版本和外部动作。通过不自动授权 commit、push、公开、tag、Release 或上传。
- 主动检查清单可能遗漏的关键风险，不以“用户没写”为由忽略。既有要求按来源验证；新增发现按下列边界处理，不把提出建议本身当成越界：
  - **新增建议**：说明依据、可能影响、最小补证动作、成本/范围影响和待确认人；必要时明确“建议补为发布门禁”，但负责人确认前不冒充既定要求。无足够依据不凑建议数量。
  - **严重但待核实风险**：有具体线索且后果重大时，标明不确定性，可建议暂缓受影响动作并给最小核查及恢复条件；不能写成已证实事故或未经确认的永久门禁，不牵连无关发布面。已有授权内的安全只读补证可继续。
  - **已证实阻塞**：证据表明违反明确合同或适用安全要求，即使原测试清单漏列，也须阻塞受影响动作并引用要求与反证；不能以“新建议未确认”为由降级放行。负责人确认新增要求后，再更新其来源、状态及受影响验收，不改写历史结论。

- 结论不是“通过”时，使用下表逐项收口。每行在通过标准中引用既有要求的 ID 或来源；缺口、补证动作和证据要求都不能暗增验收义务。新增建议另列，确认前不进入必关缺口或发布前置；严重待核风险须显式保留不确定性及暂缓的影响面。

## 执行流程

### 1. 判断阶段与范围

- PRD 前：返回 `/idea` 或 `/prd`。
- 开发中且没有候选结果：只给预验收清单，不给通过结论。
- 开发完成：核验功能、异常、回归和可发布性。
- 发布前：按已确认范围核对配置/数据兼容、安装升级、回滚和发布说明；不适用项略去，新发现按建议/风险处理。
- 发布后：观察异常，决定继续、修复或回滚。

已有 PRD、dev plan、progress、verification 或上一轮验收时读取 `references/workflow-control.md`，只重开受影响项。需要核对“文档要求是否被实现和测试”时读取 `references/intent-implementation-audit.md` 并复用规则 ID；不存在的交付面不进入分母。

### 2. 建立证据清单与执行轨道

每项记录验收 ID/标准、对象、环境/前置、动作/观察窗、预期、实际、证据时间、状态和失败处理。

按 `capability-routing.md` 和 `tooling.md` 选最小真实轨道；验收图形交付时同时读 `visual-delivery.md`，逐项核对事实映射、双视口、离线与静态回退：

- **Web**：浏览器操作、控制台、网络、响应式、可访问性和截图。
- **Desktop**：Computer Use、进程、窗口、托盘、日志、配置、文件和系统状态。
- **Data/API**：接口、查询/迁移、口径复算、权限、幂等、数据质量和失败恢复。
- **Release**：源码身份、构建、哈希、CI、许可证、安装/升级/回滚和发布面。

工具或材料不可用时标“待验证”，不补想象证据。用户说 `/metric` 或 `/launch` 时也进入本入口，并说明已合并到实际验收。

### 3. 执行、继承与判定

验收结论只使用四类：

- **通过**：实际结果与可核对证据满足标准。
- **部分通过**：核心路径通过，但有明确遗留或覆盖不足。
- **未通过**：证据显示偏离、破坏旧体验或阻塞发布。
- **待验证**：缺少工具、材料或实际结果。

门禁跟踪可另用“未开始、进行中、阻塞、待补证、暂不验证、已接受风险”，但后两者仍不是通过。

<!-- contract:acceptance-evidence-impact -->
续测建立最小证据影响表，记录“原证据对象、变更影响、当前状态、理由、是否重测”。哈希变化只使依赖旧产物的包体验证失效，不自动否定独立文档、静态分析或数据证据；局部 Bugfix 也不应清零无关证据。最终汇总继承通过、新测通过、证据失效和待补证。

负向、失败注入或回滚测试必须保留注入前、失败时和恢复后的证据；执行结束恢复用户配置、权限、进程、网络、设备或系统状态，并记录恢复结果。

### 4. 输出与发布判断

版本级或多轨道验收读取 `templates/acceptance-template.md`。少量验收可压缩为对象身份、证据表、汇总结论和缺口表，但预期、实际、证据、四态结论与处理不得省略；不存在的发布面、源码身份或外部写授权不因模板完整而新增。

发布前分别判断：源码、便携包、安装器/商店包、版本整体、本地提交、远端推送、tag、Release、附件上传和仓库可见性。每项写“可执行 / 暂不执行 / 被阻塞”及授权状态；用户未授权外部写操作时统一为“暂不执行”。用户未说明各发布面能否拆分时，写“全部发布面是否必须同时完成：待确认”，并给条件结论。

<!-- contract:acceptance-unsigned-installer -->
未签名 Windows 安装器不能作为公开 Release 附件，只能作为内部测试产物；它不自动阻塞已独立验收的源码或便携包，但不能以“接受风险”绕过。

发布说明只写用户可感知的新增、修复、体验改善和已知限制；回滚要点名上一版产物、配置/数据备份和恢复步骤。上线后按产品风险观察启动/崩溃、核心路径、错误、兼容和用户反馈，不机械堆指标。

## 手动验证文档

当前工具无法覆盖真实托盘、系统弹窗、硬件/声音、多显示器、真实账号/网络、视觉动效或其他关键路径时，必须生成独立手动验证文档；聊天中的缺口表不能替代需要交给人逐步执行的材料。

读取 `templates/manual-verification-template.md`，包含候选身份、前置、配置/日志路径、逐步操作、点击/等待点、预期、证据、通过标准、失败处理、环境恢复和记录区。无人工补证时写“无需额外手动验证文档”。

AI/Agent 验收另加失败样例、人工抽检、幻觉/遗漏/越权/过度执行、用户确认点、降级和反馈闭环；不能只以平均成功率掩盖安全护栏失败。
