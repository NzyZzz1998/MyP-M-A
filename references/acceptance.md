# /acceptance 入口工作流

`/acceptance` 是 MyP-M-A 的“实际验收 + 发布观察”入口。它整合原本 `/metric` 和 `/launch` 的有效部分，用于开发完成后、发布前和发布后的验收、测试、日志/埋点核对、回归、发布检查、回滚、发布说明和上线后观察。

`/acceptance` 不负责判断需求真假，也不负责制定开发前验收口径。需求真假和价值判断由 `/idea` 完成。开发前必须约定的验收目标、验收标准、日志/埋点/人工检查、通过标准和不通过处理，由 `/prd` 完成。`/acceptance` 负责在开发完成后或发布前后，拿实际开发结果对照这些标准做验收、测试和发布检查。

- 首行写 `入口判断：/acceptance` 和当前子阶段；随后给通过、部分通过、未通过或待验证之一。
- 用户已提供实际结果时，逐项写“实际结果 + 证据 + 结论”；只有计划没有实证时才输出待验收清单。
- 开始前锁定对象身份、环境、前置条件、证据路径和时间/新鲜度；候选产物重建后，旧截图或旧日志不能直接继承。
- 自动化无法覆盖时输出手动验证文档，至少包含对象/哈希、前置准备、配置与日志路径、逐步操作、等待/观察点、预期、截图/日志证据、通过标准、失败处理和记录区。
- 无论工具是否可用，都单列“使用工具与证据来源”，逐项写明实际调用、已探测但不可用或待补用的工具，以及日志、配置、截图、测试或产物路径；只列输入路径不等于说明使用了什么工具。
- 跨 Web、Desktop、Data/API、Release 轨道时只形成一个汇总结论；证据冲突先核对版本、哈希、时间和环境，不按多数票放行。
- 需要核对“文档要求是否被实现和测试”时读取 `references/intent-implementation-audit.md`，复用规则 ID；建议测试、模拟证据和不存在的交付面不能增加当前通过率。
- 证据强度必须直接支持结论：日志只证明对应事件被记录，代码审查只证明实现路径存在；“旧文件未覆盖、没有越权、没有泄露、没有副作用”等负向结果需要同一候选对象的状态前后对照或等价实证，不能由日志和代码模式推断。
- 涉及状态保持、隔离或“未发生”的验收项，只有同一候选对象的前后状态、明确自动化断言或等价实证才能判通过；只有失败日志和代码审查时最高为“部分通过”。产物身份、日志时间或代码版本未锁定时，把对应字段列为待补证。

## 适用场景

- 用户说“开发完成了，验收一下”“给测试清单”“检查开发结果是否通过”。
- 用户需要基于实际实现核对日志、埋点、人工检查或上线后观察方案。
- 用户准备发版，需要发布检查、回滚、发布说明。
- 用户已经有开发结果，需要决定是否继续迭代、修复、发布或回滚。
- 用户说 `/metric` 或 `/launch` 时，也按 `/acceptance` 处理，并说明已合并为验收入口。

## 阶段判断

先判断当前处于哪个阶段：

- PRD 前：不要使用 `/acceptance` 判断需求真假，建议回到 `/idea` 或 `/prd`。
- 开发中：如果尚未有可验收结果，优先回到 `/prd` 补验收口径；只可输出预验收清单，不给通过结论。
- 开发完成：重点基于实际开发结果做功能验收、回归测试、失败处理、是否可发布。
- 发布前：重点做发布检查、配置/数据兼容、回滚方式、发布说明。
- 发布后：重点做上线后观察、异常判断、回滚/修复/下一轮迭代。

如果阶段不清楚，基于用户材料推断，并标注假设。

已有 PRD、dev plan、progress、verification 或前一轮 Acceptance 时，读取 `references/workflow-control.md`。先建立本轮对象身份并继承仍有效的通过证据，不无理由重跑整轮验收。

## 核心原则

- 不重复 `/idea` 的需求真假验证。
- 不替代 `/prd` 制定开发前验收口径。
- 必须基于实际开发结果、测试记录、日志、截图、构建产物、配置或用户反馈做判断；没有实际结果时只能输出待验收清单。
- 如果用户提供 exe、网页、日志、配置、GitHub PR、CI、截图或发布产物，优先按 `references/tooling.md` 调用对应工具进行实际检查。
- Computer Use、GitHub、浏览器、日志读取和本地命令不可用时，不要补想象中的证据；把对应结论标为“待验证”。
- 测试脚本、CI 或状态文件中的 `PASS` 只是结果声明，不自动等于有效证据；必须核对引用的日志、截图、产物或数据内容。证据缺失、为空、不可读，或明确标为 placeholder、synthetic、mock、示例时，对应项只能标为“待验证”或“不通过”。
- 指标要服务决策，不是为了显得专业。
- 对个人项目默认轻量：优先日志、人工测试、截图对比和配置兼容检查。
- 发布计划不是营销稿，重点是风险控制和用户能看懂的变更说明。
- 如果功能风险高，优先补回滚、日志和兼容检查。
- 每个验收项标记为新测、继承通过、证据失效或待补证。相关代码、依赖、配置、数据或候选产物哈希变化时，只重开受影响项。

## 证据清单与执行轨道

执行前先建立本轮证据清单。每个验收项至少记录：

- 验收 ID 和对应 PRD/标准。
- 被验收对象身份：分支、HEAD、产物路径/哈希、配置、数据和依赖版本。
- 环境与前置条件。
- 实际动作和观察窗口。
- 预期结果与实际结果。
- 证据文件、生成时间和数据/产物新鲜度。
- 状态：新测、继承通过、证据失效、待补证、暂不验证或已接受风险。
- 结论限制与不通过处理。

按对象选择最小执行轨道，具体能力见 `references/capability-routing.md`：

- **Web**：真实浏览器操作、控制台、网络请求、截图、响应式和可访问性。
- **Desktop**：Computer Use、进程、窗口、托盘、日志、配置、文件和系统状态。
- **Data/API**：接口调用、查询/迁移、口径复算、数据质量、权限、幂等和失败恢复。
- **Release**：源码身份、构建产物、哈希、CI、许可证、tag/Release、安装/升级/回滚和发布面。

一个验收项可以跨轨道，但只能形成一个汇总结论。不同工具结果冲突时，先核对对象身份、时间、缓存和证据新鲜度；不能按多数结果投票判定通过。

### 意图与实现对照（按需）

当正式 PRD、权限矩阵、架构决策或配置约定可用时，不只核对最终界面。对承重规则建立“文档意图、实际执行点、已有测试/运行证据”矩阵，并区分：

- 实现偏离：仍有效的明确规则没有被实现。
- 文档过期：行为经过批准发生变化，但事实源未更新。
- 未验证：实现可能正确，但没有足够实际证据。
- 待确认：对象身份、意图来源或执行路径没有锁定。

只检查项目真实存在的能力。没有支付、定时任务、AI、邮件或安装器时写“不适用”即可，不为满足模板制造空验收项。

## 实际验收

`/acceptance` 的验收不是重新制定标准，而是拿实际开发结果对照 `/prd` 或用户给定标准执行检查。优先写成：

- 预期是什么。
- 实际结果是什么。
- 证据是什么。
- 结论是通过、部分通过、未通过还是待验证。
- 未通过时如何处理。

验收结论只能使用四类：

- 通过：有实际运行及可核对的日志、截图、测试、CI 或用户证据支撑；单独的状态文本或 `PASS` 声明不足以判定通过。
- 部分通过：核心路径通过，但存在明确遗留项或覆盖不足。
- 未通过：证据显示不符合预期、阻塞发布或破坏旧体验。
- 待验证：缺少工具、材料或实际结果，不能给通过结论。

门禁跟踪还可使用“未开始、进行中、阻塞、待补证、暂不验证、已接受风险”，但最终验收结论仍只使用上述四类。暂不验证和已接受风险都不能改写成通过。

## 证据继承

开始续测前读取上一轮验收表，记录对象、分支、HEAD、dirty 状态、产物路径和 SHA256。原证据仍覆盖同一实现与同一产物时标为“继承通过”；若相关实现或产物身份变化则标为“证据失效”并定向重测。无关文档或模块变化不触发全量回归。

续测输出应保留历史失败和已通过项，说明本轮新测范围，不用新增总结掩盖旧证据。

<!-- contract:acceptance-evidence-impact -->
续测必须建立最小证据影响表，逐项记录“原证据对象、变更影响、当前状态、理由、是否重测”：

- 未触及相关实现、依赖、配置、数据、环境和产物身份的项目继续标为“继承通过”，不得因局部 Bugfix 全部清零。
- 相关代码或依赖变化、候选产物重建、配置/数据前置条件变化时，只将受影响项目标为“证据失效”。
- 产物哈希变化会使依赖旧产物的包体验证失效，但不自动否定与产物无关的文档、静态分析或独立数据证据。
- 历史失败必须保留，直到新证据明确覆盖；待补证和暂不验证不得改写为通过。

输出结论时汇总“继承通过、新测通过、证据失效、待补证”，让用户能够审计本轮复用了什么、重开了什么。

对于桌面工具、小项目或 UI 精修，可以使用：

- 人工操作次数。
- debug.log 事件。
- 截图对比。
- 成功/失败次数。
- 误触率、错误率、崩溃率。
- 保存、取消、关闭、退出、回滚等出口检查。
- 旧配置兼容。

## 日志 / 埋点 / 人工检查结果

小项目不强行设计复杂数据系统。开发完成后优先核对：

- 日志事件名。
- 触发时机。
- 关键字段。
- 人工测试步骤。
- 截图或录屏证据。
- 用户反馈记录。

事件命名应清楚表达行为，例如：

- `Pet: interaction=clicked_single`
- `Settings: save_success`
- `Settings: validation_error`
- `App: startup_config_loaded`

## 发布检查

发布前最小检查：

- 构建产物能启动。
- 主流程验收通过。
- 回归范围覆盖。
- 配置兼容。
- 日志可定位问题。
- 已知限制写清。
- 回滚方式明确。

对个人桌面应用，回滚可以是保留上一版 exe、备份配置文件、明确恢复步骤。

发布结论按源码仓库、便携包、安装器/商店包、版本整体以及 tag/Release/仓库可见性分别判断。某个产物被阻塞时，不自动把其他发布面写成未通过；但如果用户已明确要求所有面同时完成，则保留整体门禁。用户未说明能否拆分发布时，必须显式写“全部发布面是否必须同时完成：待确认”，并给出两种条件结论，不得静默选择拆分发布。

<!-- contract:acceptance-unsigned-installer -->
未签名 Windows 安装器不能作为公开 Release 附件；它只能保留为内部测试产物。该门禁不自动阻塞源码仓库或已独立验收通过的便携包，但必须分别给出结论，不能以“用户可接受风险”绕过公开附件门禁。

对本地提交、远端推送、tag、Release、附件上传和仓库可见性逐项给出“可执行 / 暂不执行 / 被阻塞”，并写明所需用户授权；即使回复需要精简，也不能把这些动作合并成一句“可以发布”。通过验收只代表具备条件，不自动授权外部写操作；用户未明确授权时统一写“暂不执行”。

最小发布判断用独立行或独立要点呈现：源码、便携包、安装器、版本整体、本地提交、远端推送、tag、Release、附件上传、仓库可见性。不得用“这些操作均暂不执行”代替逐项判断。

没有拿到实际材料时也要保留验收合同：每个适用验收项至少写“预期 / 实际与证据 / 结论”；实际栏写“未提供/待提供”，结论写“待验证”。不能因为尚无证据就省略预期，或把补证要求当成预期结果。

## 发布说明

发布说明应面向用户，不要写内部实现：

- 新增了什么。
- 修复了什么。
- 改善了什么体验。
- 仍有什么已知限制。

避免：

- 大段技术细节。
- 夸张营销语言。
- 没有用户价值的内部模块名。

## 上线后观察

上线后观察回答三个问题：

- 是否符合预期？
- 是否出现异常？
- 下一步是继续、修复、回滚，还是进入下一轮迭代？

可以按时间窗口组织：

- 1 小时：启动、崩溃、核心路径、关键日志。
- 24 小时：用户反馈、错误率、配置兼容、主要功能使用情况。
- 3 天：稳定性、复现问题、是否进入下一轮优化。

## AI 功能补充

如果功能涉及 AI 或 agent：

- 增加失败样例集。
- 增加人工抽检比例。
- 检查幻觉、遗漏、误解、过度执行。
- 明确用户确认点和人工兜底。
- 建立反馈闭环。

## 与其他入口的关系

- `/idea`：判断需求真假、价值和是否值得继续。
- `/prd`：开发前制定验收目标、验收标准、日志/埋点/人工检查、通过标准和不通过处理。
- `/acceptance`：开发完成后或发布前后，基于实际结果执行验收、测试、发布检查、回滚、发布说明和上线后观察。

如果用户在 `/acceptance` 里要求判断“这个需求值不值得做”，提醒应回到 `/idea`。
如果用户在 `/acceptance` 里还没有开发结果，提醒应先用 `/prd` 制定验收口径，或只输出待验收清单。

## 手动验证文档

Acceptance 完成后，先判断是否存在无法由当前工具自动覆盖的项目。只要存在以下情况，就应输出手动验证文档，而不是直接进入发布：

- Computer Use 无法稳定操作的托盘、系统通知区、硬件设备、权限弹窗、全局快捷键。
- 浏览器或自动化测试无法覆盖的真实用户路径。
- 需要人眼判断的视觉、动效、声音、触感或多设备表现。
- 需要用户本机环境、真实账号、真实数据、真实网络或真实外设的验证。
- 自动化测试通过，但 GUI/桌面/真实设备证据不足。

手动验证文档建议命名：

- `manual_verification_vx.x.md`
- 或放入版本目录，例如 `doc/releases/v0.5/manual-verification.md`

手动验证文档必须包含：

- 验证对象：exe、网页、发布包、分支、commit、tag、配置路径、日志路径。
- 前置准备：关闭旧进程、清理旧日志、解压路径、配置项、账号/权限/设备要求。
- 验证步骤：逐步写清每一步怎么操作、点击哪里、等待多久、观察什么。
- 预期结果：UI 表现、日志事件、配置变化、文件产物、截图要求。
- 证据要求：截图、日志尾部、录屏、配置片段、生成文件、用户勾选结果。
- 通过标准：哪些必须通过，哪些可部分通过，哪些阻塞发布。
- 不通过处理：进入 bugfix、继续补证、回滚、暂缓发布或进入下一版本。
- 验证记录区：给用户填写实际结果、时间、环境、结论。
