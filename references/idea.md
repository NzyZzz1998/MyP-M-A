# /idea 入口工作流

`/idea` 完成“发现问题 -> 判断价值”：接收需求、Review、反馈、日志、截图、竞品、技术发现或业务目标，判断问题真假、证据、价值、时机及最小下一步。它不是路由或 PRD。

- 首行写 `入口判断：/idea`，紧接结论，不能用标题代替。
- 直接回答：真假、证据、用户价值、时机、是否压力测试、分数与低分项、最小下一步。证据不足时使用“暂定判断 / 待验证”，不得硬判。
- 3 个以上可拆需求时读取 `templates/idea-pool-template.md`，创建 `.md` 需求池并写依赖；1～2 个可在聊天中完成。
- 比率先锁定统计对象、粒度、分子、分母、时间窗、时区、新鲜度、缺失/重复/测试数据和代表性。时间范围与更新时点不得互换。
- 数值来源标记为 `N1 已确认事实`、`N2 可复算结果`、`N3 内部启发式`、`N4 建议阈值`。N2 写公式、分子分母和时间窗；缺少分母或时间窗不输出比率。N3 只辅助排序；N4 无依据时写“建议值/待确认”，不进入正式门禁。直接证据足够时可跳过压力总分，但须写理由与证据。
- 反馈与日志并存时保留反馈 ID、角色、版本、任务 ID 和失败原因绑定；角色必须落到对应反馈。
- 无数据或工具时不输出伪精确结论；给最小采集、质量门槛和分析去向。
- 没有明确证据支撑的中高价值需求必须做带证据评分的压力测试。跳过完整压力测试时也要写明理由。
- 压力测试后仍有决策未知时读 `references/red-team.md`，只保留 3～5 个承重假设、最低成本实验和继续/缩小/停止阈值。
- 输入含访谈、JTBD、切换行为或机会树时读 `references/discovery.md`，分开事实、解释、机会和方案。仅需案例校准时读 `references/case-library.md`，不得继承案例事实。
- 输入涉及市场、细分用户、定位、替代方案、定价、商业模式、GTM、渠道或增长时读 `references/strategy-gtm.md`；给选择与排除项，把无来源的市场数字、支付意愿和渠道效果保留为假设。
- Discovery 实验使用 `对象 | 样本/分母 | 时间窗 | 继续阈值 | 缩小/停止阈值`。数值无依据时把“确认阈值”列为执行前门禁，不编造样本量或用“多数、稳定、效果好”替代。

## 处理流程

### 1. 拆分并翻译问题

识别问题、需求、方案、反馈、Bug、体验感受或业务目标，保留原始表达，再写清：谁在什么场景遇到什么影响；它是用户问题还是方案冲动；属于可用性、效率、信任、审美、稳定性、增长或维护成本中的哪类。

3 个以上需求必须落盘。用户未指定路径时，在当前工作区创建 `mypm-idea-pool-YYYY-MM-DD.md`；不能写文件时输出完整 Markdown 并说明建议文件名。聊天只汇报总体分流和文件路径，不复制全文。

### 2. 建立证据与反证

按来源记录证据、强弱、时间和适用范围：

- **强证据**：多次真实反馈、行为数据、日志/错误报告、稳定复现，或能解释适用性的强对标。
- **中证据**：访谈/试用/社群信号、核心路径 Review、开发测试风险、尚未证明需求强度的竞品做法。
- **弱证据**：个人直觉、单次观感、只因竞品存在、为了完整或高级。弱证据最多支持继续验证。
- **反证**：低频、不影响核心目标、已有低成本替代、典型用户不需要、范围或维护成本过大。

用户提供项目、数据库、表格、日志、GitHub、Issue、截图、录屏、埋点或历史验收材料时，按 `references/tooling.md` 选择最小只读取证；工具只用于判断真假与价值，不冒充 `/acceptance`。

涉及指标、日志统计、数据库、漏斗、分群、市场规模或数据质量时读 `references/data-analysis.md`。先做最小数据地图：来源、表/字段、主外键或关联、量级、异常值、权限和质量；再选择当前决策真正需要的分析。数据库不可访问时标为假设，不猜表、字段或数据量。

复杂分析最终压缩为一个证据包：

1. 决策问题及本次真正回答的部分。
2. 数据来源、统计对象、粒度、时间范围、时区和数据新鲜度。
3. 数据质量、代表性、偏差与置信边界。
4. 关键发现、反证和替代解释。
5. 当前数据不能推出的结论。
6. 对真假、价值和时机的影响。
7. 最小补证动作或实验。

### 3. 判断价值与阶段

结论使用：高价值、中价值、低价值、待验证、不建议。每项都写“基于什么证据”和“仍缺什么证据”。再判断当前阶段：探索期验证问题，打磨期修核心体验，稳定期重可靠性与回滚，增长期看转化/留存/传播。个人项目默认更严格，不轻易接受平台、市场或大配置中心。

最终分流使用：

- **继续**：证据足且符合当前目标，可进入 `/prd`。
- **小范围验证**：方向可能成立，但证据或范围未闭合。
- **延后**：有价值但时机或依赖不合适。
- **不做**：问题不成立、成本过高或偏离主线。
- **直接治理/Bugfix**：事实已清楚且不改变产品合同；不为文档、测试或明确缺陷强行写 PRD。

## 压力测试

除“明确证据支撑、当前阶段适配、影响可控的中高价值需求”外都执行。评分用于暴露弱项，不能替代证据；每维 0～5 分，总分 40 分：

| 维度 | 核心问题 |
| --- | --- |
| 用户痛点强度 | 是否影响核心体验、效率、信任、留存或收入 |
| 用户/场景清晰度 | 角色、触发、频率、前后步骤和任务是否明确 |
| 证据强度 | 是否有反馈、数据、日志、复现或可解释对标 |
| 频率/紧迫性 | 不做的损失及是否正在发生 |
| 核心目标贡献 | 是否直接支撑当前版本目标或核心路径 |
| 差异化/替代方案 | 是否存在更小、更便宜的解法 |
| 成本可控性 | 开发、维护、迁移和回滚边界是否清楚 |
| 验证速度 | 能否低成本得到明确失败信号 |

分档：`32～40` 可推进候选；`24～31` 收敛为小版本或原型；`16～23` 只验证；`0～15` 当前不做。证据、痛点、成本可控性或验证速度低于 3 分时触发闸门：不得被总分抵消，分别降级为待验证、缩小范围或先设计实验。两个需求只差 1～2 分时不机械排序，优先比较证据闸门、版本目标、依赖和不可逆风险。

压力测试必须回答：真实问题和用户是谁、不做会怎样、现有替代是什么、是否让产品变重或破坏旧体验、是否挤占更重要事项、最小实验是什么、什么证据才允许进入 `/prd`。结论为通过、部分通过、未通过或信息不足，并给低分项的补证或缩小动作。

承重假设只选择会改变做法的主张。优先复用现有日志、查询、反馈和复现；Agent 模拟与合成数据只能预检，不能关闭真实用户或生产数据门禁。

## 输出结构

单需求默认只保留：结论、产品问题、证据/统计口径、价值与时机、压力测试或跳过理由、承重假设、最小下一步。能按 ID 关联的反馈与日志使用一张表；不能关联时明确缺口，不重复逐条事实。

多需求文件至少包含：总体判断、版本主线、需求总览、依赖关系和逐项分析。固定字段为：编号、标题、原始来源、输入类型、产品问题、证据等级、价值/阶段、压力测试评分与低分项、分档结论、依赖、建议去向、最小下一步。

版本型输入来自 Review、Acceptance、Bugfix 或上一版本反馈时，再补：

- 本版真正解决的问题，以及为什么不是更大的方向。
- 上一版本证据到候选需求的映射。
- 最小、推荐、过大三档范围。
- `进入 /prd / 现在直接做 / 继续验证 / 暂不做` 的最终分流。

## 质量终检

- 未把方案直接当需求，未把所有输入推进 PRD。
- 事实、推断、假设和反证可追溯；统计口径完整。
- 评分绑定证据，关键闸门未被总分覆盖。
- 样本、阈值、市场规模和收益没有伪精确。
- 需求超过 2 个时已落盘，依赖和下一步可执行。
