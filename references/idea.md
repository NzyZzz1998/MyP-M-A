# /idea 入口工作流

`/idea` 是 MyP-M-A 的“发现问题 -> 判断价值”入口。它接收外部需求、内部 review 发现、模糊想法、截图反馈、竞品启发、技术发现和业务目标，然后直接给出一个轻量结论。

`/idea` 不是单纯路由，也不等于 PRD。它应该在当前上下文内尽量完成判断：这是真问题吗、值不值得继续、现在该不该做、证据是否足够、下一步最小动作是什么。

当需求没有明确证据支撑，或价值不足以直接推进时，`/idea` 必须做带评分的压力测试，帮助 PM 重新认识这类需求，而不是顺手把它推进需求池。

- 首行写 `入口判断：/idea`，再给结论；不要让标题或长分析代替入口判断。
- 输入含 3 个以上候选需求时，输出或明确创建 `.md` 需求池，并写出候选项依赖关系。
- 涉及完成率、漏斗或分群时，先核对分子、分母、统计对象、粒度、时间窗、数据新鲜度、缺失/重复/测试数据和样本代表性，再讨论价值。
- 数据证据包中的“时间范围”和“数据新鲜度”是两个独立字段：前者说明观察哪段时间，后者说明数据更新到何时、是否仍适用于当前决策；不得互相代替。
- 附件同时含反馈与日志时，逐条保留反馈 ID、角色、版本、任务 ID 和失败原因的已知绑定；管理员、运营等角色必须分别落到对应反馈，不能只在汇总句里说“覆盖多个角色”。
- 没有数据或联网能力时，不给伪精确结论；写清最小采集方案，以及数据质量达到什么条件后调用产品分析、指标诊断或市场规模能力。
- 复杂数据判断最终压缩为证据包，明确不能推出的结论和对“做不做、何时做”的影响。
- 压力测试后仍有会改变做法的关键未知时，读取 `references/red-team.md`，只输出 3-5 个承重假设、最低成本实验和预先约定的继续/停止阈值。
- 输入包含访谈、研究笔记、JTBD、用户切换行为或机会树时，读取 `references/discovery.md`；先把事实、解释、机会和方案分开，再回到本入口判断真假、价值与时机。只有用户要求案例或需要校准交付深度时才读 `references/case-library.md`，不得继承案例中的项目事实。
- 输入涉及目标市场、细分用户、定位、替代方案、定价、商业模式、GTM、渠道或增长时，读取 `references/strategy-gtm.md`；必须给选择与排除项，并将无来源的市场数字、支付意愿和渠道效果保留为待验证假设。
- Discovery 输入需要实验时，使用 `对象 | 样本/分母 | 时间窗 | 继续阈值 | 缩小/停止阈值` 表；数值缺少依据时把“确认阈值”列为执行前门禁，不以“多数、稳定、效果好”代替。

## 适用输入

- 用户明确说“/idea 我想做……”
- 用户说“我有个想法”“这个需求怎么样”“帮我判断值不值得做”
- 用户给截图、体验反馈或 review 发现的问题池
- 用户提出一个方案，但问题定义还不清楚
- 用户想把外部反馈录入需求池
- 用户想知道一个方向是不是自嗨
- 用户一次性输入多个需求，希望整理成需求池

## 核心输出

处理 `/idea` 时，直接回答这些问题：

1. 这是真问题吗？
2. 证据从哪里来，够不够？
3. 它对用户有什么价值？
4. 值不值得继续？
5. 现在该不该做？
6. 是否需要压力测试？
7. 压力测试分数是多少，低分项是什么？
8. 如果继续，最小下一步是什么？

如果证据不足，不要硬判。可以给“暂定判断 + 压力测试评分 + 需要补的证据 + 最小验证方式”。

## 单需求与多需求

### 单需求

如果输入只有 1-2 个需求，可以直接在对话中输出 `/idea 结论`。

### 多需求

如果输入中包含 3 个或更多可拆分需求，必须通过 `.md` 文件输出，方便后续整理为需求池。

文件输出规则：

- 如果用户指定文件路径，写入用户指定路径。
- 如果用户没有指定路径，在当前工作区创建 `mypm-idea-pool-YYYY-MM-DD.md`。
- 如果当前环境不能写文件，输出完整 Markdown 内容，并提示建议保存为该文件名。
- 文件必须包含需求总览表和每个需求的单独分析。

多需求文件的结构：

## 证据标准

判断价值时不能只凭项目 review 或主观感觉。可以使用以下证据来源，并明确标注证据强弱。

如果用户提供 GitHub 链接、用户反馈文档、竞品线索、数据表、项目路径或 review 结果，按 `references/tooling.md` 选择最小必要工具补证据。`/idea` 调用工具的目的只是判断问题真假和价值，不做实际验收；实际验收交给 `/acceptance`。

### 强证据

- 真实用户多次反馈同一问题。
- 行为数据显示用户卡住、流失、重复点击、放弃流程。
- 日志或错误报告能证明问题发生。
- 人工测试稳定复现。
- 竞品或同类产品普遍采用某模式，并且能解释为什么适用于当前产品。

### 中证据

- 用户访谈、朋友试用、社群讨论中出现相关信号。
- 项目 review 发现的问题与核心路径、高频操作或产品信任相关。
- 竞品中存在类似设计，但还不能确认用户是否真的需要。
- 开发或测试指出当前实现会造成维护、稳定性或理解成本。

### 弱证据

- 只有产品直觉。
- 只有“我觉得可以加”。
- 只有单次截图观感。
- 只有竞品有，但不知道为什么有。
- 只是为了显得完整、专业或高级。

弱证据不能支撑“马上开发”，最多支撑“继续验证”。

## 压力测试

### 触发条件

除“有明确证据支撑的中价值或高价值需求”外，其他需求都要做压力测试。

需要压力测试的情况包括：

- 证据等级为弱。
- 价值判断为低价值、待验证或不建议。
- 需求来自方案冲动，而不是用户问题。
- 需求范围明显偏大。
- 需求看起来“完整、专业、高级”，但用户价值不清楚。
- 需求可能破坏当前产品的轻量性、可完成性或核心体验。
- 当前阶段不适合，但用户仍想推进。

不需要完整压力测试的情况：

- 有强证据或明确中证据。
- 价值判断为中价值或高价值。
- 当前阶段适配。
- 影响范围可控。

即使免测，也要简短说明为什么可以跳过压力测试。

### 评分卡

压力测试参考创业 idea pressure test 的做法，但要改成产品需求评分。每个维度 0-5 分，总分 40 分。打分时必须写明证据，不允许只写“感觉不错”。

| 维度 | 0-1 分 | 2-3 分 | 4-5 分 |
| --- | --- | --- | --- |
| 用户痛点强度 | 只是想要、好看或完整 | 有不便，但不阻塞 | 明显影响核心体验、效率、信任、留存或收入 |
| 目标用户/场景清晰度 | 不知道谁用、何时用 | 有大致用户和场景 | 用户、场景、触发时机、任务目标都清楚 |
| 证据强度 | 只有直觉或单次观感 | 有 review、访谈、少量反馈或竞品信号 | 有多次反馈、数据、日志、稳定复现或强对标解释 |
| 频率/紧迫性 | 低频，晚点做也无影响 | 中频或影响一类用户 | 高频、阻塞、正在造成明显损失 |
| 核心目标贡献 | 和当前目标弱相关 | 能改善体验但不影响主线 | 直接支撑当前版本目标或核心路径 |
| 差异化/替代方案 | 有更小替代方案，需求本身不必要 | 需要做，但可大幅缩小 | 替代方案弱，当前方案是合理最小解 |
| 成本可控性 | 范围大、维护重、风险高 | 成本中等，可拆分 | 成本小、边界清晰、可回滚 |
| 验证速度 | 很难验证，验证成本高 | 可通过原型、访谈或日志验证 | 很快能验证，且失败信号清楚 |

评分解释：

- 32-40 分：可进入推进候选，但仍要检查阶段适配和影响范围。
- 24-31 分：建议小范围推进或原型验证，不宜一次做完整版本。
- 16-23 分：只建议验证，不建议进入正式 PRD。
- 0-15 分：当前不建议做，除非补到关键证据。

证据闸门：

- 如果证据强度小于 3 分，整体结论最高只能是“待验证”或“小范围验证”，不能直接判定“继续开发”。
- 如果成本可控性小于 3 分，即使总分高，也必须拆出更小版本或延后。
- 如果用户痛点强度小于 3 分，不能因为“看起来高级/完整/竞品有”而推进。
- 如果验证速度小于 3 分，下一步优先是设计验证方法，而不是写 PRD。

### 压力测试问题

对需要压力测试的需求，至少回答这些问题：

1. 用户真实问题是什么？如果说不清，说明它可能只是方案。
2. 谁会频繁遇到？频率和痛感是否足够？
3. 不做会怎样？是否真的会影响核心体验、信任或留存？
4. 有没有更小、更便宜的替代方案？
5. 这个需求会不会让产品变重、变复杂、变难维护？
6. 它是否破坏已有体验、默认行为或用户习惯？
7. 当前阶段做它，是否会挤占更重要的事项？
8. 如何用最小成本验证它？
9. 什么证据出现后才值得进入 `/prd`？

### 压力测试结论

压力测试后必须给出一个结论：

- 通过：通常为 32-40 分，可以继续推进，但仍需控制范围。
- 部分通过：通常为 24-31 分，只建议做更小版本或原型验证。
- 未通过：通常为 0-15 分，不建议当前推进。
- 信息不足：通常是关键维度缺证据，尤其是证据强度、用户痛点或目标场景不清，需要补证据后再判断。

压力测试的目标不是否定需求，而是防止 PM 被“功能看起来很完整”迷惑。

### 从评分进入假设验证

8 维评分用于暴露弱项，不自动告诉用户应该做什么实验。出现以下任一情况时，继续使用 `references/red-team.md`：

- 证据、痛点或验证速度低于 3 分，但需求仍可能影响主线。
- 总分较高，但结论依赖一个尚未证明的用户、机制、商业或技术主张。
- 用户准备投入开发，却无法说出什么结果会让自己缩小、转向或停止。

只挑会改变决策的承重假设，不把全部风险重新包装成实验清单。现有日志、查询、反馈和复现能回答时先复用；Agent 模拟和合成数据只能做预检，不能关闭真实用户或生产数据门禁。

## 处理流程

### 1. 拆分原始输入

先判断输入中有几个独立需求。

- 1-2 个：直接输出对话结论。
- 3 个或以上：输出 `.md` 需求池文件。

拆分时保留原始表达，不要过度改写。

### 2. 输入类型

从下面选择一个或多个：

- 问题：用户描述了不顺、错误、低效、困惑。
- 需求：用户明确提出想要某个能力。
- 方案：用户已经提出实现方式。
- 反馈：来自用户、朋友、社群、测试或自用。
- Bug：有可复现异常或日志证据。
- 体验感受：例如怪、丑、不精致、不顺。
- 业务目标：例如提升留存、降低投诉、提高转化。

### 3. 问题翻译

把原始输入翻译成产品问题：

- 影响谁？
- 在什么场景发生？
- 影响是什么？
- 是真实问题，还是方案冲动？
- 属于可用性、效率、信任、审美、稳定性、增长，还是维护成本问题？

### 4. 证据盘点

列出当前已有证据：

- 用户证据：有没有用户反馈、访谈、评论、社群信号。
- 行为数据：有没有点击、留存、完成率、错误率、重复操作。
- 项目证据：有没有截图 review、日志、bug、测试复现、技术限制。
- 对标证据：同类产品是否存在类似做法，为什么可能适用或不适用。
- 反证：有没有说明这个需求可能不重要、太早或过度设计的信号。

如果用户要求判断同类产品或当前市场做法，而上下文没有资料，应主动说明需要检索或让用户提供竞品；拿到资料前只能给假设判断。

### 5. 价值判断

给出一个明确等级：

- 高价值：影响核心路径、稳定性、信任或高频体验，并且有较强证据。
- 中价值：能改善体验，有一定证据，但不阻塞主流程。
- 低价值：锦上添花，证据弱，当前阶段可延后。
- 待验证：可能有价值，但证据不足。
- 不建议：成本高、范围大、偏离当前阶段，或用户价值不成立。

判断必须写清“基于什么证据”和“缺什么证据”。

### 6. 当前阶段判断

判断它是否适合当前产品阶段：

- 探索期：优先验证问题是否真实。
- 打磨期：优先修核心体验和精致度。
- 稳定期：优先可靠性、日志、回滚和边界情况。
- 增长期：优先转化、留存、传播。

对个人项目默认更严格：不轻易接受大系统、大平台、大配置中心。

### 7. 压力测试

根据触发条件判断是否需要压力测试。

- 明确证据支撑的中高价值需求：可跳过完整压力测试，只给跳过理由；必要时给简短总分辅助排序。
- 其他需求：执行评分卡，给出各维度分数、总分、低分项、证据闸门和通过、部分通过、未通过或信息不足。

### 8. 结论与下一步

输出一个轻量结论：

- 继续：证据足够，且适合当前阶段。
- 小范围验证：方向可能对，但证据不足或压力测试只部分通过。
- 延后：有价值但当前不是时候。
- 不做：问题不真实、成本过高、压力测试未通过或偏离主线。

然后给最小下一步：

- 做一次用户访谈。
- 收集 5 条真实反馈。
- 加日志验证。
- 做一次 A/B 或人工对比。
- 看 3 个同类产品如何处理。
- 写一份 product brief。
- 直接进入轻量 PRD。

## 默认输出结构

单个需求在聊天中默认只保留：结论、证据/统计口径、压力测试、承重假设与最小下一步。原始输入、产品问题、价值判断和当前阶段可合并进首段，不建立内容重复的独立章节。反馈和日志能按 ID 关联时优先使用一张关联表；不能关联时分别保留最小事实表，并明确关联缺口，不在后续段落重复逐条事实。

输入超过 2 个需求时读取 `templates/idea-pool-template.md` 并落盘；聊天只汇报分流结果和文件路径，不再复制整份需求池。

压力测试分数可以用紧凑表格呈现：

```markdown
| 维度 | 分数 | 证据/理由 |
| --- | --- | --- |
| 用户痛点强度 |  |  |
| 目标用户/场景清晰度 |  |  |
| 证据强度 |  |  |
| 频率/紧迫性 |  |  |
| 核心目标贡献 |  |  |
| 差异化/替代方案 |  |  |
| 成本可控性 |  |  |
| 验证速度 |  |  |
```

总分后要写分档结论，例如：`总分 21/40，证据强度 1 分触发证据闸门，因此最高只能判定为待验证。`

## 质量要求

- 不要把用户的方案直接当成需求。
- 不要只做路由，必须给出轻量结论。
- 不要把所有输入都推进 PRD。
- 必须说明证据来自哪里，证据强弱如何。
- 如果只有项目 review 或个人直觉，要明确说证据不足。
- 如果需要竞品或用户数据支撑，要说明需要什么资料。
- 如果输入明显过大，主动拆小或建议暂缓。
- 除明确证据支撑的中高价值需求外，必须做带分数的压力测试。
- 压力测试分数必须绑定证据，并说明低分项如何补证据或缩小范围。
- 如果需求数量大于 2，必须输出 `.md` 文件形式的需求池。

## 示例判断

输入：“我想做插件市场。”

可能输出：

- 输入类型：方案 / 新功能想法。
- 产品问题：用户可能希望扩展桌宠能力，但当前是否存在足够扩展需求未证明。
- 证据盘点：当前只有产品直觉和功能想象，没有用户反馈、使用数据或同类产品适配分析，证据弱。
- 价值判断：待验证偏低价值。
- 当前阶段：如果产品还在打磨核心体验，不适合做平台型能力。
- 压力测试分数：13/40，未通过。痛点 1、场景 2、证据 1、频率 1、核心目标 2、差异化 2、成本 1、验证速度 3。真实用户问题不清楚，范围大，维护成本高，会挤占核心体验打磨。
- 低分项：用户痛点、证据强度、成本可控性。
- 结论：不建议当前做插件市场。
- 最小下一步：先收集用户是否真的想要更多宠物、主题或自定义能力；如果有信号，先做主题预设或宠物包导入，而不是插件市场。

## 数据分析补强

`/idea` 不应只依赖用户的主观描述或项目 review。只要用户给出项目路径、日志、数据库、表格、GitHub 链接、Issue、用户反馈、截图、录屏、埋点、配置或历史验收材料，就应主动判断是否能提取数据证据。

当判断依赖指标、漏斗、分群、市场规模、数据质量或复杂日志统计时，读取 `references/capability-routing.md`。只选择一个最贴近当前决策问题的专门能力；如果当前环境没有对应能力，按本文件和 `references/data-analysis.md` 完成可支持部分，不把能力名称写成已调用事实。

没有原始数据时不要调用分析能力，但要写明后续路由：先收集达到最小样本与字段要求的数据并做数据质量检查；质量可用后，再用产品分析、指标诊断或市场规模能力回答业务问题。只写“以后分析”不算完整取证方案。

优先寻找这些数据：

- 使用数据：访问量、活跃用户、触发次数、功能使用频率、留存、转化、完成率。
- 行为路径：入口、关键步骤、退出点、取消点、失败点、重复操作。
- 问题数据：错误日志、崩溃、失败率、重试次数、客服反馈、Issue 数量、复现次数。
- 用户分群：新用户/老用户、轻度/重度、不同设备/系统/版本、不同套餐/角色。
- 成本数据：开发复杂度、维护成本、性能成本、支持成本、用户迁移成本。
- 替代方案数据：用户当前如何绕过问题、竞品如何处理、是否已有低成本替代。

如果没有数据，要明确写出“当前缺少的数据”，并给出最小取证动作，例如补 3-5 条真实用户反馈、从日志统计一周内错误次数、检查数据库中相关字段分布、用 Computer Use 或浏览器复现关键路径、用竞品截图或公开文档验证同类方案。

涉及数据库时，先做数据理解，不急着给方案。输出至少包含相关表、字段、主键/外键或关联方式、当前数据量级和异常值、是否需要新增表/字段/索引/迁移、现有数据是否足以支撑需求判断。如果无法访问数据库或数据源，不要假装有数据；把结论降级为假设，并写清下一步取证方式。

如果数据来源复杂，或涉及数据库、日志统计、指标口径、漏斗、分群、样本偏差，读取 `references/data-analysis.md`，按其中的最小数据地图和阶段输出处理。不要把复杂数据分析全部塞进 `/idea` 正文。

复杂分析完成后，必须把结果压缩为证据包：

- 决策问题，以及分析真正回答了哪一部分。
- 数据来源、统计对象、粒度、时间范围和数据新鲜度。
- 数据质量、代表性、偏差和置信边界。
- 关键发现、反证或其他可能解释。
- 当前数据不能推出的结论。
- 对“真假、价值、时机”的影响。
- 最小补证动作或实验。

不能说明分母、时间窗、样本来源或数据质量时，不输出看似精确的失败率、用户比例、市场规模或收益预测。专门分析报告可以作为附件或证据文件，`/idea` 正文只保留会改变产品判断的部分。

## 用户与场景压力测试

除非需求已有明确证据且中高价值，否则 `/idea` 要主动对用户和场景做压力测试。压力测试不是质疑用户，而是帮助 PM 避免自嗨。

至少检查：

- 目标用户是谁：具体到角色、场景、频率，而不是“所有用户”。
- 触发场景是什么：用户在什么时候遇到问题，前一步和后一步是什么。
- 痛点是否真实：有没有行为、日志、反馈或复现证据。
- 当前替代方案是什么：用户是否已经有办法绕过，绕过成本多高。
- 不做会怎样：是否影响核心目标，还是只是体验小瑕疵。
- 做小版是否足够：是否可以先用文档、配置、提示、轻量 UI、手动流程验证。
- 谁会反对或不用：有没有典型用户根本不需要它。

如果用户输入只是一句话想法，要先补场景，而不是直接写需求池。可以用简短问题或“假设版压力测试”输出：已知事实、关键假设、最大缺口、我会先问你的 3 个问题、未回答前的临时判断。

## 固定评分阈值

压力测试采用 8 个维度，每项 0-5 分，总分 40 分。分档建议：

评分用于暴露证据和取舍，不代表统计精度。两个需求只差 1-2 分时，不据此机械排序；优先比较证据闸门、当前版本目标、依赖关系和不可逆风险。关键维度只能写“判断”而没有证据时，同时给出置信度和补证动作。

- `32-40`：高价值，证据较强，可进入 `/prd` 或直接进入开发承接前的 PRD 澄清。
- `24-31`：中等价值，需要收敛范围；通常先进入最小方案 PRD 或补关键证据。
- `16-23`：证据不足或价值不稳，进入继续验证，不应直接写完整 PRD。
- `0-15`：当前不建议推进；保留为观察项或暂不做。

如果某项高分但没有证据，要降级并说明“这是判断，不是事实”。如果总分较高但成本不可控，不能直接进入完整 PRD，应先做技术 spike 或原型验证。

## 版本型需求池

当 `/idea` 输入来自上一版本 review、acceptance、bugfix、用户验收反馈或版本规划时，必须输出版本主线判断。

版本型需求池应包含：

- 本版本主线：一句话说明本版本真正要解决什么。
- 为什么不是其他方向：明确排除更大的主题、安装器、自动更新、多平台、主题系统等范围外目标。
- 证据映射：把上一版本验收项、bugfix、用户反馈、日志证据映射到候选需求。
- 依赖关系：用 Mermaid 或表格说明哪些需求依赖控件系统、架构治理、数据字段、后端能力或发布流程。
- 三档范围方案：最小方案、推荐方案、过大方案。
- 最终分流：进入 `/prd`、现在直接做、继续验证、暂不做。

如果候选需求超过 2 个，必须输出 `.md` 需求池文件，并使用固定字段：编号、标题、来源、证据等级、压力测试评分、分档结论、依赖关系、建议去向、最小下一步。
