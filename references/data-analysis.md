# 数据分析工作流

本文件用于补强 `/idea`、`/prd` 和必要时 `/acceptance` 的数据判断能力。它不要求每个项目都有复杂数据系统，但当用户提供日志、数据库、表格、埋点、Issue、反馈或后端架构时，MyP-M-A 应用数据支撑判断，而不是只凭主观感觉。

## 什么时候读取

读取本文件的情况：

- `/idea` 需要判断需求真假、价值、影响面或优先级，但仅靠用户描述不够。
- 用户提供数据库、日志、表格、埋点、GitHub issue、客服反馈、用户访谈、错误报告。
- `/prd` 涉及后端、数据库、数据来源、字段、查询、筛选、报表、推荐、权限或状态流。
- `/acceptance` 需要核对日志、埋点、数据兼容、迁移结果或线上观察指标。

不要为了显得专业而强行设计复杂指标系统。个人项目、小工具或早期原型可以使用日志、人工记录、截图对比和少量样本。

## 按输出用途选择深度

先区分字段核对、指标定义、模型讲解、异常诊断或研发交付，按请求交付，不因提到数据就自动输出完整数据地图、KPI 合同或工程方案。

- 只查字段时，给字段、取值/口径、来源位置和差异/未知的紧凑结果；指定 PDF 或版本优先，不从其他草稿静默补齐。未知物理表名和映射保持待核验。
- 讲核心模型时，围绕要解决的问题、输入及来源、中文计算逻辑、取值理由、可复算算例和结果用途解释；技术字段只在有助理解时并列，不扩写字段百科。这是组织线索，不强制六节模板。
- 权重、阈值和示例值分别说明来自材料、用户决定、建议或演示假设；核对单位、时间范围、舍入和适用边界。聚合比例按业务定义汇总分子分母后复算，不默认平均每日百分比。示例不能证明生产数据、阈值有效或真实效果。

局部解释只展开影响理解的边界；正式完整数据合同仍覆盖必要异常和验收。技术交付深度继承 `references/work-mode-boundary.md`，不因输入 schema 自动获得工程设计或写库授权。

- 日志或任务数据用于产品判断时，先输出“统计对象快照”，分别列出事件数、去重任务数、按明确终态规则得到的最终失败任务数、去重用户/租户数；四项都必须出现，无法确认的项写“无法确认”及原因，不能静默省略。
- 每个数量绑定唯一键、筛选条件和时间窗。事件失败占比、任务失败占比和用户失败率分别计算；其中任一项不能冒充总体线上失败率。
- 重试只增加事件/尝试次数，不增加任务数；小样本可以证明风险信号存在，但不能单独证明需要整体重做。
- 区分“样本内已观测最终状态”和“业务权威终态”。当每个任务只有一条结果，或 attempt/retry、序号、时间等能确定样本内最后一次结果时，必须计算已观测最终失败任务数，同时说明它不必然等于完整生命周期终态；只有事件先后也无法确定时才写“无法确认”。
- “最终失败”不等于“重试后仍失败”。只有同一任务存在至少两次可排序尝试，且最后一次仍失败，才可写“重试后仍失败”；只有一次失败记录时写“样本内最终失败，但未观察到重试”。

## 数据输入类型

常见输入：

- 日志：debug log、access log、error log、诊断文件、崩溃报告。
- 数据库：schema、SQL、迁移文件、样本数据、ORM model、配置表。
- 表格：用户反馈、测试记录、问卷、手动验收结果、需求池。
- GitHub：Issue、PR 评论、CI 失败、Release 记录、commit 历史。
- 产品行为：埋点事件、点击、转化、留存、漏斗、功能使用频率。
- 定性材料：访谈、社群反馈、截图、录屏、客服记录。
- 竞品材料：公开文档、截图、定价页、更新日志、用户评论。

## 分析顺序

### 1. 先判断数据是否能回答问题

先写清楚：

- 本次要回答的问题是什么。
- 现有数据能回答哪一部分。
- 哪些结论只能是假设。
- 还缺哪些数据。

不要把“有数据文件”误当成“有证据”。数据必须能支撑当前判断。

### 2. 建立最小数据地图

涉及数据库或后端且本轮需要梳理结构或血缘时，输出最小数据地图；单项字段核对或模型解释只列所需部分：

- 表 / 文件 / 模型：
- 关键字段：
- 主键 / 外键 / 关联方式：
- 状态字段：
- 时间字段：
- 用户或租户字段：
- 配置字段：
- 日志或埋点事件：

如果无法确认，标为“待确认”，不要编造。

### 3. 看样本和分布

优先看：

- 数据量级。
- 空值、异常值、重复值。
- 最近时间范围。
- 高频用户或高频场景。
- 错误集中在哪些版本、设备、配置或路径。
- 是否存在样本偏差。

### 3.1 先锁定统计对象与不能得出的结论

当输入同时包含反馈、日志、任务、订单、用户或租户记录时，先分别定义统计对象，再写数量。例如“3 条反馈”“3 个任务”“其中 2 个失败任务”是不同事实，不能自动推导为“3 个受影响用户”或“失败率 66%”。

数量来自附件或查询结果时，先机械枚举每个对象的唯一键，再计数并做一致性校验：`列出的唯一 ID 数 = 声明的对象数`。任务日志还要分别列事件数、去重任务 ID、按明确顺序或终态规则得到的最终失败任务，以及去重用户/租户；没有时间或终态顺序时不得自行选“最后一条”。重试事件只计入事件数和尝试次数，不能增加任务数。

每个用于产品判断的数量至少说明：

- 对象是什么：反馈、请求、任务、去重用户、租户、订单或其他实体。
- 时间窗口、筛选条件和版本/环境边界。
- 分子、分母和去重键；缺少其中任一项时，明确写“无法计算比例/影响用户数”。
- 在正文写比例前复核分子、分母与已枚举 ID，禁止出现“列出 5 个任务 ID，却声明只有 4 个任务”这类自相矛盾。
- 事实归属：日志中的单条任务只能证明该任务及其字段，不能把不同版本、不同入口或不同批次的记录合并归因。

附件已经提供反馈 ID、角色、版本、任务 ID或失败原因时，关键发现必须逐条保留这些绑定关系；不能只写“覆盖管理员和运营”之类汇总句，导致无法判断哪条反馈来自哪个角色、对应哪个任务。反馈与日志同时存在时，先列可确认的对应关系，再把无法关联的记录标为待确认。

把“缺少什么数据”写成可补证字段，而不是笼统写“数据不足”。常见缺口包括总请求量、去重用户/租户键、版本发布基线、时间窗口、成功任务数、失败原因分布和样本来源。

反馈与日志共同支撑 `/idea` 时，最小补证动作应显式写出三联项：补齐总量/成功/失败数作为失败率分母，按版本与用户/租户交叉分组，并建立反馈 ID 与任务日志的关联。除非材料本身不具备某个维度且明确说明替代动作或跳过原因，不得只按批量大小或错误类型分组后就宣称影响范围已闭合。

### 4. 转成产品判断

用于需求判断的数据分析回到产品问题；字段核对或模型解释直接完成指定交付，不强加立项分析：

- 问题是否真实。
- 影响多少用户或多少次操作。
- 是否影响核心路径。
- 是高频小痛点，还是低频大风险。
- 是否值得当前版本做。
- 最小可验证动作是什么。

## /prd 中的数据输出

`/prd` 编写完整数据需求时，按交付模式和已知材料选择以下内容；局部修订、字段核对与模型讲解不自动展开整套：

- 数据来源与存储位置。
- 前端写死 / 配置文件 / 后端接口 / 数据库查询 / 系统 API 的选择理由。
- 涉及表、字段、索引、默认值、枚举和兼容策略。
- 查询条件、排序、分页、缓存、权限。
- 新增字段或表的迁移方式。
- 空数据、加载失败、查询失败、权限不足、超时的 UI 和日志处理。
- 开发前验收需要查哪些数据或日志。

如果数据库结构不清，PRD 中必须标“待确认”，并把确认动作列为开发前阻塞或开放问题。

### 报表、排行榜与 KPI 数据契约

输入已经提供事件、表、字段、样例或统计口径时，先据此形成“已确认的暂定契约”，再只追问缺口。不得因为仍有开放问题而丢掉已知字段、重新从零盘问，或把整份数据设计退化为问题清单。

交付完整 KPI 契约时按以下五组核对；未知项不自造。核心业务语义、安全或范围冲突阻塞对应部分，物理实现未知列研发核对，低风险可逆缺口给带依据的待确认建议，不把局部解释升级成完整门禁：

1. **指标定义**：指标名、统计对象与粒度、分子、分母、去重键、采用的最终状态、空分母、低样本提示。
2. **时间与范围**：事件时间/处理时间、窗口、时区、数据截至时间、版本、租户/主体筛选、权限、迟到回填、删除或合并主体、未知状态。
3. **来源与血缘**：业务源表/事件、关键字段、清洗与聚合、API/缓存/页面去向、负责人、刷新频率和新鲜度 SLA。
4. **交付契约**：查询或 API 输入输出、排序/分页/缓存、前端加载/空/错误/过期状态，以及权限不足和数据不完整提示。
5. **验收样例**：至少包含正常、空分母、迟到数据、未知状态、删除/合并主体、低样本和越权样例，并写明期望结果。

唯一键必须继承完整作用域。字段只在租户内唯一时，去重、冲突、关联和验收键必须使用 `(tenant_id, object_id)`；不同租户出现相同 `object_id` 是合法事实，不能判为重复或异常。只有来源明确声明全局唯一时才可省略租户键。

<!-- contract:kpi-source-interface-completeness -->
事件型 KPI 用一张合同覆盖来源字段校验和逻辑接口：关键字段的缺失/格式/未知枚举处理；请求、结果行、截至时间/新鲜度及不同错误出口；调用者与服务端租户绑定。物理路径或类型未知时，用材料字段写 `字段 | 来源/推导 | 继承类型 | 必填/可空 | 约束` 并标 schema 核对，不留空也不编造。计数指标没有分母，应写“不适用”，不得把分子本身填成分母；只有比例才定义分子/分母。越权必须明确拒绝并审计，不能伪装成正常空结果。已知 Top N 等事实只固化到材料点名的出口；页面默认 Top N 不能自动扩成 API 硬上限或导出范围。未定义出口用 N4 建议、依据和确认点，不冒充已确认。并列排序等低风险缺口同样只给一个 N4 建议，不保留多个并列默认。

同一作用域去重键出现冲突主体、冲突状态或冲突时间时，不得任意“保留一条”。合同必须定义隔离/拒绝、数据完整性标记和告警出口；权威优先级未知时列为开发前门禁，并给可复现的冲突验收样例。

审计、数据完整性提示、告警等风险控制若不是材料原文，必须标成“由已知权限/质量风险推导的产品要求”或 N4 建议，不能混入“已确认事实”。推导要求可以进入推荐合同，但要给依据、责任人和确认点。

交付前按用户点名项核对 `来源字段 | 统计对象 | 去重键 | 时间边界 | 权限 | 异常 | 接口出口 | 页面状态 | 验收样例`。物理表名或字段类型未知可以作为 schema 核对门禁，但必须先给可实现的逻辑字段和约束；每个验收样例必须写具体输入记录、时间点、调用身份和期望输出/错误，不能只引用 `G-001` 等门禁编号代替可执行样例。

任何关键组未关闭时，明确写“数据契约部分完成”和具体阻塞；不要宣称完整，也不要忽略已经确认且可进入 PRD 的部分。

## 后端与数据库深度检查

当需求涉及真实后端或数据库时，除最小数据地图外，按风险选择检查：

- 数据所有权：用户、租户、组织或角色如何隔离，谁可以读写。
- 数据约束：主键、外键、唯一性、非空、枚举、默认值和审计字段。
- 查询行为：筛选、排序、分页、索引、缓存、超时和大数据量退化。
- 写入行为：事务、幂等、并发冲突、重试、部分成功和重复提交。
- 生命周期：创建、更新、软删除/硬删除、恢复、归档和保留期限。
- 迁移兼容：旧数据补值、灰度期间新旧代码兼容、失败回滚和修复脚本。
- 权限与隐私：最小权限、敏感字段、日志脱敏、导出边界和审计要求。
- 指标口径：分子、分母、统计粒度、去重键和最终状态；事件数、任务数、用户数和租户数不得混作同一分母。
- 时间语义：事件时间还是处理时间、时区、迟到数据进入哪个时间桶、历史回填是否重算，以及报表刷新频率和数据新鲜度提示。
- 长尾数据：空分母、未知状态、删除/合并租户、缺失维度和低样本量如何计算、排除、告警或展示。
- 数据血缘：从业务源表/事件，经过去重与聚合，到 API、缓存和页面的完整路径；标出每层负责人、刷新方式和可追溯字段。
- 状态契约：定义唯一的状态枚举、状态含义、允许迁移、终态、重试语义和日志字段；不要让 `processing`、`running`、`retrying` 等同义词在不同模块任意混用。

`/prd` 负责定义产品所需的数据行为和验收口径，不替代技术设计。涉及高并发、复杂事务、分库分表、生产迁移或不可逆数据操作时，明确要求技术设计或 spike，并把它列为开发承接前置条件。

数据库取证默认只读。除非用户明确授权，不执行写入、迁移、删除、生产修复或可能影响数据完整性的命令。

## /acceptance 中的数据输出

`/acceptance` 使用数据时，输出建议包含：

- 实际数据是否符合 PRD 预期。
- 迁移是否成功。
- 配置是否兼容旧版本。
- 日志 / 埋点是否按预期触发。
- 错误率、失败次数或异常样本。
- 是否需要人工补证或线上观察。

不要只说“日志正常”，要列出关键日志事件、时间、文件路径或查询结果。

## 常用分析问题

需求真假：

- 这个问题出现了多少次？
- 是多少用户遇到，还是一个用户反复遇到？
- 有没有最近版本集中出现？
- 是否有稳定复现路径？

价值判断：

- 影响核心路径吗？
- 用户是否已经找到替代方案？
- 替代方案成本高吗？
- 不做会造成流失、投诉、信任下降、收入损失还是维护成本增加？

范围判断：

- 能否先做只读、导出、提示、日志、配置的小版本？
- 是否必须改数据库？
- 是否必须改后端？
- 是否能先用前端静态枚举或配置文件验证？

验收判断：

- 做完后用什么数据证明有效？
- 日志事件名是什么？
- 数据库字段如何变化？
- 人工检查哪些样本？
- 多久后观察一次？

## 输出边界

- 不访问不到的数据，不假装分析过。
- 不用复杂指标掩盖证据不足。
- 不把数据库设计当成 PRD 的全部；数据设计要服务用户场景。
- 不在 `/idea` 阶段过早给出完整数据库构筑方案。
- 涉及高风险数据迁移时，必须提示需要技术评审和回滚方案。
