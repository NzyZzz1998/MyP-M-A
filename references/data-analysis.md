# 数据分析工作流

本文件用于补强 `/idea`、`/prd` 和必要时 `/acceptance` 的数据判断能力。它不要求每个项目都有复杂数据系统，但当用户提供日志、数据库、表格、埋点、Issue、反馈或后端架构时，MyP-M-A 应用数据支撑判断，而不是只凭主观感觉。

## 什么时候读取

读取本文件的情况：

- `/idea` 需要判断需求真假、价值、影响面或优先级，但仅靠用户描述不够。
- 用户提供数据库、日志、表格、埋点、GitHub issue、客服反馈、用户访谈、错误报告。
- `/prd` 涉及后端、数据库、数据来源、字段、查询、筛选、报表、推荐、权限或状态流。
- `/acceptance` 需要核对日志、埋点、数据兼容、迁移结果或线上观察指标。

不要为了显得专业而强行设计复杂指标系统。个人项目、小工具或早期原型可以使用日志、人工记录、截图对比和少量样本。

## 数据输入类型

常见输入：

- 日志：debug log、access log、error log、诊断文件、崩溃报告。
- 数据库：schema、SQL、迁移文件、样本数据、ORM model、配置表。
- 表格：用户反馈、测试记录、问卷、手动验收结果、需求池。
- GitHub：Issue、PR 评论、CI 失败、Release 记录、commit 历史。
- 产品行为：埋点事件、点击、转化、留存、漏斗、功能使用频率。
- 定性材料：访谈、社群反馈、截图、录屏、客服记录。
- 竞品材料：公开文档、截图、定价页、更新日志、用户评论。

## 分析顺序

### 1. 先判断数据是否能回答问题

先写清楚：

- 本次要回答的问题是什么。
- 现有数据能回答哪一部分。
- 哪些结论只能是假设。
- 还缺哪些数据。

不要把“有数据文件”误当成“有证据”。数据必须能支撑当前判断。

### 2. 建立最小数据地图

如果涉及数据库或后端，输出最小数据地图：

- 表 / 文件 / 模型：
- 关键字段：
- 主键 / 外键 / 关联方式：
- 状态字段：
- 时间字段：
- 用户或租户字段：
- 配置字段：
- 日志或埋点事件：

如果无法确认，标为“待确认”，不要编造。

### 3. 看样本和分布

优先看：

- 数据量级。
- 空值、异常值、重复值。
- 最近时间范围。
- 高频用户或高频场景。
- 错误集中在哪些版本、设备、配置或路径。
- 是否存在样本偏差。

### 3.1 先锁定统计对象与不能得出的结论

当输入同时包含反馈、日志、任务、订单、用户或租户记录时，先分别定义统计对象，再写数量。例如“3 条反馈”“3 个任务”“其中 2 个失败任务”是不同事实，不能自动推导为“3 个受影响用户”或“失败率 66%”。

每个用于产品判断的数量至少说明：

- 对象是什么：反馈、请求、任务、去重用户、租户、订单或其他实体。
- 时间窗口、筛选条件和版本/环境边界。
- 分子、分母和去重键；缺少其中任一项时，明确写“无法计算比例/影响用户数”。
- 事实归属：日志中的单条任务只能证明该任务及其字段，不能把不同版本、不同入口或不同批次的记录合并归因。

把“缺少什么数据”写成可补证字段，而不是笼统写“数据不足”。常见缺口包括总请求量、去重用户/租户键、版本发布基线、时间窗口、成功任务数、失败原因分布和样本来源。

### 4. 转成产品判断

数据分析的输出必须回到产品问题：

- 问题是否真实。
- 影响多少用户或多少次操作。
- 是否影响核心路径。
- 是高频小痛点，还是低频大风险。
- 是否值得当前版本做。
- 最小可验证动作是什么。

如果数据不足，优先给补证动作，而不是进入 PRD。

## /prd 中的数据输出

`/prd` 使用数据时，输出建议包含：

- 数据来源与存储位置。
- 前端写死 / 配置文件 / 后端接口 / 数据库查询 / 系统 API 的选择理由。
- 涉及表、字段、索引、默认值、枚举和兼容策略。
- 查询条件、排序、分页、缓存、权限。
- 新增字段或表的迁移方式。
- 空数据、加载失败、查询失败、权限不足、超时的 UI 和日志处理。
- 开发前验收需要查哪些数据或日志。

如果数据库结构不清，PRD 中必须标“待确认”，并把确认动作列为开发前阻塞或开放问题。

## 后端与数据库深度检查

当需求涉及真实后端或数据库时，除最小数据地图外，按风险选择检查：

- 数据所有权：用户、租户、组织或角色如何隔离，谁可以读写。
- 数据约束：主键、外键、唯一性、非空、枚举、默认值和审计字段。
- 查询行为：筛选、排序、分页、索引、缓存、超时和大数据量退化。
- 写入行为：事务、幂等、并发冲突、重试、部分成功和重复提交。
- 生命周期：创建、更新、软删除/硬删除、恢复、归档和保留期限。
- 迁移兼容：旧数据补值、灰度期间新旧代码兼容、失败回滚和修复脚本。
- 权限与隐私：最小权限、敏感字段、日志脱敏、导出边界和审计要求。
- 指标口径：分子、分母、统计粒度、去重键和最终状态；事件数、任务数、用户数和租户数不得混作同一分母。
- 时间语义：事件时间还是处理时间、时区、迟到数据进入哪个时间桶、历史回填是否重算，以及报表刷新频率和数据新鲜度提示。
- 长尾数据：空分母、未知状态、删除/合并租户、缺失维度和低样本量如何计算、排除、告警或展示。
- 数据血缘：从业务源表/事件，经过去重与聚合，到 API、缓存和页面的完整路径；标出每层负责人、刷新方式和可追溯字段。
- 状态契约：定义唯一的状态枚举、状态含义、允许迁移、终态、重试语义和日志字段；不要让 `processing`、`running`、`retrying` 等同义词在不同模块任意混用。

`/prd` 负责定义产品所需的数据行为和验收口径，不替代技术设计。涉及高并发、复杂事务、分库分表、生产迁移或不可逆数据操作时，明确要求技术设计或 spike，并把它列为开发承接前置条件。

数据库取证默认只读。除非用户明确授权，不执行写入、迁移、删除、生产修复或可能影响数据完整性的命令。

## /acceptance 中的数据输出

`/acceptance` 使用数据时，输出建议包含：

- 实际数据是否符合 PRD 预期。
- 迁移是否成功。
- 配置是否兼容旧版本。
- 日志 / 埋点是否按预期触发。
- 错误率、失败次数或异常样本。
- 是否需要人工补证或线上观察。

不要只说“日志正常”，要列出关键日志事件、时间、文件路径或查询结果。

## 常用分析问题

需求真假：

- 这个问题出现了多少次？
- 是多少用户遇到，还是一个用户反复遇到？
- 有没有最近版本集中出现？
- 是否有稳定复现路径？

价值判断：

- 影响核心路径吗？
- 用户是否已经找到替代方案？
- 替代方案成本高吗？
- 不做会造成流失、投诉、信任下降、收入损失还是维护成本增加？

范围判断：

- 能否先做只读、导出、提示、日志、配置的小版本？
- 是否必须改数据库？
- 是否必须改后端？
- 是否能先用前端静态枚举或配置文件验证？

验收判断：

- 做完后用什么数据证明有效？
- 日志事件名是什么？
- 数据库字段如何变化？
- 人工检查哪些样本？
- 多久后观察一次？

## 输出边界

- 不访问不到的数据，不假装分析过。
- 不用复杂指标掩盖证据不足。
- 不把数据库设计当成 PRD 的全部；数据设计要服务用户场景。
- 不在 `/idea` 阶段过早给出完整数据库构筑方案。
- 涉及高风险数据迁移时，必须提示需要技术评审和回滚方案。
