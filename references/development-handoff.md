# 开发承接工作流

正式实施计划承接已确认的完整 PRD，不重新定义需求或直接写业务代码。用户明确要求评审草案时，可先形成技术方案与候选任务；未决选项和依赖保持待评审，不称为正式实施计划。

先读取 `references/work-mode-boundary.md`。`team_pm` 默认停在产品、设计、研发和测试的团队承接清单，只有用户明确要求工程计划或确认由同一 Agent 继续实现时才进入本工作流；`vibe_coding` 按既有规则承接。模式切换必须由用户授权，不能因 PRD 已完整而静默发生。
<!-- contract:work-mode-handoff-authorization -->

开发承接完成后，仅在已有实施授权内进入“实施”子阶段；只委托文稿则停在评审点。阶段识别、批次边界和门禁状态遵循 `references/workflow-control.md`。

## 触发条件

读取本文件的情况：

- 用户确认 PRD 方向并准备进入开发。
- 用户要求“写实施计划”“拆 progress”“拆 Vibe Coding 任务”“进入开发承接”。
- `vibe_coding` 的完整 PRD 已确认且用户没有要求暂停。
- `team_pm` 的完整 PRD 已确认，并且用户明确要求生成工程实施计划。

以下情况不能宣布正式实施条件齐备；评审草案可保留缺口并继续不依赖它的部分：

- PRD 仍是方案收敛版。
- 当前任务依赖的设计、影响范围、数据来源或验收标准缺失。
- 用户仍在确认核心方案或版本主线。
- 需求仍处在 `/idea` 继续验证阶段。

如果已经存在 PRD、dev plan 和 progress，且用户要求继续某个任务、模块或里程碑，应识别为实施阶段，不再生成一套新的开发承接文档。只有范围或契约改变时才回写 PRD/dev plan。

实施答复必须在“执行基线”中明确列出 `事实源：PRD；dev plan；progress` 及实际文件；没有需求契约变化时直接说明“本轮不重写 PRD”。完成任务后更新 progress，把实现过程写入 dev log；不要只在内部执行而不说明记录去向。

## 输入要求

开发承接至少需要：

- 完整 PRD 文件或完整 PRD 内容。
- 目标版本或功能版本。
- 现有项目结构、历史 dev plan / progress 风格。
- 已明确的不做项、延后项、风险和验收标准。
- 按任务标明设计依赖；UI 实施需满足所依赖的设计与验证条件，设计未交付不阻断独立的服务侧评审任务。`vibe_coding` 实际 UI 承接仍遵守五行高保真门禁。
- 正式多阶段项目需有上游 IDEA/PRD ID 或来源文件，并按 `references/traceability.md` 保留承接关系。

缺少会改变任务合同的输入时，标明受阻任务及关闭标准；不猜实现，不让局部依赖阻断其他已明确的评审内容。

## 固定输出

已获正式实施计划委托时，默认输出：

- `dev_plan_vx.x.md`：开发实施计划。
- `progress_vx.x.md`：开发状态看板和最小任务 checklist。

该“默认”只适用于已经进入本工作流的任务，不代表 `team_pm` PRD 完成后自动触发。

仅需技术草案或候选拆分时，按请求交付，不自动创建整套计划、看板和日志。

如该版本需要记录开发过程，再输出：

- `dev_log_vx.x.md`：开发日志。

如果任务会跨线程、跨窗口或跨天继续，建议同时创建或更新 Basic Memory 任务，但记忆只保存任务状态、正式文档路径、当前阻塞和下次继续点，不复制 dev plan、progress 或 dev log 的正文。

命名规则：

- `vx.x` 使用目标版本，例如 `v0.5`、`v1.4.x`。
- 如果项目已有版本目录，优先放在版本目录下，例如 `doc/releases/v0.5/dev_plan_v0.5.md`。
- 如果项目历史使用根文档，也可以沿用历史风格，但必须保持新版本与旧版本平级。

## dev_plan_vx.x.md

`dev_plan_vx.x.md` 面向开发执行，重点是实施顺序和影响范围。

必须包含：

- 目标版本、来源 PRD、本次包含、本次不包含。
- PRD 对照表：每个主要需求点对应到开发模块。
- 文件与模块影响：涉及前端、后端、UI、数据库、配置、日志、打包、测试。
- 实施顺序：先做基础能力，再接 UI，再接日志/配置，再验证和打包。
- 模块任务拆解：每个任务写目标、涉及文件、实施要点、验证方式、完成标准。
- 测试与验收计划：自动化、手动、日志、配置、打包、回归范围。
- 开发日志约定：是否需要 `dev_log_vx.x.md`，记录颗粒度是什么。
- 风险与回退：不要只写“风险较低”，要写具体触发条件和处理方式。
- 开放问题：仍需用户或开发确认的事项。
- 长期记忆建议：如果后续实现会跨线程，给出可直接发送的 `memory-tasks` 提示词。

边界：

- 可以比 PRD 更工程化，但不能重新扩大 PRD 范围。
- `team_pm` 可先提供受委托的技术草案；架构、物理 schema、接口、代码模块、测试实现和发布方案由研发评审后才能作为对应实施任务基线。“待研发确认”不得冒充已确认，候选任务不等于排期或开工。
- 如果实施中发现 PRD 范围不合理，应回到 PRD 修订或标注为开放问题。
- 不要把未确认的延后项偷偷塞进实施计划。

## progress_vx.x.md

`progress_vx.x.md` 面向状态跟踪，重点是“做到哪、卡在哪、下一步是什么”。

必须包含：

- 当前状态：未开始 / 进行中 / 待验收 / 已完成 / 阻塞。
- 来源 PRD、对应 dev plan、对应 dev log。
- 版本目标。
- 总体进度概览：里程碑、模块、状态、完成度。
- 模块任务 checklist：按实际承接角色拆分有输入、依赖、产物和关闭标准的任务；`vibe_coding` 再细化为 Agent 可执行的最小任务。
- 当前阻塞。
- 最近验证。
- 下一步。
- 记录边界。

生成 `progress_vx.x.md` 前，必须先 review PRD 和 dev plan，确认模块划分、范围、任务粒度和完成标准是否一致。Progress 不是复制实施计划，而是把每个模块拆成可连续执行的最小任务。

边界：

- 不写详细开发日志。
- 不写 bug 修复流水账。
- 不写大量技术排查细节。
- 不把新版本写成旧版本附录。

多阶段项目使用 `references/workflow-control.md` 的统一门禁状态。后续批次优先继承已通过项，只有相关实现、依赖、配置、数据或候选产物身份变化时才重开验证。

## dev_log_vx.x.md

`dev_log_vx.x.md` 用于记录开发过程。它是可选但推荐的，尤其适合版本开发、bugfix 较多、技术验证较多或用户希望保留过程记录的项目。

建议颗粒度：

- 日期 / 阶段。
- 本轮目标。
- 改动模块。
- 关键实现。
- 遇到的问题。
- 处理方式。
- 已验证。
- 未验证 / 待补证。
- 关联 bugfix / spike。

边界：

- 开发日志不替代 progress。
- bugfix 很多时，可以另建 `bugfix-log.md`。
- 技术探索较多时，可以另建 `spike-log.md`。

## Basic Memory 任务跟踪

开发承接适合接入 `memory-tasks`，但只在任务需要跨线程、跨窗口、跨天或跨版本继续时建议使用。

建议记录：

- 任务名称、目标版本、当前状态。
- PRD、dev plan、progress、dev log、原型路径。
- 当前实现边界和不允许扩张范围。
- 必须运行的验证命令。
- 当前阻塞和下一步。

不要记录：

- 完整 PRD、完整 dev plan、完整 progress 正文。
- 临时 debug 输出。
- 大段日志。
- 敏感配置或凭据。

示例提示词：

```text
用 memory-tasks 创建一个任务，跟踪这个版本从实现到验收和发布收口的进度。任务中记录项目路径、PRD、dev plan、progress、dev log、原型路径、当前边界、验证命令、当前状态和下一步。不要复制正式文档正文，也不要记录临时 debug 过程。
```

## 与 PRD 的关系

开发承接必须尊重 PRD：

- PRD 定义“为什么做、做什么、做到什么程度”。
- dev plan 定义“怎么做、先后顺序、影响文件、怎么验证”。
- progress 定义“现在做到哪、还有哪些最小任务”。
- dev log 定义“开发过程中发生了什么”。

发现缺口时回写相应 PRD 条目，标明影响任务；只在缺口会改变当前任务合同或实施安全时阻断该任务，不把待评审草案等同于已批准实施。

## 下一阶段提示词

开发承接完成后，应给出下一阶段建议。

如果下一步是实现，输出可直接发送给开发窗口的提示词，至少包含：

- 项目路径。
- PRD 文件路径。
- dev plan 文件路径。
- progress 文件路径。
- dev log 文件路径，如有。
- 本次实现边界。
- 必须运行的验证命令。
- 不允许扩张的范围。

默认只生成精简执行提示词：引用正式文档和任务 ID，不重复粘贴 dev plan 中已有的安全规则、测试清单和输出模板。高风险系统操作或用户明确要求时，才生成完整审计版。

如果实现会跨线程继续，附加：

```text
用 memory-tasks 创建或更新这个版本开发任务，只保存任务状态、正式文档路径、当前阻塞和下次继续点，不复制项目文档正文。
```

如果下一步是继续补 PRD，输出补 PRD 的提示词。
