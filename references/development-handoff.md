# 开发承接工作流

开发承接发生在完整 PRD 被用户确认之后。它不负责重新定义需求，也不负责直接写业务代码，而是把 PRD 转成可执行、可跟踪、可验收的开发计划。

## 触发条件

读取本文件的情况：

- 用户确认 PRD 方向并准备进入开发。
- 用户要求“写实施计划”“拆 progress”“拆 Vibe Coding 任务”“进入开发承接”。
- `/prd` 已经产出完整可开发 PRD，并且用户没有要求暂停。

不要在以下情况进入开发承接：

- PRD 仍是方案收敛版。
- 原型、影响范围、数据来源、验收标准缺失。
- 用户仍在确认核心方案或版本主线。
- 需求仍处在 `/idea` 继续验证阶段。

## 输入要求

开发承接至少需要：

- 完整 PRD 文件或完整 PRD 内容。
- 目标版本或功能版本。
- 现有项目结构、历史 dev plan / progress 风格。
- 已明确的不做项、延后项、风险和验收标准。
- 如涉及 UI，需有高保真原型或明确原型路径。

如果缺少关键输入，先输出“开发承接阻塞项”，不要硬写计划。

## 固定输出

完整 PRD 确认后，默认输出：

- `dev_plan_vx.x.md`：开发实施计划。
- `progress_vx.x.md`：开发状态看板和最小任务 checklist。

如该版本需要记录开发过程，再输出：

- `dev_log_vx.x.md`：开发日志。

命名规则：

- `vx.x` 使用目标版本，例如 `v0.5`、`v1.4.x`。
- 如果项目已有版本目录，优先放在版本目录下，例如 `doc/releases/v0.5/dev_plan_v0.5.md`。
- 如果项目历史使用根文档，也可以沿用历史风格，但必须保持新版本与旧版本平级。

## dev_plan_vx.x.md

`dev_plan_vx.x.md` 面向开发执行，重点是实施顺序和影响范围。

必须包含：

- 目标版本、来源 PRD、本次包含、本次不包含。
- PRD 对照表：每个主要需求点对应到开发模块。
- 文件与模块影响：涉及前端、后端、UI、数据库、配置、日志、打包、测试。
- 实施顺序：先做基础能力，再接 UI，再接日志/配置，再验证和打包。
- 模块任务拆解：每个任务写目标、涉及文件、实施要点、验证方式、完成标准。
- 测试与验收计划：自动化、手动、日志、配置、打包、回归范围。
- 开发日志约定：是否需要 `dev_log_vx.x.md`，记录颗粒度是什么。
- 风险与回退：不要只写“风险较低”，要写具体触发条件和处理方式。
- 开放问题：仍需用户或开发确认的事项。

边界：

- 可以比 PRD 更工程化，但不能重新扩大 PRD 范围。
- 如果实施中发现 PRD 范围不合理，应回到 PRD 修订或标注为开放问题。
- 不要把未确认的延后项偷偷塞进实施计划。

## progress_vx.x.md

`progress_vx.x.md` 面向状态跟踪，重点是“做到哪、卡在哪、下一步是什么”。

必须包含：

- 当前状态：未开始 / 进行中 / 待验收 / 已完成 / 阻塞。
- 来源 PRD、对应 dev plan、对应 dev log。
- 版本目标。
- 总体进度概览：里程碑、模块、状态、完成度。
- 模块任务 checklist：每项必须是 Vibe Coding 可执行的最小任务。
- 当前阻塞。
- 最近验证。
- 下一步。
- 记录边界。

生成 `progress_vx.x.md` 前，必须先 review PRD 和 dev plan，确认模块划分、范围、任务粒度和完成标准是否一致。Progress 不是复制实施计划，而是把每个模块拆成可连续执行的最小任务。

边界：

- 不写详细开发日志。
- 不写 bug 修复流水账。
- 不写大量技术排查细节。
- 不把新版本写成旧版本附录。

## dev_log_vx.x.md

`dev_log_vx.x.md` 用于记录开发过程。它是可选但推荐的，尤其适合版本开发、bugfix 较多、技术验证较多或用户希望保留过程记录的项目。

建议颗粒度：

- 日期 / 阶段。
- 本轮目标。
- 改动模块。
- 关键实现。
- 遇到的问题。
- 处理方式。
- 已验证。
- 未验证 / 待补证。
- 关联 bugfix / spike。

边界：

- 开发日志不替代 progress。
- bugfix 很多时，可以另建 `bugfix-log.md`。
- 技术探索较多时，可以另建 `spike-log.md`。

## 与 PRD 的关系

开发承接必须尊重 PRD：

- PRD 定义“为什么做、做什么、做到什么程度”。
- dev plan 定义“怎么做、先后顺序、影响文件、怎么验证”。
- progress 定义“现在做到哪、还有哪些最小任务”。
- dev log 定义“开发过程中发生了什么”。

如果开发承接发现 PRD 缺少完整链路、影响范围、数据来源、原型或验收标准，要退回 `/prd` 补齐。

## 下一阶段提示词

开发承接完成后，应给出下一阶段建议。

如果下一步是实现，输出可直接发送给开发窗口的提示词，至少包含：

- 项目路径。
- PRD 文件路径。
- dev plan 文件路径。
- progress 文件路径。
- dev log 文件路径，如有。
- 本次实现边界。
- 必须运行的验证命令。
- 不允许扩张的范围。

如果下一步是继续补 PRD，输出补 PRD 的提示词。
