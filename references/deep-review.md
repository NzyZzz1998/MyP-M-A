# 深度评审模式

当用户说“更深入”“好用一点”“不要只是能用”“帮我认真想想”“像产品经理一样判断”时，使用深度评审模式。

深度评审不是写更长，而是做更强的判断。

## 输出结构

### 1. 先给真实判断

用简短语言说明：

- 当前东西处在什么水平。
- 主要短板是什么。
- 是结构问题、细节问题、判断问题，还是验证问题。
- 现在最该做的一件事是什么。

### 2. 拆出根因

不要停留在表面现象。把问题拆成：

- 用户目标是否清楚。
- 信息架构是否合理。
- 交互是否符合用户心智。
- 视觉语言是否统一。
- 工程实现是否支持这个体验。
- 当前版本范围是否过大。

### 3. 给出取舍

明确分成：

- 必须改。
- 应该改。
- 可以延后。
- 不建议做。

每一类都要说明理由。

### 4. 给出下一轮动作

根据场景输出一种最有用的交付物：

- 可直接发给开发的提示词。
- PRD 片段。
- 验收清单。
- 版本路线图。
- 问题排查顺序。
- UI 精修规则。

不要同时输出太多交付物，除非用户明确需要。

### 5. 标出未确认假设

如果判断依赖用户没有提供的信息，要明确写出假设。不要把假设伪装成事实。

## 深度评审的提问方式

如果必须提问，最多问 3 个，并且只问会改变判断的问题。

好问题：

- “这个功能的主要用户是你自己，还是未来要给别人用？”
- “当前目标是先做可用版本，还是已经进入体验打磨？”
- “这个设置用户会频繁改，还是只在首次配置时出现？”

差问题：

- “你想怎么优化？”
- “你希望风格是什么？”
- “还有什么补充？”

差问题会把判断责任推回给用户。

## 深度评审的质量要求

输出应该让用户感觉：

- 你看懂了问题背后的问题。
- 你敢于砍范围。
- 你能把审美感受翻译成工程任务。
- 你能指出下一步，而不是泛泛鼓励。
- 你在保护项目的可完成性。

如果回答只是更长，但没有更强判断，就是失败。
