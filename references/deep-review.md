# 深度评审模式

用户要求“深入、好用、不要泛泛建议”时加载。深度不是写更长，而是从对象领域选择根因维度并给出取舍。

<!-- contract:review-deep-domain-assembly -->

## 领域装配

对象地图建立后，声明本轮选择的 3～6 个维度；只选会改变判断的项，不为完整填表：

| 对象 | 可选根因维度 |
| --- | --- |
| UI / 页面 | 用户任务；信息架构；交互与状态；视觉系统；可访问性/视口；实现约束 |
| Skill / Agent 工作流 | 触发与路由；阶段/输出合同；证据与权限；渐进加载/上下文；评测与校验；生命周期/回退 |
| 后端 / 数据库 | 领域与租户边界；API/状态/幂等；schema/迁移；队列/重试/可观测性；失败恢复；数据质量/审计 |
| 项目 / 产品 | 用户价值与阶段；核心路径；架构/所有权；验证/运营；范围与路线图；维护成本 |

例如评审 Skill 时，不因模板里有 UI、市场或数据库就展开；评审后端也不强制视觉建议。容易被误选的维度可用一句说明为何排除。

## 判断结构

1. **真实判断**：当前水平、首要短板、问题类型和现在最该做的一件事。
2. **根因链**：用本轮维度把“现象 → 机制/约束 → 用户或工程影响 → 证据缺口”串起来，不把审美词当根因。
3. **取舍**：分为必须改、应该改、可延后、不建议做，并给理由；保护项目可完成性。
4. **下一动作**：只选择最有用的一种交付物，如提示词、PRD 片段、验收清单、路线图或排查顺序。
5. **假设**：未提供的信息明确标为假设或待确认，不伪装成事实。

必须提问时最多 3 个，只问会改变判断的问题。若输出只是更长、维度与对象无关或没有明确取舍，则深度评审失败。
