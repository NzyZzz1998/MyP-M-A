# 意图、实现与验证对照

当 `/review` 同时有 PRD/架构/权限等意图材料和代码实现，或 `/acceptance` 需要判断开发结果是否真正符合文档规则时读取本文件。它用于发现“文档说应当如此，但实现或测试并未保证”的差距。

## 三类证据

1. **意图证据**：PRD、验收标准、权限矩阵、架构决策、配置约定、用户明确决策。文档是待核对的主张，不自动等于真实实现。
2. **实现证据**：实际代码路径、服务端校验、查询过滤、状态迁移、配置读写、原生调用和外部副作用。注释与命名不能替代执行点。
3. **验证证据**：现有自动化测试、实际运行、日志、截图、查询结果、构建产物和人工补证。测试计划或拟新增用例不算已有覆盖。

任何正式“不一致”发现都应能引用意图和实现两侧；实现路径尚未查全时标为“待确认”，不能把搜索未命中写成“实现不存在”。

证据结论不能超过其直接证明范围：

- 日志可证明事件、参数或错误被记录，不能单独证明持久化状态未变化。
- 代码审查可证明存在某条实现路径，不能单独证明候选产物实际执行了该路径。
- 成功路径不能证明拒绝、失败、越权或恢复路径。
- “未覆盖、未泄露、未发生副作用”等负向主张需要状态前后对照、拒绝结果或等价实证。
- 计划、建议和未来测试必须显式标为 `建议新增`，不能混入现有验证。

若验收标准本身要求“失败后旧状态保持不变”，失败日志加实现模式只能证明失败被记录且代码意图合理，最高判“部分通过”；必须补同一候选对象的前后内容/哈希、读取结果或明确自动化断言，才能判“通过”。

## 对照步骤

1. 锁定对象、版本、分支、产物和文档适用范围。
2. 提取会影响权限、隐私、租户、资金、数据完整性、外部副作用或运营安全的规则。
3. 沿真实入口到出口找到每条规则的执行点，包含失败与拒绝路径。
4. 查找现有验证，区分正向、拒绝/越权、失败恢复和回归覆盖。
5. 对照并分类，不按文件数量、测试数量或多数结果投票。
6. 只为真实差距给出最小修复、补文档、补测试或补证动作。

## 对照矩阵

| 规则 ID | 文档意图与来源 | 实现证据 | 现有验证 | 状态 | 影响 | 最小动作 |
| --- | --- | --- | --- | --- | --- | --- |
|  |  | 文件/行/执行路径 | 测试/日志/截图/无 | 一致 / 实现偏离 / 批准后的文档过期 / 未验证 / 待确认 / 范围外变化 / 不适用 |  |  |

状态含义：

- **一致**：意图、实现和有效验证相互支持。
- **实现偏离**：代码行为与仍有效的明确意图不符。
- **批准后的文档过期**：实现变化已有可定位批准依据，但正式文档仍描述旧行为；动作是同步文档，不回退正确实现。
- **未验证**：实现看起来符合意图，但没有足够测试或真实运行证据。
- **待确认**：意图冲突、来源不明、执行路径未查全或对象身份不一致。
- **范围外变化**：实现或文档新增了既有意图未要求、也未批准的用户、数据、权限、状态或交付面；单列影响并回到责任人确认，不自动判 Bug 或正式范围。
- **不适用**：当前产品确实没有该能力，并有项目证据支撑。

状态按事实而非严重程度选择：静态搜索未命中只能支持“待确认”；测试未覆盖只能支持“未验证”；只有仍有效意图与已确认执行行为冲突才能判“实现偏离”。

## 条件化交付面

先建立能力清单，再生成需要的图或文档。不要为不存在的子系统制造空章节。

所有项目通常需要核对：

- 产品与工程架构。
- 承重用户流程和状态变化。
- 配置、环境变量、密钥边界。
- 意图到测试的覆盖映射。

仅在能力真实存在时核对：

- 登录、角色、权限、租户隔离。
- 数据库 schema、迁移、备份、恢复和数据保留。
- 异步任务、队列、定时任务、重试与幂等。
- 外部 API、Webhook、邮件、支付和其他副作用。
- AI/Agent 的输入、工具面、人工批准、输出校验、审计和停止开关。
- 桌面原生能力、安装器、更新器、托盘、系统权限和多平台行为。
- 公开网页、SEO、可访问性或响应式。

不适用项在架构或报告中用一行说明即可，不创建空文档。

## 测试映射

从意图推导测试时分开记录：

- **已有覆盖**：仓库或候选产物今天已经具备的测试及证据。
- **建议新增**：尚未实现的单元、集成、真实操作或人工验证。
- **无覆盖缺口**：关键规则目前没有任何可信验证。

每条测试至少关联规则、预期行为、拒绝或失败场景、证据位置和 CI/人工门禁。建议用例不能计入当前覆盖率，也不能用于 Acceptance 判定通过。

## 阶段输出

- `/review`：输出对照矩阵、值得保留的规则、真实偏离、文档漂移、验证缺口和候选去向。
- `/prd`：仅在修复差距会改变产品合同或范围时进入 PRD；纯文档事实漂移可直接修，明确 bug 可进入 Bugfix。
- `/acceptance`：用同一规则 ID 对照实际产物和证据。对象身份、时间或环境不匹配时，旧证据失效或待补证。

## 输出纪律

- 对象不超过 5 条规则时，默认只输出：入口与范围、一个对照矩阵、结论、最小动作；控制在约 600～1200 个中文字。
- 同一发现不要在领域地图、流程图、矩阵、Finding 和分流表中重复展开。矩阵已经表达清楚时，只在结论中引用规则 ID。
- 只有项目级或复杂跨模块对象才增加架构图、领域地图和多张发现表；单接口、单权限或单配置合同不强制画图。
- `/acceptance` 只有一项核心规则时，不自动展开通用人工清单、回归、发布说明和上线观察；确有相关证据或阻塞再补。

## 禁止事项

- 不把文档当实现证明。
- 不把代码注释当权限或安全保证。
- 不因没有搜索到调用就断言逻辑不存在。
- 不把 proposed、mock、synthetic、placeholder 或计划中的测试写成已有验证。
- 不为制造发现而虚构意图、攻击者、用户影响或外部能力。
