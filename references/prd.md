# /prd 工作流

`/prd` 对应产品经理工作流中的“收敛方案 -> 定义需求”。它用于把已经决定推进的需求，或准备进入原型验证的想法，整理成可讨论、可设计、可开发、可验收的需求文档。

`/prd` 不只是写文档。它必须先帮助用户澄清需求、探索方案、收敛方案，再输出 PRD。任何不明确的地方都不要猜测用户意图，应通过提问确认。

`/prd` 融合轻量 brainstorming 和单版本优先级能力：先理解上下文和目标，再提出 2-3 个可选方案及取舍，基于当前目标给出推荐优先级和版本范围，推荐一个方向，得到用户确认或基于明确假设后，再进入 PRD 起草。

- 异步后端开发前验收用一张矩阵同时覆盖越权、重复/并发提交、重试终止、结果过期和结构化日志；日志至少点名租户、任务、请求者、幂等键/请求摘要、状态迁移、尝试次数、错误码、追踪标识和时间。
- 数据/KPI 需求必须锁定统计对象、分子分母、时间窗、时区、版本/租户过滤、空分母、迟到/删除/未知状态、来源/血缘/刷新频率/权限、排行榜最小样本或低样本提示，以及 API/查询、前端状态、验收样例和影响范围。
- AI/Agent 需求必须覆盖提示注入、幻觉、越权、超时、限流、模型不可用降级、审计、成本预算、供应商切换/回滚、离线评测集、人工质检和线上成功/护栏指标，以及前端、后端、数据、权限、日志、测试和运营影响。
- 原型验证合同必须点名验证结论回写到 PRD、规则表或状态契约的具体位置与更新规则，不能只写“验证后继续开发”。
- 方案仍依赖承重假设时，读取 `references/red-team.md`，继承假设 ID、现有证据、最小实验、继续/停止阈值和阻塞阶段；未知不能改写成已确认。
- 原型验证型即使还有开放值，也先用已知目标形成最小暂定实验合同：基线与统计口径、样本、行为事件、成功/停止阈值、证据位置和结论回写规则。只追问会改变实验安全性或结果解释的缺口，不因等待回答而省略可执行骨架。

## 必备要求

每一份 PRD 都必须包含：

- 方案收敛与优先级：在正式成文前，明确当前版本目标、候选需求优先级、本次范围、延后项和不做项。
- 影响范围：明确这次改动影响哪些前端、后端、UI、数据、配置、日志、权限、文件、第三方能力和既有体验。
- 需求表达物：根据需求类型选择高保真原型、接口契约、ER/数据流图、状态机、时序图或影响矩阵。UI/交互需求必须有原型；纯后端、数据库或工程治理需求不强制伪造 UI 原型。
- 详细功能说明：精确到入口、出口、保存、取消、关闭、异常、数据来源、状态变化和验收标准。
- 开发前验收与指标：PRD 中必须制定验收目标、验收标准、日志/埋点/人工检查、通过标准和不通过处理。这部分用于让开发、测试和用户在开工前对齐“未来怎么验收”，不用于重新判断需求真假，也不基于已完成实现做实际验收。

PRD 不能只写“做一个功能”。开发要能据此判断实现方式，测试要能据此判断覆盖范围，用户要能据此确认是否符合意图。

## Brainstorming 融合原则

`/prd` 中的 brainstorming 不是发散聊天，而是为 PRD 做方案收敛。

兼容旧拼写 `/brainstroming`。命中该入口时，首行明确写 `入口判断：/prd（兼容 /brainstroming，当前为前置方案探索）`，不能静默改名后让用户看不出已正确分流。

必须融入这些能力：

- 先探索项目上下文：已有页面、配置、日志、接口、数据库、历史行为、用户反馈和当前版本目标。
- 一次只问一个关键问题；如果用户要求“请用提问确认需求”，优先只问最影响方向的问题，但结尾仍要预告回答后会比较 2-3 个候选方案，并补齐影响范围、原型或对应表达物和开发前验收。
- 提出 2-3 个方案，不要只给单一默认方案。
- 每个方案必须说明取舍：用户价值、开发成本、影响范围、风险、验证方式。
- 在方案收敛时给出推荐优先级和版本范围；优先级必须服务当前目标，而不是机械套模板。
- 给出推荐方案和推荐理由。
- 在方向未确认前，不要把方案写成最终 PRD。
- 如果用户已经给了明确方案，也要判断是否存在更小方案或替代方案。

不需要照搬 superpowers 的完整实现流程，例如写 `docs/superpowers/specs`、提交 git。MyP-M-A 的 `/prd` 只吸收“先探索、再比较、再确认、再成文”的产品能力。PRD 完成后，如果用户要继续进入开发承接，再输出轻量 `dev_plan_vx.x.md` 和 `progress_vx.x.md`。

## 适用场景

- `/idea` 已经判断需求值得继续，现在要正式推进。
- 用户明确说“写 PRD”“写需求文档”“给开发看的文档”。
- 用户使用 `/brainstorming`、`/brainstroming` 或“先头脑风暴”来启动 PRD 前置探索。
- 用户要做某个版本迭代，需要整理本次范围。
- 用户需要在写 PRD 前判断候选需求先后顺序、哪些进本版、哪些延后或不做。

如果影响范围、数据来源、已有 UI、已有接口、配置路径、数据库字段或历史实现不清楚，按 `references/tooling.md` 使用本地文件、GitHub、文档、截图、浏览器或 Computer Use 补上下文。`/prd` 调用工具的目标是让需求可开发、可测试、可验收，而不是替代 `/acceptance` 做开发后通过判断。
- 需求还未经验证，但用户想先做原型、demo 或技术验证。
- 已有 review/brief/日志/截图，需要沉淀为工程可执行文档。

## 两种 PRD 类型

### 1. 正式推进型 PRD

适用于已经有证据、价值判断清楚、准备进入开发的需求。

重点：

- 写清为什么现在做。
- 写清范围和非目标。
- 写清影响范围，不能因为新需求破坏原本体验。
- 写清与需求类型匹配的表达物；UI/交互需求写清原型，其他需求写清接口、数据、状态或影响表达。
- 写清功能、交互、状态、异常流程。
- 写清验收标准和验证方式。

### 2. 原型验证型 PRD

适用于未经充分验证，但用户希望先进入原型阶段的需求。

重点：

- 明确这是验证，不是正式定型。
- 写清要验证的假设。
- 限制原型范围。
- 必须包含低保真原型图或可运行原型，用于验证方向。
- 写清验证成功/失败标准。
- 先给出可执行的暂定测量与决策合同，再把未确认的时间窗、样本量或阈值标为门禁；不要只输出问题清单。
- 避免把临时原型写成完整系统。

## 工作流程

### 1. 探索项目上下文

先尽量从用户提供的信息和当前项目材料中理解背景。不要脱离项目现状直接写理想化 PRD。

需要关注：

- 当前版本目标和产品阶段。
- 相关页面、窗口、组件、入口和出口。
- 既有配置、日志、数据、接口、数据库或本地文件。
- 相关历史体验：哪些原本行为不能被破坏。
- `/idea`、review、brief、日志、截图、用户反馈中已经确认的内容。
- 当前需求是修问题、做精修、加能力，还是做原型验证。

如果上下文不足，先问一个最关键问题，不要一次抛出一大串。

### 2. 识别输入状态

先判断用户给的是：

- 已验证需求：来自 `/idea` 结论、用户反馈、数据、日志、竞品对标或明确版本目标。
- 未验证想法：只有直觉、方案、截图感受或功能想象。
- 问题集合：多个问题混在一起，需要先收敛范围。
- 已有材料：用户提供了 brief、review、日志、截图、会议记录或旧 PRD。

### 3. 提问澄清

输出 PRD 前，先用提问帮助用户确认需求。不要猜测用户意图。

提问规则：

- 只问会影响 PRD 判断的问题。
- 第一轮通常选择 3-7 个最高影响问题，按决策主题分组；不要一次问十几个松散问题，也不要为了显得高效而漏掉阻塞问题。
- 如果信息足够，可以直接说明“我会基于以下假设起草”。
- 如果信息不足以写 PRD，先停在问题清单，不要强行生成完整文档。
- 如果缺少影响范围、原型输出模式、数据来源或验收标准，优先提问确认。
- 用户明确要求少问时，压缩低影响问题，不删除支付、权限、隐私、数据迁移、不可逆操作等安全关键问题。

按下面的决策顺序提问，不机械照抄：

1. **先解冲突与风险**：目标、实时性、成本、技术限制或非目标是否互相冲突；涉及支付、权限、隐私、迁移或不可逆操作时，哪些边界必须先确认。
2. **再锁定问题与范围**：目标用户、核心场景、问题证据、版本目标、成功标准、本次范围、明确不做项和必须保护的既有体验。
3. **再补完整链路**：入口、触发、主流程、状态变化、用户控制、保存/取消/关闭、无变化、失败反馈、重试、恢复和出口。
4. **按需求类型补契约**：UI 问组件与状态；API 问输入输出、错误和权限；数据库问表字段、迁移与回滚；异步任务问状态、幂等、重试、超时、取消、并发、存储和审计。
5. **最后确认表达与验收**：原型或技术表达物、日志/埋点/人工检查、通过标准、不通过处理和开发/发布门禁。

能从项目文件、代码、数据库 schema 或现有原型直接查到的事实优先使用工具核对，不把可查事实全部反问用户。问题应暴露真正的产品决策，不把实现细节伪装成用户必须回答的产品问题。

首轮输出必须按以下顺序组织：

1. **已确认事实**：复述并保留输入与项目中已经确认的用户、场景、范围、需求类型、候选方案、表/字段、枚举、状态、限制和非目标。技术标识保持原样，不用概括替代精确契约；需求类型使用“前端 / 后端 / UI / 数据”显式标注，不用正文中零散提到相关模块代替。
2. **冲突与开放问题**：区分真正互斥的约束、尚未核对的事实和需要用户决策的取舍。冲突未解决前不承诺方案。
3. **第一轮关键问题**：只问 3-7 个会改变目标、范围、安全边界或核心契约的问题，按“冲突/风险 → 用户与范围 → 完整链路 → 数据与技术契约 → 验收”排序。
4. **续接说明**：以“请先回答这些问题，我再继续下一轮或成文”等明确句子结束，并说明回答后会比较 2-3 个候选方案或解释为何只有一个合理方案；后续 PRD 会覆盖影响范围、原型图或对应需求表达物，以及开发前验收。

问题清单不得覆盖或省略“已确认事实”。信息足够时直接基于已知契约起草；部分契约未知时使用“已确认部分 + 待确认部分”，不要把整项退回空白，也不要重复询问已知内容。

用户要求“先提问确认，再输出 PRD”时，当前回复只完成首轮确认并停下等待回答；不得在同一回复中替用户回答开放问题、同时展开完整 PRD。只有项目证据已经关闭全部阻塞问题时，才可说明无需追问并直接成文。

用户没有要求先提问、而是直接要求可开发 PRD 时，如果权限、迁移或其他高风险边界仍未关闭，输出“方案收敛版 + 暂定契约骨架”：保留已确认字段/API，给出可回滚的保守候选方案、状态/时序或数据表达物和开发前验收框架，并把未决值明确标为门禁。不要只列问题，也不要把暂定合同宣称为完整 PRD。

仅处于首轮提问或方案收敛时，默认控制在 600-1200 个中文字，使用紧凑清单，不提前展开完整 PRD、通用模板和重复解释。用户确认并进入完整成文后，详细度由需求复杂度决定，不受该预算限制。

异步任务需要按实际风险从以下主题选择问题：数据范围与截至时间、权限与租户边界、状态与幂等、失败/重试/取消、结果存储与过期、并发限额、持久化迁移/兼容/回滚、日志审计与验收。不得为了覆盖清单一次抛出所有问题；已由输入或代码确认的部分直接进入“已确认事实”。首轮只询问现有 API、表、字段和状态值及其业务语义，不主动给出具体名称或枚举供用户确认；只有用户要求候选方案，或现状核对后进入方案收敛/完整 PRD，才可提出明确标注为“候选”的契约。

支付、退款、资金、权限、隐私、生产迁移或不可逆操作必须先关闭资格、金额/权限边界、人工确认、幂等、审计、失败补偿与回滚等阻塞项。用户要求少问或直接成文时，只压缩低影响问题，不绕过这些门禁。

### 4. 方案探索

在收敛前，先提出 2-3 个方案。方案数量不要为了凑数；如果确实只有一个合理方案，说明为什么。

每个方案包含：

- 方案说明。
- 适用场景。
- 用户价值。
- 开发成本。
- 影响范围。
- 风险。
- 验证方式。

最后给出推荐方案，并说明为什么推荐。

常见方案类型：

- 最小可用方案：最快验证，功能少，影响范围小。
- 标准版本方案：适合进入当前版本，覆盖核心体验。
- 完整方案：体验更完整，但成本和影响范围更大。
- 原型方案：用于验证想法，不承诺正式上线。
- 暂缓方案：证据不足或阶段不合适。

如果用户已经指定方案，仍然要检查是否有更小方案、替代方案或不做方案。

### 5. 优先级与版本范围

`/prd` 的前半段必须完成单版本优先级判断。优先级不是独立路线图，也不是越多越完整，而是为了明确当前 PRD 的开发范围、测试范围和验收重点。

先确认当前目标，再排序。常见目标包括：

- 修复核心可用性。
- 提升用户信任和稳定性。
- 打磨高频体验和产品质感。
- 验证新方向。
- 提升转化、留存或收入。
- 降低维护成本或技术风险。

优先级判断使用轻量综合策略：

```text
优先级 = 当前目标匹配度 + 用户痛点/证据 + 高频/核心路径 + 风险降低
       - 开发成本 - 维护成本 - 对现有体验的破坏风险
```

可以参考但不要机械套用这些模型：

- Impact / Effort：适合快速判断价值与成本。
- RICE：适合有覆盖人数、影响、信心和成本数据的团队。
- ICE：适合早期快速排序，关注影响、信心和易做程度。
- MoSCoW：适合收敛版本范围，区分 Must / Should / Could / Won't。
- Kano：适合体验型产品，区分基础型、期望型和兴奋型需求。
- WSJF：适合复杂项目，判断延迟成本和工作量。

对个人项目和早期工具，默认使用“目标匹配 + 证据 + 成本 + 可完成性”的轻量策略，不要为了显得专业而引入沉重模型。

推荐输出：

```markdown
### 方案收敛与优先级

- 当前版本目标：
- 优先级策略：

| 需求/方案 | 推荐优先级 | 进入版本 | 理由 | 证据 | 成本 | 风险 |
| --- | --- | --- | --- | --- | --- | --- |

- 本次范围：
- 延后项：
- 不做项：
```

优先级分档：

- P0：不做会导致核心路径不可用、信任受损、数据错误、稳定性风险或版本目标失败。
- P1：强相关当前目标，能明显改善高频体验或核心问题，成本可控。
- P2：有价值但不阻塞本版目标，可作为增强项或排期靠后。
- P3：锦上添花、证据不足、范围偏大或当前阶段不适合，进入延后或不做。

版本范围判断：

- 本次范围：与当前目标强相关、证据足、成本可控、影响范围清楚。
- 延后项：有价值但缺证据、依赖前置能力、成本偏高或不是本版目标。
- 不做项：问题不真实、偏离目标、维护成本过高或会破坏现有体验。

如果候选事项很多，优先级表只保留会影响本 PRD 的事项；跨多个版本的大规划再使用 `references/roadmap.md`。

### 6. 方案确认

在方向未确认前，不要直接输出最终 PRD。

可以使用以下方式继续：

- 如果用户明确选择某个方案，再基于该方案写 PRD。
- 如果用户没有回复，但材料足够，可以标注“基于以下假设起草”，并把方案选择写入假设。
- 如果方案选择会显著影响架构、数据库、原型或验收，必须提问确认。

### 7. 方案收敛

在写 PRD 前，先收敛方案：

- 最小方案：能验证或解决核心问题的最小范围。
- 标准方案：本次版本合理完成的范围。
- 延后项：有价值但不适合当前版本。
- 不做项：与目标无关、范围过大或证据不足。

如果用户提出的方案过大，要主动拆小。不要把所有想法都塞进 PRD。

### 8. 定义需求

在方案收敛后，输出 PRD。对不确定内容使用“待确认”，不要编造。

## 影响范围

PRD 必须包含影响范围。影响范围不是简单写“需要回归测试”，而是要明确这次改动关联到哪些既有链路、模块、数据、接口和体验。

按以下维度逐项列出；不涉及也要写“不涉及”，避免遗漏：

- 前端/UI：页面、窗口、组件、弹窗、菜单、表单、按钮、状态、路由、快捷键。
- 前端状态：本地状态、缓存、配置读取、禁用态、加载态、错误态、保存态。
- 后端/API：接口、新增参数、返回字段、错误码、鉴权、幂等、超时。
- 数据库：表、字段、索引、默认值、迁移、兼容旧数据。涉及数据库时必须精确到表名和列名；未知时标为“待确认”。
- 配置与环境：配置文件、默认值、环境变量、用户本地数据、兼容旧配置。
- 日志与指标：日志事件、埋点、debug 信息、监控、告警。
- 权限与安全：用户权限、系统权限、本地文件访问、敏感信息。
- 任务与异步流程：定时任务、队列、后台进程、托盘常驻、启动/关闭流程。
- 文件与存储：本地文件、导入导出、缓存、资源包、图片或宠物资产。
- 第三方依赖：系统 API、原生能力、外部 SDK、浏览器或桌面平台能力。
- 既有体验保护：这次改动不能破坏哪些原本可用的路径、默认行为、用户习惯。
- 测试与验收影响：新增测试、回归重点、人工验证路径。

影响范围必须服务开发、测试和验收。不能只写“影响设置页”，要写清具体影响到设置页的哪些控件、保存链路、配置字段和相关体验。

## 开发前验收与指标

PRD 必须在开发前制定验收与指标。这里不再判断需求真假；需求真假已经由 `/idea` 的证据和压力测试负责。这里也不做实际验收，因为功能还没有开发完成。PRD 里的验收与指标只回答：未来做完以后应该如何判断符合需求、开发和测试要看什么、失败时应该怎么处理。

必须包含五项：

```markdown
## 验收目标
## 验收标准
## 日志 / 埋点 / 人工检查
## 通过标准
## 不通过处理
```

写作要求：

- 验收目标：用自然语言定义未来开发完成后应达到的状态。
- 验收标准：制定可测试条目，尽量使用“给定/当/则”或明确操作步骤。
- 日志 / 埋点 / 人工检查：约定未来用日志、事件、截图、人工测试、数据查询还是用户反馈验证；小项目优先日志和人工检查，不强行设计复杂埋点。
- 通过标准：预先定义多少次通过、哪些关键日志出现、哪些旧体验不被破坏、哪些错误率可接受。
- 不通过处理：预先定义验收失败后是修复、回滚、降级、延后、补日志，还是重新进入 `/review` 或 `/idea`。

注意区分：

- `/prd`：制定验收口径，面向开发前对齐。
- `/acceptance`：基于开发完成后的实际结果执行验收、测试和发布检查。

对个人桌面工具，优先使用：

- debug.log 事件。
- 人工测试清单。
- 截图对比。
- 操作步骤数量。
- 错误率、失败率、误触率。
- 旧配置兼容检查。
- 用户主观反馈。

对 AI 功能，补充：

- 失败样例。
- 人工抽检方式。
- 幻觉、遗漏、误解、过度执行等失败模式。
- 用户反馈闭环。
- 提示注入、越权、超时、限流和模型不可用时的降级。
- 审计日志、成本预算，以及供应商/模型适配器切换和版本回滚。

## 开发承接边界

PRD 只负责定义需求并判断是否达到“完整可开发”。用户确认后再加载 `references/development-handoff.md`，生成 `dev_plan_vx.x.md`、`progress_vx.x.md` 和按需使用的 `dev_log_vx.x.md`。

开发承接不得扩张 PRD 范围；发现功能链路、影响范围、数据契约、表达物或验收标准仍有缺口时，返回 `/prd` 补齐。Progress 只记录状态、阻塞、验证和下一步，开发过程与缺陷分别进入 dev log、bugfix log 或 spike log。

## 需求表达物

UI/交互型 PRD 必须包含原型。其他类型需求必须提供与实现风险相匹配的表达物，不能为了满足形式而伪造 UI 页面。

先写出原型要回答的决策问题，再选择形式：

- 主要风险是规则、计算、状态或数据流：使用决策表、状态机、时序图、可执行样例或轻量逻辑原型。
- 主要风险是信息层级、控件、操作路径或视觉反馈：使用可点击高保真 UI 原型。
- 两类风险同时存在：先验证会改变架构或范围的一类，再让第二类原型建立在已确认契约上；不要默认同时制作两套重型实现。

原型不是静态展示物。无论逻辑还是 UI 原型，都必须单列待验证假设、验证任务、成功/失败信号、模拟数据/假行为边界，以及结论回写 PRD 的位置和规则，缺一项就不能宣称原型验证闭环。需要设计或浏览器能力时按 `references/capability-routing.md` 选择当前环境真实可用的工具。

原型或实验要优先回答承重假设，而不是展示最多页面。一个实验可以同时收集多项信号，但必须逐项给出结论；不能因为用户喜欢界面，就推断问题价值、技术可行性或商业可持续性都已验证。

UI/交互需求可选原型模式：

- 文字线框：用结构化文本或 ASCII 表示页面布局、按钮位置、状态变化。适合快速澄清。
- 网页原型：输出可打开的 HTML/CSS/JS 原型。适合需要实际交互、布局或视觉验证。
- 原型绘制工具说明：输出给 Figma、MasterGo、墨刀等工具使用的页面结构、组件清单、交互说明。

如果用户没有指定表达方式：

- UI/交互需求默认先用低保真线框澄清，完整 PRD 阶段更新或生成高保真原型。
- API/后端需求提供接口契约、错误码、权限和必要时序图。
- 数据库需求提供表字段、关系、迁移、兼容、回滚和必要 ER/数据流图。
- 状态或异步需求提供状态机、时序图或流程图。
- 纯工程治理提供影响矩阵、验证计划和回退方案。
- 如果用户明确要求“原型阶段”，优先输出低保真原型和验证目标。

UI 原型至少要包含：

- 页面/窗口名称。
- 入口。
- 主区域布局。
- 核心控件。
- 主要按钮。
- 空状态、错误态、禁用态或加载态。
- 保存、取消、关闭、返回等出口。
- 关键交互说明。

可运行网页原型还必须用真实浏览器检查目标视口、关键交互、控制台错误和页面脚本错误；涉及接口时同时检查失败请求或模拟边界。只打开 HTML 或只看截图不等于浏览器验证通过。

## 需求详细程度

优质 PRD 必须精确到开发可以判断实现方式，测试可以判断覆盖范围。

每个功能点都要标注需求类型：

- 前端：页面、状态、路由、组件、交互、客户端逻辑。
- 后端：接口、服务逻辑、任务、权限、错误码。
- UI：布局、视觉、控件样式、文案、动效、状态。
- 数据：表、字段、配置项、枚举、缓存、日志或埋点。

每个核心功能点必须写清：

- 入口：用户从哪里进入。
- 前置条件：什么时候可用，什么时候禁用。
- 主流程：正常使用路径。
- 分支流程：不同选择、不同状态下怎么走。
- 异常流程：失败、为空、超时、配置缺失、权限不足。
- 出口：保存、取消、关闭、返回、重置、完成后去哪里。
- 状态变化：UI、配置、数据、日志如何变化。
- 数据来源：前端写死、配置文件、后端接口、数据库查询、系统 API。
- 实现约束：哪些行为必须兼容，哪些不能破坏。

完整 PRD 还要建立最小领域与决策合同：

- 领域词汇：关键角色、对象、动作、状态和不变量；沿用现有名称，冲突处显式标出。
- 决策记录：会改变接口、数据、权限、状态或用户路径的选择、依据、替代方案和回退条件。
- 测试接缝：可独立观察或替换的接口、状态边界、时钟/随机数、外部服务、文件/数据库、平台能力和故障注入点。

测试接缝不展开成技术设计，而是保证主流程、异常、幂等、权限、回滚和日志能被开发及 `/acceptance` 实际验证。每个关键或高风险功能至少对应“验收标准 -> 可观察结果 -> 所需接缝/证据”；现有架构不具备接缝时列为开发承接风险。

涉及异步任务、导出、上传、后台处理或重试时，还要写一份可测试的状态契约：

- 规范状态枚举及每个状态含义。核对现有语义后，可把 `pending -> running -> succeeded / failed` 作为候选基线；只有确有业务需要时再增加 `cancelled`、`expired` 等终态。首轮澄清不得把这组候选值写成用户已确认或要求用户直接接受的合同。
- 允许的状态迁移、触发者、日志事件和用户可见反馈。
- 重试是一次动作/尝试计数，还是一个独立状态；不要在没有定义的情况下用 `processing`、`retrying` 等同义词替代规范状态。
- 先盘点现有代码和数据中的状态值。若 worker、数据库和 API 使用了未定义或相互重叠的 `processing`、`running`、`retrying`，明确标为现状不一致；选择一套规范枚举，给出旧值映射、灰度兼容和迁移/回退方案。不要把偶然存在的旧值直接抄进新合同。
- 幂等键、重复提交处理、失败后可否重试及数据保留期限。

涉及报表、排行榜、成功率或其他 KPI 时，完整 PRD 还必须锁定：统计粒度与最终状态、分子分母、去重键、时间/时区、空分母、迟到与回填、未知状态、删除/合并主体、低样本量、端到端数据血缘、刷新频率/SLA、权限和数据截至时间。任何一项暂时不能确定，都要写成开发前门禁，不能用“后续刷新”“按现有逻辑”等模糊措辞代替。

示例：下拉查询功能不能只写“提供下拉框”。必须说明：

- 下拉项是前端写死还是后端查询。
- 如果前端写死，枚举值是什么、是否需要配置化。
- 如果后端查询，接口是什么、查询哪张表、返回哪些字段。
- 如果数据库查询，表名、字段名、筛选条件、排序规则是什么。
- 空数据、加载失败、禁用态、默认值如何显示。
- 用户选择后保存到哪里，是否影响旧配置。

## 输出策略

如果用户只给了目标，例如“进行 v0.5 版本迭代”，先输出澄清问题，不要直接写完整 PRD。

如果用户给了足够材料，例如 `/idea` 结论、review 内容、日志证据、明确范围，可以先列“基于以下假设”，再起草 PRD。

如果用户明确要求“请使用提问的方式帮助我确认需求”，必须先提问，不能直接写文档。

## 写作要求

- 让开发读完可以开工。
- 让测试读完知道测什么、回归什么、哪些旧体验不能破坏。
- 让用户能看出哪些是已确认，哪些是假设。
- 不要堆砌商业术语。
- 不确定的信息明确标为“待确认”。
- 对小功能保持轻量，不要为了完整而臃肿。
- 对未经验证需求，必须标明“原型验证型”，不要伪装成正式开发需求。
- PRD 不能缺少影响范围。
- UI/交互 PRD 不能缺少原型；其他 PRD 不能缺少与需求类型匹配的表达物。

## 提问深度补充

`/prd` 的问题数量应服务需求理解，而不是追求少问。相比纯聊天式回答，PRD 更需要把不确定性前置暴露。

- 小改动：1-3 个关键问题即可，重点确认范围、入口、验收。
- 单功能正式 PRD：通常需要 4-8 个问题，覆盖用户、入口、链路、数据、失败态、验收、非目标。
- 版本级 PRD：可以分 2-3 轮提问，先确认版本主线和范围，再确认模块细节、原型、验收和发布风险。
- 跨前后端或数据库需求：必须追问数据来源、接口、表字段、迁移、兼容和回滚。

如果用户要求“请用提问方式帮我确认需求”，不要为了快速输出而压缩关键问题。可以先给“第一轮问题”，待用户回答后继续第二轮，直到足以写完整 PRD。

## 完整 PRD 门禁

`/prd` 输出可能处于两个不同成熟度：

- 方案收敛版 PRD：完成类型判断、候选方案、推荐方向和关键问题，适合让用户确认方向，但不能直接进入开发承接。
- 完整可开发 PRD：已经补齐功能链路、影响范围、数据/配置、原型、验收标准、非目标、风险和开发承接条件，可以进入 `dev_plan_vx.x.md`。

完整可开发 PRD 必须包含：

- 完整入口到出口链路，包括保存、取消、关闭、失败、无变化、重试、异常反馈。
- 影响范围，覆盖前端/UI、后端/API、数据库、配置、日志、权限、测试、发布和既有体验保护。
- 数据来源，涉及数据库时精确到表、字段、索引、迁移和兼容策略；未知时标注待确认。
- 需求表达物。UI/交互需求已有高保真原型时必须更新，没有时必须输出高保真原型或明确原型文件路径；非 UI 需求必须提供对应的接口、数据、状态或影响表达物。
- 原型要回答的决策问题、验证假设、模拟数据边界和结论回写方式。
- 领域词汇、关键决策及关键测试接缝。
- 开发前验收目标、验收标准、日志/埋点/人工检查、通过标准、不通过处理。
- 本次不做项、延后项和范围保护。

如果这些内容缺失，不要进入开发承接。应先补 PRD，或明确输出“当前仍是方案收敛版，不能进入 dev plan”。

## 验证层级选择

开发前验证按 `references/workflow-control.md` 的 L0-L4 层级选择，不机械要求每个个人项目在开发前完成真人用户测试。

- 低风险早期原型在用户明确授权后，可以先用 L0 静态审查和 L1 Agent 预检进入 MVP 开发承接；授权、适用范围和遗留的真人验证门禁要写入 PRD。
- 可运行 MVP 通常在候选验收前完成 L2 真实操作。
- 高认知风险、外部 Beta、真实设备/账号、支付、隐私或不可逆数据操作应提高到 L3/L4。
- Agent 模拟只能作为模拟证据，不能产出真实用户完成率、困惑率、用户原话或市场认可。

PRD 要说明选择了哪些层级、为什么、阻塞开发还是阻塞 Beta/正式发布。用户招募困难时，优先调整门禁时点，而不是把 Agent 模拟冒充真人证据或让项目无限停在原型阶段。

如果建议继续 MVP，必须单列 `进入开发授权：已获得 / 未获得`。只有“低风险条件成立”和“用户明确授权”同时满足，才可进入开发承接；允许 Agent 预检不自动等于允许开发。

如果用户当前只在询问“真人测试是否必须前置”“能否用 Agent 预检”“某门禁应卡在哪个阶段”，先输出简短门禁决策、证据边界和下一步，不自动生成完整 PRD。只有用户要求成文或门禁决策会改变既有 PRD 时才进入完整文档。

## 与开发承接文件的关系

完整 PRD 被用户确认后，默认进入开发承接；如果用户仍在确认方向或明确要求暂停，则停在确认点。文件命名、任务颗粒度、开发日志格式和模板使用均以 `references/development-handoff.md` 为准。
