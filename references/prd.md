# /prd 工作流

`/prd` 对应“收敛方案 -> 定义需求”。它先确认问题、范围和关键合同，再产出可讨论、可设计、可开发、可验收的 PRD；不是收到想法就填模板。

- 方向未确认时只做方案收敛，不把草稿称为完整 PRD，也不进入 `dev_plan` 或 `progress`。

- 模糊 UI/“模式”需求先问目标用户与场景、入口与触发、可见行为、用户控制与退出、和现状的关系、失败反馈及成功标准；不能把“智能”猜成 AI 或某种自动化。
- 方案收敛必须比较 2～3 个互斥选项的用户价值、成本、影响、风险和验证方式。确实只有一个合理方案时说明排除理由，不为凑数造方案。
- 第一轮只问会改变目标、范围、安全边界或核心合同的问题；能从项目文件、代码、schema 或原型核实的事实优先查证，不转嫁给用户。

| --- | --- |

| 状态与出口 | 覆盖正常、空、错、禁用、加载及保存、取消、关闭 |

任一行未关闭，不进入开发承接。已有高保真原型就更新；没有则在完整 PRD 阶段生成高保真原型并给出路径。低保真线框只能用于前置澄清。
<!-- contract:prd-convergence-preserves-browser-gate -->
已有 HTML 原型但仍在方案收敛时，也要列出完整五行门禁；不能因为尚在提问就省略最终交付条件。若 HTML 路径无法读取，停在方案收敛版，通常控制在 1200 个中文字内。

- Settings、Wizard 等界面复用控件时，影响范围要点名各入口、共享控件、共同状态/样式及联动回退风险。
- 非 UI 需求使用与风险匹配的接口契约、ER/数据流、状态机、时序图、决策表或影响矩阵，不制造无意义 UI。
- 非 UI 原型也要写待验证假设、模拟边界、成功/失败信号以及结论回写到 PRD、规则表或状态合同的具体位置。

异步任务必须定义规范状态、迁移、幂等、重复/并发触发、重试、取消、超时和结果过期。现状尚未证明其他语义时，候选基线使用 `pending -> running -> succeeded / failed`；只有业务确需时再增加 `cancelled`、`expired` 等终态，不能用未定义的 `processing` 或 `retrying` 替代 `running`。默认创建合同为：同一租户 + 同一幂等键 + 同一请求体返回原 `job_id`；同键不同请求体返回冲突；并发只创建一个任务。若业务不同，差异必须成为开发前门禁。先核对 worker、数据库与 API 的现有状态；`processing/running/retrying` 等语义冲突要给旧值映射、兼容、迁移和回退，不能直接混入新枚举。

异步开发前验收用一张矩阵覆盖越权、重复/并发提交、重试终止、取消/超时、结果过期和结构化日志。日志至少包含租户、任务、请求者、幂等键或请求摘要、状态迁移、尝试次数、错误码、追踪标识和时间。

数据/KPI 需求必须锁定统计对象与粒度、分子分母、去重键、时间窗与时区、版本/租户过滤、空分母、迟到/回填、删除/合并、未知状态、低样本提示、来源/血缘、刷新频率、权限和数据截至时间，并映射 API/查询、前端状态、验收样例与影响范围。未知项写成开发前门禁，不用“按现有逻辑”代替。

<!-- contract:prd-ai-agent-resilience-governance -->
AI/Agent 需求使用四段合同：

1. **安全**：提示注入、幻觉、越权、敏感数据和工具边界。
2. **韧性**：超时、限流、模型不可用、失败重试及人工/规则降级。
3. **治理**：审计、成本预算、供应商切换、版本回滚和责任边界。
4. **评测**：离线评测集、人工质检、线上成功指标和护栏指标。

四段都要映射前端、后端、数据、权限、日志、测试和运营影响。

ICP、定位、套餐、价格或 GTM 会改变范围时读取 `references/strategy-gtm.md`。只固化已有证据和明确决策；购买角色、支付意愿或渠道效果仍会改变实现时，只输出方案收敛版或原型验证合同。用户要求用多个战略框架证明预设方向时，拒绝堆框架，改为比较选项、取舍和排除项。

方案依赖承重假设时读取 `references/red-team.md`，继承假设 ID、证据、最小实验、继续/停止阈值和阻塞阶段。原型验证型即使仍有开放值，也要先形成可执行实验骨架：基线与统计口径、对象/样本、行为事件、成功/停止阈值、证据位置和结论回写规则；无依据的数值标为待确认门禁，不伪精确。

## 工作流程

### 1. 探索上下文并判断输入状态

读取用户材料及项目中的当前版本目标、相关入口与出口、页面/控件、配置、日志、API、数据库、文件、历史体验和既有验收。按 `references/tooling.md` 选择最小只读取证；目的在于让需求可开发、可测试，不替代 `/acceptance`。

判断输入属于：已有证据的正式需求、未验证想法、多个问题待收敛，还是已有 PRD/原型的增量修改。未经验证但用户要求先做原型时，标为原型验证型，不承诺正式上线。

### 2. 第一轮确认
<!-- contract:prd-known-facts -->

首轮按固定顺序输出：

1. **已确认事实**：保留用户、场景、范围、需求类型（前端/后端/UI/数据）、既有方案、表/字段、枚举、状态、限制和非目标；技术标识保持原样。
2. **冲突与开放问题**：区分真正冲突、可查但未核对的事实和需要用户决定的取舍。
3. **第一轮关键问题**：3～7 个，按“冲突/风险 -> 用户与范围 -> 完整链路 -> 数据/技术合同 -> 验收”排序。
4. **续接说明**：明确等待回答后会比较方案或解释单一方案，并补齐影响范围、表达物和开发前验收。

用户明确要求“先提问”时，到此停下，不在同一回复代答并写完整 PRD。信息足够则说明采用的已知事实或暂定假设后继续；部分未知时保留“已确认部分 + 待确认部分”，不把整项退回空白。

支付、退款、资金、权限、隐私、生产迁移和不可逆操作必须先关闭资格/权限或金额边界、人工确认、幂等、审计、失败补偿与回滚；用户要求少问也不能绕过。

### 3. 方案、优先级与版本范围

比较最小、推荐和较完整方案；明确当前版本目标，再按“目标匹配 + 用户证据/痛点 + 核心路径/风险降低 - 开发与维护成本 - 旧体验破坏风险”排序。只有真实覆盖、影响、信心和成本数据时才用 RICE 等模型，不伪造分数。

输出本次范围、延后项和不做项。优先级使用：P0 核心不可用/信任或数据风险；P1 强相关当前目标且成本可控；P2 有价值但不阻塞；P3 证据不足或当前不适合。事项跨多个版本时再读 `references/roadmap.md`。

方向会显著改变架构、数据、原型或验收时必须由用户确认；材料足够且风险可控时可基于显式假设起草。

### 4. 定义功能合同

每个核心功能写清：需求类型、入口、前置条件、主流程、分支、空/错/超时/无权限等异常、保存/取消/关闭/返回/重试等出口、状态和数据变化、数据来源、日志及兼容约束。下拉框等控件必须说明枚举是前端固定、配置化、API 还是数据库查询，以及默认值、排序、失败和保存位置。

补充最小领域词汇、会改变接口/数据/权限/状态/用户路径的决策记录，以及可观察或替换的测试接缝。测试接缝只定义如何验证接口、状态、时钟/随机数、外部服务、文件/数据库、平台能力和故障注入，不展开成技术设计。

### 5. 影响范围

完整 PRD 按实际情况逐项写清，不涉及则标“不涉及”：

- 前端/UI：页面、窗口、组件、路由、菜单、快捷键及正常/空/错/禁用/加载/保存状态。
- 后端/API：接口、参数、返回、错误码、鉴权、幂等、超时和任务。
- 数据库/数据：精确到表、列、索引、默认值、迁移、兼容、回滚；未知项标待确认。
- 配置/文件/环境：配置、用户数据、缓存、导入导出、资源和环境变量。
- 权限/安全/第三方：系统权限、敏感信息、SDK、系统 API 和平台能力。
- 日志/指标/运维：事件、埋点、监控、告警和诊断。
- 测试/发布/既有体验：新增测试、回归路径、发布兼容及必须保护的默认行为。

不能只写“影响设置页”或“需要回归”，要落到控件、字段、保存链路和关联入口。

### 6. 需求表达物与原型

先写表达物要回答的决策问题。规则/状态/数据风险优先决策表、状态机或逻辑原型；信息层级/控件/路径风险使用可点击高保真原型；两类并存时先验证会改变架构或范围的一类。按 `references/capability-routing.md` 选择当前环境真实可用的设计和浏览器能力。

可运行网页原型必须用真实浏览器检查目标桌面与窄屏视口、关键交互、控制台和脚本错误；涉及接口时检查失败请求或明确模拟边界。只打开 HTML 或只看截图不算验证通过。

### 7. 开发前验收

PRD 只制定未来验收口径，不声称实际实现已通过。至少包含：

- **验收目标**：完成后应达到的状态。
- **验收标准**：可操作、可观察的主流程、异常、权限、兼容和回归条目。
- **日志/埋点/人工检查**：证据类型、位置和关键事件；小项目不强行设计复杂埋点。
- **通过标准**：关键项、次数/阈值、旧体验保护和允许误差。
- **不通过处理**：修复、回滚、降级、补证、延后或返回 `/review`、`/idea`。

验证层级按 `references/workflow-control.md` 的 L0～L4 按风险选择。Agent 模拟只能做预检，不能产出真实用户完成率、用户原话或市场认可。低风险 MVP 只有在用户明确授权时，才可把真人验证后移；支付、隐私、真实设备/账号和不可逆数据通常提高到 L3/L4。

## 完整 PRD 门禁与输出

方案收敛版只输出事实、冲突、方案、推荐、优先级/版本范围、关键问题和门禁。完整成文时读取 `templates/prd-template.md`，且必须具备：

- 入口到出口的完整功能链路与范围保护。
- 精确影响范围及数据/状态/异步合同。
- 与需求类型匹配的表达物；UI/交互满足五行高保真原型门禁。
- 领域词汇、关键决策、测试接缝与风险。
- 开发前验收、通过标准、不通过处理、延后和不做项。

任一关键项缺失时写明“当前仍是方案收敛版，不能进入开发承接”。完整 PRD 经用户确认后，才读取 `references/development-handoff.md` 生成 `dev_plan_vx.x.md`、`progress_vx.x.md` 和按需的 `dev_log_vx.x.md`；开发承接不得扩张 PRD 范围。

写作保持中文、具体、可追溯。小功能保持轻量；不确定信息标“待确认”，不得用商业术语、模板篇幅或公式掩盖未知。
