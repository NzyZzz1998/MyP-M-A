# `/prompt` 提示词生成

`/prompt` 是工作流辅助入口，不是第五个产品阶段。它把当前项目事实、阶段状态和用户授权压缩成另一个任务可直接执行的中文提示词。

## 不可压缩执行合同
<!-- contract:prompt-preserve-core -->

无论选择 L1、L2 还是 L3，生成的提示词都必须保留：

- 用户已给出的正式事实源、任务 ID、当前增量和对象身份；例如输入明确给出 PRD、dev plan、progress 与里程碑时，正文必须逐项引用，不能压缩成“相关文档”。
- 明确范围、禁止动作、成功标准、关键证据和停止条件；证据齐全或达到失败条件时停止，不重复已经完成且仍有效的检查。
- 默认不创建子 Agent，也不要求“再检查、反复确认或二次复核”；只有独立工作确需并行时才写入明确预算。
- 路径、产物、版本或环境与继承证据不一致时，说明哪些证据失效，并停止冒充完成。
- 单一文档状态更新必须写清“只改该文档、不改业务代码、不提交、不推送”；长上下文不能自动把任务升级成大范围实施。
- 用户列出很多历史文档、但本轮只更新一个可逆状态时，只读取目标状态文件和能直接证明该状态的最小证据；不要在提示词中逐项复述或要求重读整份历史文档清单。

## 触发

以下情况加载本文件：

- 用户显式输入 `/prompt`。
- 用户说“帮我写提示词”“下一步怎么跟他说”“生成后续任务”“交给新对话”。
- 用户提供某阶段结果，只要求转换成下一轮可执行指令。

显式参数可用但不强制记忆：

| 场景 | 含义 |
| --- | --- |
| `next` | 进入下一阶段 |
| `continue` | 继续当前子阶段或下一批任务 |
| `bugfix` | 根据缺陷与失效证据生成修复任务 |
| `acceptance` | 生成首次验收或定向续测任务 |
| `release` | 生成发布收口任务 |
| `handoff` | 生成新线程交接任务 |

没有参数时，根据当前产物、门禁和用户动词自动判断。先读 `references/workflow-control.md` 识别真实子阶段；阶段去向再参考 `references/next-step-prompts.md`。

## 生成顺序

1. 确认当前项目、版本、阶段和事实源。
2. 判断目标是四个主入口之一，还是开发承接、实施、Bugfix、手动验证、发布收口等内部子阶段。
   - `continue` 已处于实施、Bugfix、验收补证或发布收口子阶段时，提示词必须明确“继续当前子阶段，不重新进入 `/prd`”；只有发现产品契约缺口时才按工作流返回 `/prd`。
3. 仅在用户明确提供目标模型、运行环境或能力边界时校准接收环境；未知时保持 `generic`，不猜测工具、子 Agent 或共享上下文。
4. 按“长度与风险分级”选择 L1、L2 或 L3，不因背景材料很多自动升级。
5. 继承仍有效的决策和证据，只保留本轮变化、失效项和待完成项。
6. 先在内部整理目标、事实源、任务、授权、验证、停止点等字段，再按当前级别选择性渲染；不要输出内部结构或 JSON。
7. 只从本次明确指向的项目对话与正式文件中提取路径、任务 ID、授权和停止边界；已有信息不重复询问。不得从 Memory、其他项目、评测环境或无关历史任务借用项目名、版本、路径和状态来填空。
8. 只有缺失信息会改变执行对象、风险或写权限时才提问；否则使用 `[项目路径]`、`[PRD 路径]` 等占位符或明确“执行前核对”，不得为了让提示词看起来完整而补写事实。
9. 默认先生成 zero-shot 提示词；只有现有评测、失败案例或严格格式要求证明仅靠规则不稳定时，才加入 1-3 个紧贴真实输入的示例。
10. 输出一段可直接发送的提示词，并执行一次“压缩检查”。

## 输出契约

默认输出：

````markdown
入口判断：`/prompt`（辅助入口，不是新的产品阶段）→ `[目标入口或内部子阶段]`

## 可直接发送的提示词

```text
[提示词正文]
```
````

用户只要提示词时，省略长篇解释。存在多个合理去向时，先用不超过三点说明推荐项与取舍，再给提示词。

用户明确说“只生成提示词，不执行”时，在代码块前用一句话确认“本轮仅生成提示词，未执行项目操作”，不要让用户从未发生的文件变化反推执行状态。

## 长度与风险分级

用户给出的字符上限是硬约束，按可直接发送的代码块正文计算；外层入口判断和一句话说明不计入。没有上限时按以下级别：

| 级别 | 适用场景 | 正文目标 | 装配内容 |
| --- | --- | --- | --- |
| L1 精简 | 单一任务或里程碑；已有正式文件；可逆；无外部写入 | 300-600 个中文字 | 目标入口、事实源/任务 ID、本轮任务、授权与停止点、验证与汇报 |
| L2 标准 | Bugfix、首次验收、多个强关联任务、需要恢复步骤 | 500-900 个中文字 | L1 + 对象身份、继承/失效证据、风险或恢复要求 |
| L3 审计 | 生产数据、不可逆迁移、历史重写、许可、签名、安全、仓库公开或正式发布 | 800-1500 个中文字 | L2 + 风险分解、回滚、审计证据和发布面 |

人工验证不是更长的默认档位：只保留准备、操作、预期、证据、通过标准与恢复。交接优先引用交接文件和 Memory，不复制完整聊天。

L1 默认渲染为一句目标加 3-5 个紧凑要点，或一个短段落；不要展开编号步骤、完整状态枚举、单独 Identity、示例、备份方案和通用发布清单。只有缺失其中一项会直接导致误操作时才增加。受 Git 版本控制的可逆文档更新默认依赖现有 diff/历史回退，不额外要求复制备份文件。

已有正式文件时，用“路径 + 任务 ID + 本轮增量”传递上下文，不复述整份 PRD、计划、数据库设计或历史验收。背景材料长、文件多或历史复杂本身不是升级 L3 的理由。提示词不是第二份实施计划。

用户明确说“别太长”“简短”且任务是当前项目内单一里程碑时，默认只输出代码块和 2-4 句正文；当前项目身份可由接收任务直接核对时，不额外添加项目路径占位符、文件名占位符、推荐说明或通用验证命令。必须保留任务 ID 对应的一句目标、事实源、停止/禁止动作，以及“结论、证据、阻塞、下一步”四项汇报要求。

## 接收环境校准

<!-- contract:recipient-profile -->
`recipient_profile` 是内部条件字段，不是新的入口。默认值为 `generic`；只有用户明确给出目标模型、运行环境或能力时才填写：

- 目标模型或运行时；
- 是否支持本地文件、浏览器、Computer Use、GitHub、数据库等工具；
- 是否支持子 Agent，以及用户给出的并发或模型要求；
- 是否与当前线程共享仓库、正式文件和 Memory；
- 接收任务的交付长度：简短回报、标准报告或审计报告。

该字段只能收紧或适配执行方式，不能凭空增加能力。目标环境未知时，提示词要求执行前探测能力或核对事实源，不得假设能调用工具、创建子 Agent或继承当前聊天。用户明确指定 Opus 5 时，优先写清可见回复长度、任务范围和子 Agent 预算，并用一次可审计证据代替泛化的重复自检；该校准不自动套用到其他模型。

提示词自身的 L1/L2/L3 字符预算与接收任务的交付长度是两件事。前者控制指令体积，后者控制执行完成后的回复或正式文档；没有用户要求时，普通执行只要求简短结果回报，正式 PRD、审计和验收文件仍按内容完整性决定长度。

## 条件装配

<!-- contract:prompt-identity -->
生成前先填写以下内部骨架。每一项都必须判断，输出时允许合并成短句，但不得因压缩遗漏适用项：

1. **目标入口或阶段**：可直接发送的代码块内，第一行必须单独写 `mypm /review`、`mypm /idea`、`mypm /prd`、`mypm /acceptance`，或明确“继续实施 / Bugfix / 发布收口”；不得写 `mypm /prompt`，不得先写背景或标题。
2. **对象身份**：写明用户已提供的项目、版本、分支、HEAD、候选产物和哈希。验收、发布和新线程交接必须显式核对；未知时写占位符或“执行前核对”，不得静默补全。
3. **事实源与继承状态**：引用正式路径、任务 ID、仍有效证据和明确失效项；不要复述完整文档。
4. **本轮范围**：只写本轮增量、明确不做项和必须保护的既有体验，防止接收任务自行扩张范围。
5. **授权与禁止动作**：分别写允许事项、停止点，以及未获授权的 commit、push、仓库公开、tag、Release、附件上传或其他外部写入。
6. **验证与失败处理**：写关键验证、证据要求和失败时停止/恢复方式，不复制通用测试清单。
7. **完成标准与汇报**：要求汇报完成项、证据、未关闭阻塞和下一步；这些内容属于不可压缩核心。

长度要求不要只写“简短”或机械追求字符数。内部先确定信息优先级（`preserve-first` / `trim-first`）：

- **必须保留**：本轮目标、事实源、范围、授权、停止条件、成功标准、关键证据、重大限制和下一步。
- **优先删除**：开场说明、背景复述、重复规则、通用鼓励、文档已有清单、与本轮无关的工具和可选说明。

当字符预算与完整性冲突时，先压缩表达和引用正式文件；不得删除授权、停止条件、成功标准或关键证据来满足软长度目标。只有用户明确给出的硬上限必须严格满足。

仅在适用时增加：

- **详细继承说明**：存在多项已通过证据或失效项、且一句话无法准确表达时展开；简单场景合并在事实源中。
- **恢复与回滚**：修改状态、配置、数据、历史或系统环境时写。
- **人工步骤**：只有自动化不能可靠完成且确实需要人工补证时写。
- **工具编排（`tool-orchestration`）**：只有任务确实需要多个工具、插件或子任务时增加；明确限定阶段、可用工具、并发条件、瞬时失败重试上限（`retry-limit`）、停止条件（`stop-condition`）和结构化失败结果。需要语义判断、用户批准、外部写入或最终验收的步骤保留为直接判断，不交给批量调用自动决定。
- **背景说明**：只有不写会导致执行对象或范围误判时保留一句；禁止写产品故事、历史流水账和文档已有 checklist。

Identity、Examples、完整步骤表都不是固定模块。只有角色会改变判断标准时才写 Identity；默认 zero-shot，示例仅用于纠正已测得的格式或行为缺口，且示例不得与正文规则冲突。

<!-- contract:single-verification -->
验证指令以“证据是否足够支持结论”为目标，不以“多检查几次”为目标。同一验证目标默认只安排一次能产生直接证据的检查；仍有效的历史证据继续继承。不要追加“再检查一遍”“反复确认”“让子 Agent 二次复核”等没有新对象、新环境或新证据的动作。代码、配置、依赖、产物或环境发生变化时，按证据影响面重测对应部分，这不属于重复验证。

<!-- contract:subagent-budget -->
子 Agent 默认预算为 `0`。只有工作确实独立、规模足够且可安全并行时才增加：

- 单条独立调查默认最多 `1` 个；
- 多条互不覆盖的工作默认最多并发 `3` 个，用户明确给出更低上限时从其要求；
- 不创建子 Agent 专门重复验证主 Agent 已完成的同一工作；
- 子 Agent 完成或失败后立即关闭；默认等待 5 分钟仍无结果时只做一次状态检查，再关闭、降级或在结果不可缺少时有限重试；
- 多轨并行结束后由主任务逐轨汇报结果、失败和未完成项；不能只给一个合并结论，也不能让子 Agent 自行作最终判断；
- 最终批准、外部写入和验收结论仍由主任务直接判断。

涉及 Git 历史审计时，默认只读；即使使用 L1 精简提示词，也必须显式写“不得重写历史”。“不提交/不推送”不能替代这条边界。

## 压缩检查

输出前按顺序处理；超限时重写，不要机械截断：

1. 删除正式文件中已经存在的背景、表结构、完整 checklist 和历史结果。
2. 用“文件路径 + 任务 ID”替代内容复述，用“继承通过”替代重复验收步骤。
3. 合并对象与事实源、授权与停止点、验证与汇报等可合并句段。
4. 删除不会改变执行、风险、验证或权限的修饰语、解释和重复提醒。
5. 按“必须保留 / 优先删除”复核，先删低价值内容，再次计算正文长度。
6. 仍超限时保留目标、任务、授权/停止点、成功标准和关键验证，继续压缩可选项；不要机械截断。

内部可参考下面的对照，但不要把示例附加到用户提示词：

- 好：`读取现有 dev plan 与 progress，执行 A3：完整历史、敏感信息、隐私和资产审计；完成验证后停在 A3，不重写历史、不公开仓库、不提交或推送；汇报结论、证据、阻塞和下一步。`
- 差：重新介绍产品背景、复述 A3 全部 checklist、重复历史结论，再在末尾补一句“不要提交”。

## 场景规则

### `continue`

- 沿用当前事实源和任务编号。
- 一轮默认只授权一个里程碑或一组强关联任务。
- 提示词明确写“继续当前实施子阶段，不重新进入 `/prd`”；不因继续实施而重新生成 PRD。
- 仅同步 progress/current/release notes 等状态文档时，要求所有指定事实源一致且明确通过；任一缺失、不一致或未通过即停止。正文显式写“不修改业务代码、不提交、不推送、不打 tag、不创建 Release”，不要用笼统的“不发布”代替。

### `bugfix`

- 引用实际缺陷、日志和复现证据。
- 要求先定位根因，再做最小修复和定向回归。
- 未受影响的既有通过证据继续有效。

### `acceptance`

- 首次验收要锁定分支、HEAD、产物路径与哈希。
- 续测只列证据失效项和待补证项。
- 代码、依赖、配置、数据、环境或产物身份变化时，明确哪些旧证据失效。
- 不可压缩的证据质量规则：脚本、CI 或状态文件写 `PASS` 时仍须读取其引用证据；证据缺失、为空或标为 placeholder、synthetic、mock、示例时，不得判为通过，只能待验证或不通过。

### `release`

- 区分源码、便携包、安装器、版本整体与外部发布操作。
- 许可、签名、安全、仓库公开或正式发布使用 L3；保留产物身份、合规、授权、停止与回滚细节，不为追求短而降为 L1/L2。
- 未签名安装器不得作为公开 Release 附件；便携包、源码和安装器分别判断，安装器阻塞不自动否定其他已通过发布面。
- 将本地 commit、push、仓库可见性变更、创建/推送 tag、创建 Release 和上传附件列为独立授权点；用户只授权其中一项时不得顺带执行其他项。
- 即使当前提示词只授权只读收口，也要写清下一轮外部发布的授权顺序：本地 commit → push → 仓库公开 → tag → Release → 附件上传；每一步均可单独停止，禁止用“发布已授权”一次性代替。
- 任一产物身份、许可、签名、敏感信息或发布证据检查失败时立即停止外部写入，并保留已验证发布面。
- 最终汇报至少包含 commit/HEAD、tag、公开附件及 SHA-256、远端分支/可见性状态、Release 状态、已知限制与回滚点；未执行项明确写“未执行”。
- 公开发布前检查不能漏掉文档状态一致性和 Git 历史：README/current/progress/verification/release notes 的版本口径要一致，历史中不得遗留凭据、私有路径、未授权资产或不宜公开的内部材料；最终汇报必须单列“已知限制”，不能用“阻塞”代替。

### `handoff`

- 写明当前阶段、正式事实源、稳定决策、阻塞和下一步。
- 用户材料已经确认是概念阶段时，提示词正文必须原样包含“当前仍处于概念阶段；尚无仓库、PRD、数据库和代码”，不能只写“不要假设已有”或“不要创建”。
- 概念方向交给 `/idea` 时，提示词必须要求先判断价值、证据、目标用户和 `v0.1` 范围，不得用笼统的“梳理下一步”替代。
- `memory_mode=auto` 时优先引用或更新既有项目笔记；正式文件仍是事实源。
- 不复制聊天全文、凭据、完整日志和临时排查过程。

## 质量检查

生成前自检：

- 可直接发送的代码块第一行是否就是目标入口或子阶段，接收任务无需阅读后文即可开始分流？
- 当前分级是否由风险决定，而不是由背景长度或文件数量决定？
- 正文是否处于当前级别或用户指定的字符预算内？
- 是否引用了真实文件，而不是重新讲一遍已有内容？
- 是否核对了适用的项目、版本、分支、HEAD、产物与哈希；未知项是否明确待核对而非静默省略？
