# 下一阶段提示词机制

MyP-M-A 每个阶段完成后，都应帮助用户知道下一步怎么走。不要只结束在“已完成”。如果用户无异议，或用户明确要继续，应输出下一阶段可直接发送给另一个窗口或同一项目线程的中文提示词。

## 基本原则

- 先给下一阶段建议，再给可复用提示词。
- 提示词必须基于当前阶段产物，不要凭空扩大范围。
- 如果下一步有多个方向，先说明推荐方向和理由。
- 如果当前阶段证据不足，下一步提示词应指向补证，而不是直接推进。
- 如果用户只是要提示词，输出一段可直接复制的中文提示词，不要加太多解释。
- 如果当前阶段形成长期决策、项目状态、发布状态或下次继续点，按 `memory_mode` 处理：`auto` 实际更新并报告，`suggest` 给出建议，`off` 不提 Memory。

## 提示词档位

默认输出“精简执行版”，已有 PRD、dev plan、progress、verification 或治理文档时直接引用，不把项目文档再复制成第二份计划。

- 精简执行版（默认）：项目路径、当前阶段、必读文件、本轮目标/任务 ID、关键新增授权、停止边界和最终汇报。通常控制在约 500-1000 个中文字。
- 完整审计版：仅用于生产数据库、不可逆迁移、许可/历史公开、签名/发布、安全或用户明确要求详细审计时；展开风险、恢复和证据要求。
- 人工验证版：只写前置准备、逐步操作、预期、证据、通过标准和恢复步骤。

先读 `references/workflow-control.md` 判断真实子阶段。实施提示词不重新解释产品背景；续测提示词只列证据失效项和待补证项；用户说“别太长”时优先压缩引用和输出结构，不删关键授权。

停止边界至少要说明 commit、push、tag、Release 和高风险外部写操作是否允许；用户没有授权时明确写“不要执行”。最终汇报至少要求：本轮结论、未关闭阻塞和下一步。精简不等于省略这两项。

## 固定结构

建议每个阶段末尾包含：

```markdown
## 下一阶段建议

- 推荐下一步：
- 原因：
- 需要准备的材料：
- 风险 / 注意事项：

## 可直接发送的提示词

[提示词正文]
```

精简执行版正文优先使用：

```text
继续 [项目/版本]，当前阶段：[阶段]。
项目路径：[路径]
先读取：[正式文件]
本轮只完成：[任务 ID / 目标]
新增决策或授权：[仅写本轮新增内容]
完成后运行：[关键验证]
不要：[停止边界]
最后汇报：[结论、证据、未关闭阻塞和下一步]
```

## /review 之后

常见去向：

- 进入 `/idea`：review 发现多个候选问题，需要判断真假和价值。
- 进入 `/prd`：价值和范围基本明确，需要正式定义需求。
- 进入 `/acceptance`：项目已开发完成或处于发布前，需要实际验收。
- 直接文档治理：文档状态、tag、分支、release notes 等事实不一致。

`/review -> /idea` 提示词应包含：

- 项目路径。
- review 文件或 review 摘要。
- 候选问题列表。
- 需要输出需求池。
- 需要证据等级、压力测试评分、分流建议。

如果 review 形成项目地图、架构图或稳定项目背景，`suggest` 模式可附加：

```text
用 memory-notes 为这个项目更新背景笔记：记录产品定位、当前版本、关键目录、架构摘要、文档结构、review 结论和下一步候选问题。不要记录临时过程。
```

`/review -> /acceptance` 提示词应包含：

- 验收对象。
- 构建产物。
- 配置路径。
- 日志路径。
- 剩余手动项。
- 必须实际运行，不要只凭文档判断。

## /idea 之后

常见去向：

- 进入 `/prd`：明确有价值且适合当前阶段。
- 继续补证：数据、用户、日志、竞品或场景不足。
- 直接做轻量任务：文档治理、CI 状态、简单配置修正。
- 暂不做：价值低、成本高、偏离主线。

`/idea -> /prd` 提示词应包含：

- 需求池文件。
- 选中的 IDEA 编号。
- 用户确认的方案或边界。
- 证据等级和压力测试分数。
- 本次不做项。

如果需求池形成版本主线或重要取舍，`suggest` 模式可附加：

```text
用 memory-notes 记录这次 /idea 的长期结论：版本主线、进入 /prd 的需求、暂不做项、继续验证项、关键证据和下一步。不要保存完整需求池内容。
```

## /prd 之后

常见去向：

- 继续补 PRD：当前仍是方案收敛版或缺少原型/影响范围。
- 进入开发承接：完整 PRD 已确认。
- 进入原型验证：需求未验证但需要高保真或交互原型。

`/prd -> 开发承接` 提示词应包含：

- 项目路径。
- PRD 文件路径。
- 高保真原型路径，如有。
- 目标版本。
- 要输出 `dev_plan_vx.x.md`、`progress_vx.x.md`、必要时 `dev_log_vx.x.md`。
- 不允许扩张的范围。

如果完整 PRD 已确认，`suggest` 模式可附加：

```text
用 memory-notes 记录这版 PRD 的最终决策：目标版本、采用方案、非目标、关键影响范围、原型路径、验收口径和开发承接文件路径。只记录长期有用结论，不复制整份 PRD。
```

## 开发承接之后

常见去向：

- 进入实现。
- 回到 PRD 补缺口。
- 先补原型或技术 spike。

`开发承接 -> 实现` 提示词应包含：

- 项目路径。
- PRD、dev plan、progress、dev log 路径。
- 本轮实现边界。
- 必须运行的验证命令。
- 需要更新的文档。
- 不允许改动的范围。

已有 dev plan/progress 时，优先引用任务 ID 和验证入口，不逐项复述全部 checklist。一个版本任务很多时，一轮默认只授权一个里程碑或一组强关联任务。

如果实现会跨线程、跨窗口或跨天继续，`suggest` 模式可附加：

```text
用 memory-tasks 创建一个任务，跟踪这个版本从实现到验收和发布收口的进度。任务中包含 PRD、dev plan、progress、dev log 路径，当前边界和完成标准。
```

## /acceptance 之后

常见去向：

- 输出手动验证文档：仍有人工补证项。
- 进入 bugfix：存在阻塞问题。
- 进入发布收口：已通过且无需人工补证。
- 回到 `/idea`：验收遗留项适合作为下一版本候选需求。

`/acceptance -> 手动验证` 提示词应包含：

- 验收对象。
- 未覆盖项。
- 需要人工操作的步骤。
- 证据要求。
- 日志 / 配置路径。
- 通过标准。

续测时只列“证据失效”和“待补证”项；仍有效的已通过项直接继承，不重复展开。

`/acceptance -> 发布收口` 提示词应包含：

- 最终发布源。
- 发布产物。
- 验收通过证据。
- release notes / changelog / tag / 回滚方式。
- 是否允许本地提交、远端推送和打 tag，等待用户确认。

如果 acceptance 得到发布状态或遗留项，`suggest` 模式可附加：

```text
用 memory-capture 记录这次验收和发布收口结论：只保存发布状态、关键证据、已知限制、回滚点、人工补证项和下次继续点，不记录临时操作过程。
```

## 长期记忆建议

长期记忆只在有复用价值时处理，不为完整而每次添加。`auto` 模式显示实际结果，例如：

```text
Memory：已更新 LetsMakeMoney project state；记录了 v0.7 验收状态、剩余门禁和下一步。
```

没有实际调用时不能使用“已更新”。`suggest` 模式继续使用可直接发送的提示词；`off` 模式完全省略本节。

`auto` 模式因工具不可用而降级为后续提示词时，至少保留最终方案或状态、非目标、正式文件路径、验收口径、已知限制和下一步，并排除凭据、连接串、完整日志与临时过程。

适合添加：

- 项目会跨线程继续。
- 阶段结束后形成重要决策。
- 用户偏好、项目约定或命名规范发生变化。
- 验收或发布状态会影响未来版本。
- 当前对话有明确下次继续点。

不适合添加：

- 只是一次轻量建议。
- 只是临时截图反馈。
- 没有形成稳定结论。
- 内容包含敏感信息或长日志。

## 写作要求

- 提示词使用中文。
- 直接可执行，少写抽象原则。
- 包含路径、文件名、版本、分支、日志、配置等关键信息。
- 明确“不做什么”和“不要猜测什么”。
- 如果需要工具，写清需要实际使用哪些工具或证据来源。
