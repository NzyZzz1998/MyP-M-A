# 下一阶段提示词机制

MyP-M-A 每个阶段完成后，都应帮助用户知道下一步怎么走。不要只结束在“已完成”。如果用户无异议，或用户明确要继续，应输出下一阶段可直接发送给另一个窗口或同一项目线程的中文提示词。

## 基本原则

- 先给下一阶段建议，再给可复用提示词。
- 提示词必须基于当前阶段产物，不要凭空扩大范围。
- 如果下一步有多个方向，先说明推荐方向和理由。
- 如果当前阶段证据不足，下一步提示词应指向补证，而不是直接推进。
- 如果用户只是要提示词，输出一段可直接复制的中文提示词，不要加太多解释。

## 固定结构

建议每个阶段末尾包含：

```markdown
## 下一阶段建议

- 推荐下一步：
- 原因：
- 需要准备的材料：
- 风险 / 注意事项：

## 可直接发送的提示词

[提示词正文]
```

## /review 之后

常见去向：

- 进入 `/idea`：review 发现多个候选问题，需要判断真假和价值。
- 进入 `/prd`：价值和范围基本明确，需要正式定义需求。
- 进入 `/acceptance`：项目已开发完成或处于发布前，需要实际验收。
- 直接文档治理：文档状态、tag、分支、release notes 等事实不一致。

`/review -> /idea` 提示词应包含：

- 项目路径。
- review 文件或 review 摘要。
- 候选问题列表。
- 需要输出需求池。
- 需要证据等级、压力测试评分、分流建议。

`/review -> /acceptance` 提示词应包含：

- 验收对象。
- 构建产物。
- 配置路径。
- 日志路径。
- 剩余手动项。
- 必须实际运行，不要只凭文档判断。

## /idea 之后

常见去向：

- 进入 `/prd`：明确有价值且适合当前阶段。
- 继续补证：数据、用户、日志、竞品或场景不足。
- 直接做轻量任务：文档治理、CI 状态、简单配置修正。
- 暂不做：价值低、成本高、偏离主线。

`/idea -> /prd` 提示词应包含：

- 需求池文件。
- 选中的 IDEA 编号。
- 用户确认的方案或边界。
- 证据等级和压力测试分数。
- 本次不做项。

## /prd 之后

常见去向：

- 继续补 PRD：当前仍是方案收敛版或缺少原型/影响范围。
- 进入开发承接：完整 PRD 已确认。
- 进入原型验证：需求未验证但需要高保真或交互原型。

`/prd -> 开发承接` 提示词应包含：

- 项目路径。
- PRD 文件路径。
- 高保真原型路径，如有。
- 目标版本。
- 要输出 `dev_plan_vx.x.md`、`progress_vx.x.md`、必要时 `dev_log_vx.x.md`。
- 不允许扩张的范围。

## 开发承接之后

常见去向：

- 进入实现。
- 回到 PRD 补缺口。
- 先补原型或技术 spike。

`开发承接 -> 实现` 提示词应包含：

- 项目路径。
- PRD、dev plan、progress、dev log 路径。
- 本轮实现边界。
- 必须运行的验证命令。
- 需要更新的文档。
- 不允许改动的范围。

## /acceptance 之后

常见去向：

- 输出手动验证文档：仍有人工补证项。
- 进入 bugfix：存在阻塞问题。
- 进入发布收口：已通过且无需人工补证。
- 回到 `/idea`：验收遗留项适合作为下一版本候选需求。

`/acceptance -> 手动验证` 提示词应包含：

- 验收对象。
- 未覆盖项。
- 需要人工操作的步骤。
- 证据要求。
- 日志 / 配置路径。
- 通过标准。

`/acceptance -> 发布收口` 提示词应包含：

- 最终发布源。
- 发布产物。
- 验收通过证据。
- release notes / changelog / tag / 回滚方式。
- 是否允许本地提交、远端推送和打 tag，等待用户确认。

## 写作要求

- 提示词使用中文。
- 直接可执行，少写抽象原则。
- 包含路径、文件名、版本、分支、日志、配置等关键信息。
- 明确“不做什么”和“不要猜测什么”。
- 如果需要工具，写清需要实际使用哪些工具或证据来源。
