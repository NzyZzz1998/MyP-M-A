# 历史案例库

本文件保存 MyP-M-A 的真实工作流案例摘要，用于校准阶段边界、证据深度和交付形态。案例是历史快照，不代表项目当前状态。

## 使用规则

- 只有用户要求案例、需要解释工作流，或当前交付深度明显失准时读取。
- 只复用方法、门禁和文档结构；版本、路径、分支、测试数、发布状态和结论必须在当前项目重新核对。
- 案例不能补全当前输入的未知事实，也不能替代用户研究、仓库证据或真实验收。
- 正式输出不展示案例项目名，除非用户明确要求对照。

## QuickRec：从候选问题到补丁发布

**历史目标**：为桌面录屏工具增加轻量诊断导出能力，避免扩成复杂诊断中心。

**阶段链路**：

1. `/review` 先分清 Full 与 Lite 工作区、版本文档和发布对象，发现工作区身份混杂会污染后续判断。
2. `/idea` 将诊断能力判为有历史故障和日志证据支撑的中价值需求，同时压缩为复制信息、打开日志目录、导出本地文件。
3. `/prd` 明确入口、配置、日志、导出、失败反馈、隐私边界、影响范围和低保真原型；方案确认后才生成开发承接文档。
4. 实现后 `/acceptance` 锁定分支、EXE、哈希和日志目录；自动化通过仍不能替代托盘、设置页、录制模式和异常注入。
5. 首轮验收因产物路径不一致和 GUI 缺证据判为部分通过；补齐真实桌面证据后才进入发布收口。

**可复用经验**：候选产物身份是验收前提；诊断功能的价值在于缩短排障链路；最小版本必须同时覆盖成功、失败和用户可带走的证据。

## LetsMakeMoney：从界面打磨到桌面发布门禁

**历史目标**：持续打磨设置页与桌宠边缘体验，并在公开发布前补齐许可、依赖和真实 Windows 行为。

**阶段链路**：

1. 多轮截图反馈先进入 `/idea` 和 UI review，逐步确认问题不只来自配色，还来自窗口层级、控件密度、套框、下拉框和说明文字占位。
2. `/prd` 将共享控件、Settings/Wizard、托盘、点击穿透和文档治理写成完整链路，并同步高保真 HTML 原型。
3. 开发承接将 `dev_plan`、`progress` 与 `dev_log` 分离，避免进度看板变成 bug 流水账。
4. `/acceptance` 使用真实 EXE、Computer Use、配置和 `debug.log` 验证；发现保存失败误报、剪贴板假阴性和纯桌宠任务栏缓存等问题后，结论保持部分通过。
5. Bugfix 只处理已证实缺口并重打候选包；无法稳定自动点击通知区时生成手动补证，不冒充自动通过。
6. 公开准备阶段另行审计代码许可、受限素材、第三方依赖、安装器签名和仓库隐私，不把功能验收等同于公开授权。

**可复用经验**：视觉精修需要真实截图与状态覆盖；桌面系统行为必须结合 GUI、日志和原生状态；验收通过、提交授权、远端推送和公开发布是四个独立判断。

## 选择案例

| 当前问题 | 可参考内容 | 不得继承 |
| --- | --- | --- |
| 工作区或版本身份混乱 | QuickRec 的对象锁定与产物哈希 | 旧分支、旧路径、旧发布状态 |
| 单功能 PRD 容易扩张 | QuickRec 的最小诊断范围 | 具体 UI、字段和版本号 |
| UI 一直“怪”但说不清 | LetsMakeMoney 的截图归因与控件状态 | 暖色风格和窗口尺寸 |
| Desktop 自动化覆盖不足 | 两个案例的 GUI、日志、手动补证组合 | 历史通过项和测试数量 |
| 准备公开仓库 | LetsMakeMoney 的许可与发布分权 | 许可结论、素材所有权和签名状态 |
