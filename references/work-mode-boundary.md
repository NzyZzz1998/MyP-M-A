# 交付模式与产品经理边界

本文件只决定交付深度和职责边界，不改变 `/review`、`/idea`、`/prd`、`/acceptance`、`/prompt` 的入口语义，也不改变已确认的用户、范围、数字、状态和验收事实。模式只改变职责和技术深度，不改变产品合同。

内部字段为 `delivery_mode`：

- `auto`：默认值；按当前任务解析为 `team_pm` 或 `vibe_coding`。
- `team_pm`：团队协作型产品交付，产品经理定义产品合同，由设计、研发、测试和运维承接实现合同。
- `vibe_coding`：同一用户或 Agent 从产品定义继续负责实现、测试和发布承接。

每次正式输出在入口判断后写 `交付模式：团队协作型` 或 `交付模式：Vibe Coding 全流程型`。显式指定优先；模式不明时默认 `team_pm`，不得因为仓库中存在代码、数据库或 CI 就自动升级为 `vibe_coding`。

## 自动解析

| 线索 | 解析结果 |
| --- | --- |
| 公司、岗位、跨部门、产品/设计/研发/测试分工；用户只要求产品文档或评审 | `team_pm` |
| 用户明确写“团队协作型”“只写产品需求”“技术方案由研发负责” | `team_pm` |
| 个人项目、独立开发，且明确要求同一 Agent 后续实现、生成 dev plan/progress 或完成发布闭环 | `vibe_coding` |
| 用户明确写“Vibe Coding 全流程型”“写到可直接编码” | `vibe_coding` |
| 线索冲突或无法判断 | `team_pm`，同时说明可由用户切换 |

不要仅凭“个人项目”推断全流程；必须同时存在继续实现或工程承接意图。不要仅凭用户提供 API、schema 或代码细节改变模式，这些材料也可能只是团队 PRD 的输入证据。

## 职责矩阵

| 内容 | `team_pm` 的产品经理职责 | `vibe_coding` 的增量 |
| --- | --- | --- |
| 问题、用户、目标、非目标、优先级、版本范围 | 负责定义 | 相同 |
| 用户流程、业务规则、状态语义、权限语义、异常体验 | 负责定义 | 相同 |
| 指标口径、数据含义、验收标准、依赖与风险 | 负责定义 | 相同 |
| API | 定义业务动作、输入输出语义、权限和错误体验；端点、协议和实现待技术设计 | 可补逻辑接口、字段约束和失败契约 |
| 数据库 | 定义业务对象、数据来源、可见性、保留和兼容要求；不猜表、列、索引、SQL | 可基于证据补逻辑 schema、迁移与回滚接缝 |
| 架构与代码 | 默认提出产品约束和研发决策问题；明确受托时可起草技术方案，不冒充既定实现 | 可进入模块、文件、任务和测试接缝 |
| 设计 | 定义信息层级、流程、状态和体验标准；设计稿由设计角色交付，除非用户要求代做 | UI 需求更新或生成可验证高保真原型 |
| 测试与发布 | 定义验收场景、业务通过标准、灰度/回退条件；不写测试实现和发布脚本 | 可生成验证命令、故障注入、打包和发布承接 |

产品语义合同不能因 `team_pm` 而变薄：主流程、分支、失败、权限、保存/取消/关闭、状态含义、指标口径、旧体验保护和验收出口仍须完整。应删除的是无证据的物理实现，不是业务细节。

用户明确要求技术草案或候选任务时，保持 `team_pm`，保留已定技术约束，区分现有实现、候选建议与研发待确认项；可用附件承接，不把工程细节塞进产品正文。两套方案成文不等于同时实施，未选定方案的任务应分别列出。文稿授权不等于编码、排期或远端建任务授权；不得编造负责人和工期。

## 各入口差量

- `/review`：`team_pm` 以产品、业务流程、模块职责和协作风险为主；代码或架构发现只形成工程风险与核验问题。只有用户明确要求实现评审或代码瘦身时才进入代码级建议。
- `/idea`：两种模式使用相同价值判断；技术内容只用于成本、依赖和风险，不把实现方案当作价值证据。
- `/prd`：`team_pm` 使用 `templates/prd-team-template.md`；`vibe_coding` 使用 `templates/prd-template.md`。两者共享同一产品事实和验收语义。
- `/acceptance`：`team_pm` 汇总真实产品证据和发布建议，可要求设计/研发/测试补证；未获授权时不代写或执行构建、迁移、CI、部署脚本。用户明确要求实际操作时仍可使用合适工具验收。
- `/prompt`：交接提示词必须保留已解析模式；不得在下一任务中静默从 `team_pm` 升级到全流程实现。

## 原型与开发承接

`team_pm` 的 UI PRD 至少需要可核对的信息架构、流程、状态与设计交付要求。已有原型时更新产品交互说明；没有原型时，若团队有设计角色，输出设计任务单和验收标准，不强制产品经理生成高保真 HTML。只有用户要求代做原型或不存在下游设计角色时才生成高保真原型。

`vibe_coding` 继续执行高保真原型门禁和工程表达物要求。该模式差异适用于首轮、方案收敛、已有 HTML、续写与验收交接；已有代码或原型不改变责任人和授权。用户明确要求代做的部分单列范围，不自动承接其余工程任务。

完整 PRD 完成后：

- `team_pm` 默认停在 PRD 确认点，输出设计、研发、测试各自的承接清单；只有用户明确要求开发承接时才生成 `dev_plan`、`progress`、`dev_log`。
- `vibe_coding` 在用户确认 PRD 后可按既有规则进入开发承接。

## 终检

发送前检查：

1. 模式有依据且已显示，模糊场景是否默认 `team_pm`。
2. 产品事实、数字、范围、状态和验收在双模式间是否一致。
3. `team_pm` 是否把候选物理方案写成已确认事实，或输出用户未委托的工程内容。
4. 是否仍完整覆盖用户流程、业务规则、异常、权限、指标和验收。
5. 是否只在明确授权时进入开发承接或实际工程操作。
