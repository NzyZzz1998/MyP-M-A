# 长期记忆集成

本文定义 MyP-M-A 如何接入 Basic Memory 与 `memory-*` skills。长期记忆不是自动保存全部聊天，而是按事件触发、可检索和跨会话续接的辅助知识库。

先按下方运行模式解析 `memory_mode`，再判断是否恢复或写入；用户选择和宿主约束优先。只有 `auto` 执行自动恢复/写入合同；`off` 不读写也不给 Memory 建议，`suggest` 只给建议。后文阶段示例和降级提示均受此条件限制，不覆盖显式模式。

Memory 提供者、项目及位置以当前宿主暴露的能力、实际配置和用户选择为准，不内置某台电脑的路径。跨电脑先核对当前仓库；旧绝对路径只作待映射线索，不创建示例目录或猜测记忆库。某个提供者的授权不自动扩展到其他记忆系统，写入始终遵守宿主要求。

## 新线程自动恢复合同
<!-- contract:memory-auto-restore-attempt -->

仅在 `memory_mode=auto` 且已知项目需要新线程恢复时完成下面六项；其他模式直接按正式项目材料继续，不把恢复动作误报为 `/review`：

1. 标明场景是“已知项目的新线程恢复”，并写明 `memory_mode=auto`。
2. 实际调用可用的 Memory 搜索/读取能力；工具未提供时写“已检查可用能力，Memory 工具不可用，未执行搜索/读取”，不能虚构调用、握手或恢复结果。
3. 继续读取仓库中的 `current`、`status`、`progress`、`verification` 或等价正式文件核对。
4. 明确 Memory 只作导航；与仓库冲突时，以本轮实际读取的仓库事实为准。
5. 明确同一线程核对后沿用结果，不在后续每轮重复恢复。
6. 证据不足时不宣布通过、发布或无阻塞，也不虚构具体下一任务。

## 基本原则

- 只保存长期有用的信息：决策、偏好、项目背景、版本状态、重要路径、约定、踩坑、未完成事项和下次继续点。
- 不保存临时过程：原始聊天流水、重复命令输出、一次性探索、已废弃草稿、无证据猜测。
- 不保存敏感信息：API key、token、密码、私密账号、不可公开的密钥内容。
- 不把 Basic Memory 当作 PRD、需求池或验收文档的替代品；正式交付物仍应写在项目仓库。
- 记忆内容默认中文；必要的 observation 标签可以使用 `[decision]`、`[preference]`、`[risk]`、`[next]` 等英文标签。
- MCP 不可用时，可使用已授权、同项目同提供者的本地 CLI；两者均不可用则按正式项目材料继续，不假装已恢复或写入，也不把重启设为必经步骤；仅在 `suggest` 或用户另行要求时给后续提示词。

## 稳定阶段写入合同
<!-- contract:memory-stable-write -->

`auto` 模式在宿主允许的稳定阶段收尾时，Memory 写入遵守以下顺序；`off`/`suggest` 不执行写入：

1. 给事实标注来源：用户明确决定记为 `[user-decision]`；仓库当前状态记为 `[repo-fact]` 并引用 `current.md`、`verification.md` 或等价正式文件；真实验收结果记为 `[verified-result]` 并带适用版本。
2. 无证据怀疑、临时排查和未关闭假设不写入稳定事实。
3. 已有精确项目映射时读取原笔记；否则先搜索同一项目已有笔记，不重复创建；写后回读或再次搜索确认。
4. 工具不可用或确认未写入时报告 `Memory：未写入`；写调用后回读失败则报告“写入状态待核对”，不得使用“已更新”“已保存”等完成措辞或盲目重试。
5. 旧 Memory 与仓库冲突时，实际读取 `verification.md`、HEAD 和候选产物身份；将旧状态标为过期/被替代并记录新来源，不静默沿用。
6. 状态被替代时，仓库事实源中仍未关闭的权限、迁移、GUI、候选包身份等证据类别要原样保留为下一步；不能只更新版本结论而遗漏未决验证面。

## 运行模式

每次进入明确项目时确定本轮 `memory_mode`。用户明确指定时优先；未指定且没有当前项目的有效授权时默认 `off`。安装 Basic Memory、切换新线程或说“继续项目”不等于授权启用。首次开启前说明恢复内容会进入模型上下文、整理可能增加 Token；取得同意后只在约定项目和期限内自动执行，不每次重复询问。

| 模式 | 行为 |
| --- | --- |
| `auto` | 在“新线程恢复”和“稳定阶段收尾”两个事件自动读写；不在普通中间轮次反复写入 |
| `suggest` | 不直接读写，只在阶段末给出适合的 `memory-*` 建议 |
| `off` | 本轮不读取、不写入，也不追加 Memory 建议 |

用户说“不要用 Memory”“本轮不保存”时视为 `off`；说“只提醒我”时视为 `suggest`；说“自动维护项目记忆”时视为 `auto`。模式只影响本轮或用户明确指定的范围，不擅自写入全局配置。

显式 `memory_mode=auto` 是本轮的启用授权，不自动扩展为其他项目或永久授权。持久启用与关闭须在本地项目配置中保留范围；历史默认 auto 不能作为新授权。普通任务不反复推销开启。Memory 和诊断日志独立授权，具体适配、限量恢复、去重及失败处理见 [本地接入](local-memory-diagnostics.md)。

## 自动恢复

`auto` 模式下，同时满足以下条件时自动尝试恢复：

- 用户给出明确项目名或项目路径；
- 当前是新线程、用户说“继续/回到/接着”，或现有上下文不足以可靠判断当前状态；
- Basic Memory 工具可用。

执行顺序：

1. 已有本地精确映射先读取绑定笔记；否则搜索项目全名、简称和稳定路径，避免单名称漏检，不自动跨项目扩大检索。
2. 找到候选后读取最相关的项目状态、版本任务或发布记录；没有命中时不创建空笔记。
3. 将 Memory 只作为导航，继续读取项目仓库中的 `current`、`status`、`progress`、PRD 或验收文档。
4. 如果 Memory 与项目事实源冲突，以项目仓库为准；本轮形成稳定事实后再更新旧记忆。
5. 只在 Memory 和正式文件都实际返回后简短说明：`Memory：已恢复 [笔记名]，并以 [正式文件] 完成核对。` 如果只完成其中一步，必须分别写明“已恢复、待仓库核对”或“Memory 不可用、已按仓库事实源核对”。

同一线程已恢复且项目没有切换时，不要每轮重复调用 `memory-continue`。

### 冲突清单契约

Memory 与仓库或仓库内部来源不一致时，不要只写“存在冲突”。逐项列出：

- 冲突来源：Memory 笔记、README、current/status、progress、verification、Git 分支/HEAD、候选产物身份或其他正式文件。
- 各来源的具体主张：版本、阶段、通过状态、产物路径/哈希、阻塞和下一步。
- 本轮实际核对证据及其时间/提交身份。
- 处理结果：采用、判定过期、仍待确认，或需要用户决策。

不得用一条笼统结论覆盖多个冲突。优先级取决于本轮可核对的事实和产物身份，而不是文件名；真实 Git/产物证据与经验证的最新正式状态优先于旧 Memory。冲突未解决前不更新旧笔记为新完成态，也不判断通过、发布或无阻塞；解决后记录“旧状态 → 新状态”及正式来源。

确认 Memory 已过期后，`auto` 模式且宿主允许、写工具可用时更新同一笔记并回读；不可用则报告“Memory：待纠正”；`suggest` 只建议，`off` 不产生记忆操作或建议。不得静默沿用旧状态。

### 恢复证据闸门

恢复过程使用四种状态，措辞必须与真实工具结果一致：

| 状态 | 允许的表述 | 禁止的表述 |
| --- | --- | --- |
| `unavailable`：工具未提供或不可用 | 已检查能力但未执行恢复，或实际调用失败；仓库读取结果单独据实报告 | 未调用却说已搜索；已恢复某笔记；未读取却声称仓库已核对 |
| `not-found`：搜索无命中 | 未找到相关记忆；将读取仓库核对 | 项目没有历史记录；当前状态为某版本 |
| `memory-only`：Memory 已返回、仓库未读取 | 已恢复记忆导航；仓库状态待核对 | 已确认分支、测试、验收或发布状态 |
| `verified-source`：Memory 与仓库均实际返回 | 已读取并核对；列出真实来源 | 超出返回内容推断完成或发布状态 |

- “准备读取”“要求用户提供”和“根据惯例推测”都不等于已经读取。
- 仓库路径未知或文件读取失败时，索取最小路径，或报告下一步只读定位；不要虚构路径、文件名、HEAD、测试结果和状态。
- 只有仓库正式文件、版本控制信息或真实产物证据支持时，才能宣布“通过”“已发布”或“无阻塞”。证据未返回时统一降级为“待验证”。
- 最终回复中的每个完成态结论都应能指向本轮实际读取的来源；无法指出来源时改写为待核对事项。

`auto` 恢复不可用时简要说明已做和未做的动作，区分工具缺项与调用失败，继续核对正式材料；仓库已核对就不写仍待核对。只有尚无有效项目证据时可用下面示例：

```text
场景：已知项目的新线程恢复。Memory（auto）：已检查能力，当前工具不可用，未执行搜索或读取。将定位项目并读取 current/progress/verification 等正式文件，冲突以仓库事实为准；本线程核对后沿用，不重复恢复；证据到位前不判断通过、发布或无阻塞。
```

上述契约仅适用于恢复失败。稳定阶段已经由本轮材料确认、只是 Memory 写工具不可用时，不重新质疑阶段结论，也不要求再次恢复仓库；继续完成正常收尾，并单独报告：`Memory：未写入（工具不可用）`。如需安排工具恢复后的动作，必须保持完整闭环：先搜索同项目既有笔记、优先更新、写后回读或搜索确认，并报告实际笔记名称。

## 自动写入

`auto` 模式只在形成可复用、可核对的稳定结论后写入。典型事件包括：

- `/review` 已形成项目地图、当前阶段和正式文档入口；
- `/idea` 已形成版本主线、正式分流或长期不做决策；
- 完整 PRD 已确认，或开发承接文件已正式落盘；
- `/acceptance` 已形成通过、部分通过、未通过或待验证的真实结论；
- 发布已完成并形成 commit、tag、Release、回滚点；
- 项目被暂停、终止、归档或满足重启条件。

写入顺序：

1. 先确认正式文档已经写入且状态一致，草稿讨论不抢跑。
2. 搜索同一项目和版本的已有笔记；优先更新现有笔记，避免重复项目摘要。
3. 只写摘要、正式路径、稳定决策、状态、阻塞、已知限制和下次继续点。
4. 对密码、Token、Cookie、数据库凭据、私密账号、密钥和敏感日志做排除；不能可靠脱敏时不写。
5. 写入后重新读取或搜索确认落盘，并简短报告：`Memory：已更新 [笔记名]；记录了 [状态/决策/下一步]。`

### 来源与新鲜度合同

<!-- contract:memory-provenance -->
长期条目必须能说明“谁确认、从哪里得出、何时仍有效”。使用以下来源标签，允许和 `[risk]`、`[next]` 等内容标签组合：

- `[user-decision]`：用户明确作出的决定、授权或取舍。
- `[repo-fact]`：仓库正式文件、Git 状态或锁定产物支持的事实。
- `[verified-result]`：本轮工具实际运行、验收或测试得到的结果。
- `[preference]`：用户明确表达且未来会复用的偏好。

本轮实际读取的仓库文件或用户提供的当前仓库状态附件，应明确标为 `[repo-fact]` 或 `verified-source`，其证据等级高于旧 Memory。附件内部存在 README、current、progress、产物清单等互相冲突的主张时，附件仍是已读取的证据源，但不能把其中每条主张都自动判真；应逐项记录来源、冲突和当前可支持的最小结论。

不得把模型推断、搜索摘要、未落盘方案或“看起来应该完成”写成长期事实；它们留在项目文档的待确认项中。生成 Memory 写入动作、候选清单、降级提示词或下次记忆建议时，也必须完全省略这些无证据内容，不能改写成“风险”“待验证”或“以后关注”后带入 Memory。输入同时包含稳定事实和模型怀疑时，只记录稳定事实。阶段、版本、验收和发布状态除来源标签外，还要保留正式文件路径，以及适用的版本、分支/HEAD、产物身份或验证时间。新证据替代旧状态时更新同一笔记，记录“旧状态已过期/被替代”，不要让相互冲突的完成态并列存在。

来源标签不降低隐私门槛：即使信息由用户明确陈述，凭据、敏感日志和不应长期保存的个人信息仍不得写入。写入失败时继续主任务并如实报告，Memory 始终是辅助层，不是完成当前阶段的前置条件。

以下情况不自动写入：轻量建议、视觉随口反馈、未确认方案、临时排查、单次命令输出、尚未落盘的中间状态、用户设为 `off`。工具不可用时写明 `Memory：未写入（工具不可用）`，不得声称成功。

如果用户要求保存一个已经确认的稳定阶段，但工具不可用，可以给出稍后执行的脱敏提示词。提示词必须要求先搜索并更新同一项目的既有笔记，写后回读确认；仍需保留该阶段的长期摘要骨架：最终方案或状态、非目标、正式文件路径、验收口径、已知限制和下一步。无证据判断即使被列为“风险”也不得进入提示词或长期记忆，只留在项目正式文档的待确认项中；不得因为降级而漏掉验收口径，也不得包含账号、密码、Token、连接串、完整日志或临时输出。

## 何时使用

| 场景 | 推荐能力 | 用途 |
| --- | --- | --- |
| 新线程恢复旧项目 | `memory-continue` | 搜索项目背景、最近状态、开放任务和上次继续点 |
| 多步骤、跨线程、跨版本任务 | `memory-tasks` | 创建或更新任务状态，避免长任务断线 |
| 长期偏好、约定、产品决策 | `memory-notes` | 记录未来会复用的信息 |
| 一个阶段或线程结束 | `memory-capture` | 沉淀本次讨论的最终结论和下一步 |
| 一段时间后整理记忆 | `memory-reflect` | 从近期记录中提炼长期有用内容 |
| 记忆重复、膨胀、过期 | `memory-defrag` | 合并重复、拆分大文件、清理过期信息 |
| Project/Task/Decision 等结构变多 | `memory-schema` | 建立或维护统一结构，提升检索质量 |

## MyP-M-A 应该记什么

优先记录：

- 项目背景：产品定位、目标用户、当前阶段、技术栈、重要目录、发布分支、版本线。
- 产品决策：为什么做、为什么不做、已确认方案、延后项、非目标。
- 用户偏好：输出语言、文档命名、粒度偏好、是否需要提示词、是否偏好轻量方案。
- 需求状态：需求池主线、进入 PRD 的 IDEA、暂不做原因、验证缺口。
- PRD 结果：最终方案、目标版本、影响范围摘要、高保真原型路径、开发承接文件路径。
- 验收结果：通过/部分通过/未通过、关键证据、人工补证项、发布状态、回滚点。
- 下次继续点：下一阶段入口、推荐提示词、需要准备的文件或证据。

谨慎记录：

- 本机路径：只有当路径稳定、未来必然会用到时才记录。
- 日志片段：只记录关键结论和证据文件路径，不复制大段日志。
- 未验证判断：不写入长期记忆；留在项目正式文档的开放问题、风险或待验证清单中。

不要记录：

- 全量聊天记录。
- 临时 shell 输出。
- 临时截图路径，除非它是正式验收证据。
- 密钥、token、cookie、完整凭据。
- 已明确作废的中间方案，除非它解释了重要取舍。

## 阶段接入

### /review

Review 结束后，如果它帮助建立了项目地图、架构图、文档结构或当前阶段判断，`auto` 模式更新项目背景；`suggest` 模式才输出建议。

适合记录：

- 项目定位、当前版本、主分支或工作区语义。
- 核心模块关系和架构图摘要。
- 文档结构治理结论。
- Review 发现但尚未进入 `/idea` 的候选问题。

示例提示词：

```text
用 memory-notes 为这个项目更新背景笔记：记录当前产品定位、版本状态、关键目录、文档结构、review 得到的主要架构结论和下一步候选问题。不要记录临时过程，只保存未来会复用的信息。
```

### /idea

`/idea` 不把每个候选想法写入长期记忆。只有需求池形成版本主线、明确进入 `/prd`、形成长期不做判断，或沉淀用户偏好时，`auto` 模式才更新记忆。

适合记录：

- 版本主线和推荐范围。
- 进入 `/prd` 的 IDEA 编号和理由。
- 暂不做/继续验证的原因。
- 压力测试中暴露的长期场景缺口。

示例提示词：

```text
用 memory-notes 记录这次 /idea 的长期结论：版本主线、进入 /prd 的需求、暂不做项、继续验证项、关键证据和下一步。不要保存完整需求池内容，需求池仍以项目文档为准。
```

### /prd

完整 PRD 确认后，`auto` 模式记录最终产品决策；如果接下来会跨线程实现，再创建或更新 `memory-tasks`。方案收敛版或未确认 PRD 不自动写入最终决策。

适合记录：

- 最终方案、目标版本、非目标。
- 关键影响范围和高保真原型路径。
- 开发前验收口径。
- `dev_plan_vx.x.md`、`progress_vx.x.md`、`dev_log_vx.x.md` 路径。

示例提示词：

```text
用 memory-notes 记录这版 PRD 的最终决策：目标版本、采用方案、非目标、关键影响范围、原型路径、验收口径和开发承接文件路径。只记录长期有用结论，不复制整份 PRD。
```

如果任务会跨线程：

```text
用 memory-tasks 创建一个任务，跟踪这个版本从开发承接到实现、验收和发布收口的进度。任务中包含 PRD、dev plan、progress、dev log 路径，以及当前完成标准。
```

### 开发承接

开发承接完成后，如果任务会跨窗口或多天实现，`auto` 模式创建或更新 `memory-tasks`。任务记录指向项目仓库中的正式文件，不复制 progress 正文。

适合记录：

- 当前任务状态。
- 文件路径和验证命令。
- 任务边界和不允许扩张范围。
- 下次继续时应该先读哪些文件。

### /acceptance

Acceptance 结束后，如果结论会影响发布或后续版本，`auto` 模式记录发布状态和遗留项。若还有人工补证项，记录真实的“部分通过/待补证”，不能写成“通过”。

适合记录：

- 验收结论：通过 / 部分通过 / 未通过 / 待验证。
- 最终发布源、产物、tag、回滚点。
- 人工补证项和证据要求。
- 进入下一版本 `/idea` 的遗留候选。

示例提示词：

```text
用 memory-capture 记录这次验收和发布收口结论：只保存发布状态、关键证据、已知限制、回滚点、人工补证项和下次继续点，不记录临时操作过程。
```

## 下一阶段建议中的写法

`suggest` 模式下，当满足以下条件之一时，在“下一阶段建议”里加入长期记忆建议；`auto` 模式改为报告实际恢复/写入结果，不再让用户重复发送保存提示词：

- 任务可能跨线程、跨天或跨项目窗口继续。
- 用户明确提到“记住”“长期”“恢复上下文”“下次继续”。
- 形成了重要产品决策、项目约定或发布状态。
- 当前输出是完整 PRD、开发承接、验收结论或发布收口。
- 发现了会影响未来判断的用户偏好。

推荐格式：

````markdown
## 长期记忆建议

建议记录：
- 决策：
- 路径：
- 下次继续点：

可直接发送：

```text
用 memory-capture 记录这次讨论的结论，只保存长期有用的决策、偏好、路径、约定、踩坑和下次继续点，不记录临时过程。
```
````

如果当前没有可用的 Basic Memory 工具，写成：

```text
当前线程未确认可直接调用 Basic Memory 工具。以下建议仅在当前模式允许且工具可用后执行，不要求重启才能继续项目：
...
```

## 周期性维护

需要验证 Memory 写入与恢复质量时，读取 `templates/memory-validation-template.md`，记录写入内容、恢复结果、过期状态和不应进入记忆的临时信息。静态模板存在不等于链路已验证，必须实际完成一次写入和恢复。

当 MyP-M-A 使用一段时间后，建议周期性维护记忆：

- 每 1-2 天或一个阶段结束后：使用 `memory-reflect` 提炼近期长期结论。
- 每 1-2 周或记忆明显重复时：使用 `memory-defrag` 清理重复、过期和膨胀内容。
- 当 Project、Task、Decision、Release 等笔记越来越多时：使用 `memory-schema` 建立统一结构。

维护原则：

- 不删除原始审计证据，除非用户明确要求。
- 合并重复结论，不追加重复段落。
- 过期状态要更新并标明替代来源，不让旧版本状态误导新线程。
