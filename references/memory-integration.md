# 长期记忆集成

本文定义 MyP-M-A 如何接入 Basic Memory 与 `memory-*` skills。长期记忆不是自动保存全部聊天，而是一个按事件触发、可检索、可整理、可跨会话续接的本地产品知识库。

本地记忆库路径：

```text
D:\Work\Software\codex_home\basic-memory
```

## 基本原则

- 只保存长期有用的信息：决策、偏好、项目背景、版本状态、重要路径、约定、踩坑、未完成事项和下次继续点。
- 不保存临时过程：原始聊天流水、重复命令输出、一次性探索、已废弃草稿、无证据猜测。
- 不保存敏感信息：API key、token、密码、私密账号、不可公开的密钥内容。
- 不把 Basic Memory 当作 PRD、需求池或验收文档的替代品；正式交付物仍应写在项目仓库。
- 记忆内容默认中文；必要的 observation 标签可以使用 `[decision]`、`[preference]`、`[risk]`、`[next]` 等英文标签。
- 如果当前线程没有可用的 Basic Memory MCP 工具，不要假装已经写入；可以输出可直接发送的 `memory-*` 提示词，或说明需要在新线程/重启后执行。

## 运行模式

每次进入明确项目时确定本轮 `memory_mode`。用户明确指定时优先；未指定时默认 `auto`。

| 模式 | 行为 |
| --- | --- |
| `auto` | 在“新线程恢复”和“稳定阶段收尾”两个事件自动读写；不在普通中间轮次反复写入 |
| `suggest` | 不直接读写，只在阶段末给出适合的 `memory-*` 建议 |
| `off` | 本轮不读取、不写入，也不追加 Memory 建议 |

用户说“不要用 Memory”“本轮不保存”时视为 `off`；说“只提醒我”时视为 `suggest`；说“自动维护项目记忆”时视为 `auto`。模式只影响本轮或用户明确指定的范围，不擅自写入全局配置。

## 自动恢复

`auto` 模式下，同时满足以下条件时自动尝试恢复：

- 用户给出明确项目名或项目路径；
- 当前是新线程、用户说“继续/回到/接着”，或现有上下文不足以可靠判断当前状态；
- Basic Memory 工具可用。

执行顺序：

1. 先搜索项目全名、简称和稳定路径，避免只按单一名称漏检。
2. 找到候选后读取最相关的项目状态、版本任务或发布记录；没有命中时不创建空笔记。
3. 将 Memory 只作为导航，继续读取项目仓库中的 `current`、`status`、`progress`、PRD 或验收文档。
4. 如果 Memory 与项目事实源冲突，以项目仓库为准；本轮形成稳定事实后再更新旧记忆。
5. 只在实际恢复过时简短说明：`Memory：已恢复 [笔记名]，并以 [正式文件] 完成核对。`

同一线程已恢复且项目没有切换时，不要每轮重复调用 `memory-continue`。

## 自动写入

`auto` 模式只在形成可复用、可核对的稳定结论后写入。典型事件包括：

- `/review` 已形成项目地图、当前阶段和正式文档入口；
- `/idea` 已形成版本主线、正式分流或长期不做决策；
- 完整 PRD 已确认，或开发承接文件已正式落盘；
- `/acceptance` 已形成通过、部分通过、未通过或待验证的真实结论；
- 发布已完成并形成 commit、tag、Release、回滚点；
- 项目被暂停、终止、归档或满足重启条件。

写入顺序：

1. 先确认正式文档已经写入且状态一致，草稿讨论不抢跑。
2. 搜索同一项目和版本的已有笔记；优先更新现有笔记，避免重复项目摘要。
3. 只写摘要、正式路径、稳定决策、状态、阻塞、已知限制和下次继续点。
4. 对密码、Token、Cookie、数据库凭据、私密账号、密钥和敏感日志做排除；不能可靠脱敏时不写。
5. 写入后重新读取或搜索确认落盘，并简短报告：`Memory：已更新 [笔记名]；记录了 [状态/决策/下一步]。`

以下情况不自动写入：轻量建议、视觉随口反馈、未确认方案、临时排查、单次命令输出、尚未落盘的中间状态、用户设为 `off`。工具不可用时写明 `Memory：未写入（工具不可用）`，不得声称成功。

如果用户要求保存一个已经确认的稳定阶段，但工具不可用，可以给出稍后执行的脱敏提示词。提示词仍需保留该阶段的长期摘要骨架：最终方案或状态、非目标、正式文件路径、验收口径、已知限制和下一步；不得因为降级而漏掉验收口径，也不得包含账号、密码、Token、连接串、完整日志或临时输出。

## 何时使用

| 场景 | 推荐能力 | 用途 |
| --- | --- | --- |
| 新线程恢复旧项目 | `memory-continue` | 搜索项目背景、最近状态、开放任务和上次继续点 |
| 多步骤、跨线程、跨版本任务 | `memory-tasks` | 创建或更新任务状态，避免长任务断线 |
| 长期偏好、约定、产品决策 | `memory-notes` | 记录未来会复用的信息 |
| 一个阶段或线程结束 | `memory-capture` | 沉淀本次讨论的最终结论和下一步 |
| 一段时间后整理记忆 | `memory-reflect` | 从近期记录中提炼长期有用内容 |
| 记忆重复、膨胀、过期 | `memory-defrag` | 合并重复、拆分大文件、清理过期信息 |
| Project/Task/Decision 等结构变多 | `memory-schema` | 建立或维护统一结构，提升检索质量 |

## MyP-M-A 应该记什么

优先记录：

- 项目背景：产品定位、目标用户、当前阶段、技术栈、重要目录、发布分支、版本线。
- 产品决策：为什么做、为什么不做、已确认方案、延后项、非目标。
- 用户偏好：输出语言、文档命名、粒度偏好、是否需要提示词、是否偏好轻量方案。
- 需求状态：需求池主线、进入 PRD 的 IDEA、暂不做原因、验证缺口。
- PRD 结果：最终方案、目标版本、影响范围摘要、高保真原型路径、开发承接文件路径。
- 验收结果：通过/部分通过/未通过、关键证据、人工补证项、发布状态、回滚点。
- 下次继续点：下一阶段入口、推荐提示词、需要准备的文件或证据。

谨慎记录：

- 本机路径：只有当路径稳定、未来必然会用到时才记录。
- 日志片段：只记录关键结论和证据文件路径，不复制大段日志。
- 未验证判断：必须标为“待验证”或 `[hypothesis]`。

不要记录：

- 全量聊天记录。
- 临时 shell 输出。
- 临时截图路径，除非它是正式验收证据。
- 密钥、token、cookie、完整凭据。
- 已明确作废的中间方案，除非它解释了重要取舍。

## 阶段接入

### /review

Review 结束后，如果它帮助建立了项目地图、架构图、文档结构或当前阶段判断，`auto` 模式更新项目背景；`suggest` 模式才输出建议。

适合记录：

- 项目定位、当前版本、主分支或工作区语义。
- 核心模块关系和架构图摘要。
- 文档结构治理结论。
- Review 发现但尚未进入 `/idea` 的候选问题。

示例提示词：

```text
用 memory-notes 为这个项目更新背景笔记：记录当前产品定位、版本状态、关键目录、文档结构、review 得到的主要架构结论和下一步候选问题。不要记录临时过程，只保存未来会复用的信息。
```

### /idea

`/idea` 不把每个候选想法写入长期记忆。只有需求池形成版本主线、明确进入 `/prd`、形成长期不做判断，或沉淀用户偏好时，`auto` 模式才更新记忆。

适合记录：

- 版本主线和推荐范围。
- 进入 `/prd` 的 IDEA 编号和理由。
- 暂不做/继续验证的原因。
- 压力测试中暴露的长期场景缺口。

示例提示词：

```text
用 memory-notes 记录这次 /idea 的长期结论：版本主线、进入 /prd 的需求、暂不做项、继续验证项、关键证据和下一步。不要保存完整需求池内容，需求池仍以项目文档为准。
```

### /prd

完整 PRD 确认后，`auto` 模式记录最终产品决策；如果接下来会跨线程实现，再创建或更新 `memory-tasks`。方案收敛版或未确认 PRD 不自动写入最终决策。

适合记录：

- 最终方案、目标版本、非目标。
- 关键影响范围和高保真原型路径。
- 开发前验收口径。
- `dev_plan_vx.x.md`、`progress_vx.x.md`、`dev_log_vx.x.md` 路径。

示例提示词：

```text
用 memory-notes 记录这版 PRD 的最终决策：目标版本、采用方案、非目标、关键影响范围、原型路径、验收口径和开发承接文件路径。只记录长期有用结论，不复制整份 PRD。
```

如果任务会跨线程：

```text
用 memory-tasks 创建一个任务，跟踪这个版本从开发承接到实现、验收和发布收口的进度。任务中包含 PRD、dev plan、progress、dev log 路径，以及当前完成标准。
```

### 开发承接

开发承接完成后，如果任务会跨窗口或多天实现，`auto` 模式创建或更新 `memory-tasks`。任务记录指向项目仓库中的正式文件，不复制 progress 正文。

适合记录：

- 当前任务状态。
- 文件路径和验证命令。
- 任务边界和不允许扩张范围。
- 下次继续时应该先读哪些文件。

### /acceptance

Acceptance 结束后，如果结论会影响发布或后续版本，`auto` 模式记录发布状态和遗留项。若还有人工补证项，记录真实的“部分通过/待补证”，不能写成“通过”。

适合记录：

- 验收结论：通过 / 部分通过 / 未通过 / 待验证。
- 最终发布源、产物、tag、回滚点。
- 人工补证项和证据要求。
- 进入下一版本 `/idea` 的遗留候选。

示例提示词：

```text
用 memory-capture 记录这次验收和发布收口结论：只保存发布状态、关键证据、已知限制、回滚点、人工补证项和下次继续点，不记录临时操作过程。
```

## 下一阶段建议中的写法

`suggest` 模式下，当满足以下条件之一时，在“下一阶段建议”里加入长期记忆建议；`auto` 模式改为报告实际恢复/写入结果，不再让用户重复发送保存提示词：

- 任务可能跨线程、跨天或跨项目窗口继续。
- 用户明确提到“记住”“长期”“恢复上下文”“下次继续”。
- 形成了重要产品决策、项目约定或发布状态。
- 当前输出是完整 PRD、开发承接、验收结论或发布收口。
- 发现了会影响未来判断的用户偏好。

推荐格式：

````markdown
## 长期记忆建议

建议记录：
- 决策：
- 路径：
- 下次继续点：

可直接发送：

```text
用 memory-capture 记录这次讨论的结论，只保存长期有用的决策、偏好、路径、约定、踩坑和下次继续点，不记录临时过程。
```
````

如果当前没有可用的 Basic Memory 工具，写成：

```text
当前线程未确认可直接调用 Basic Memory 工具。建议在新线程或重启后发送以下提示词：
...
```

## 周期性维护

需要验证 Memory 写入与恢复质量时，读取 `templates/memory-validation-template.md`，记录写入内容、恢复结果、过期状态和不应进入记忆的临时信息。静态模板存在不等于链路已验证，必须实际完成一次写入和恢复。

当 MyP-M-A 使用一段时间后，建议周期性维护记忆：

- 每 1-2 天或一个阶段结束后：使用 `memory-reflect` 提炼近期长期结论。
- 每 1-2 周或记忆明显重复时：使用 `memory-defrag` 清理重复、过期和膨胀内容。
- 当 Project、Task、Decision、Release 等笔记越来越多时：使用 `memory-schema` 建立统一结构。

维护原则：

- 不删除原始审计证据，除非用户明确要求。
- 合并重复结论，不追加重复段落。
- 过期状态要更新，不让旧版本状态误导新线程。
