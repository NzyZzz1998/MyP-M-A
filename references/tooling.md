本文件定义 MyP-M-A 四个入口如何使用外部工具、插件和本地验证能力。工具不是为了让输出显得复杂，而是为了让产品判断、评审、PRD 和验收更有证据。

当任务需要数据分析、原型、浏览器/桌面验证或远端发布等专门方法时，同时读取 `references/capability-routing.md`。本文件回答“工具怎样安全使用和降级”，能力路由回答“当前产品问题应该选择哪一种专门能力”，两者不要重复堆叠。

## 总原则

- 先判断入口和阶段，再选择工具。
- 优先使用最小必要工具：能读文件解决的，不先打开桌面；能用日志确认的，不只靠肉眼截图。
- 事实结论必须绑定证据来源。证据可以来自代码、日志、截图、实际操作、CI、PR、用户反馈、数据表、文档或公开资料。
- 工具不可用时，不要伪造证据；把相关项标为“待验证”，并说明缺少什么工具或材料。
- 对个人项目默认轻量：优先本地文件、日志、截图、人工路径和少量关键测试。
- 涉及发布、验收、回滚、数据迁移、配置兼容时，工具检查优先于主观判断。
- 先识别当前会话真实可用的工具、skill 和插件，不把文档中的能力名称当作已经安装。
- 只读检查可以在用户给定范围内主动执行；发送消息、修改远端、发布、推送、打 tag、改生产数据、产生费用等外部写操作必须等待用户授权。
- 产品页面、原型和可视化交付使用当前项目品牌；MyP-M-A 评测页使用 MyP-M-A。外部 brainstorming/skill 只作内部材料，不把 `.superpowers` 等目录或品牌写进正式产物；真实调用记在证据附录或内部元数据，不改写评测原文。

## 能力探测与降级

工具能力分开记录 `installed / callable / call_succeeded / version / commit / license`。清单出现只表示已知或已安装；当前会话暴露接口才可调用；本轮最小探测成功才可写调用成功。缺字段写未知，不互相推导。最终状态统一为：

| 状态 | 判定 | 后续动作 |
| --- | --- | --- |
| 可用 | 最小探测成功 | 只在探测覆盖范围内使用 |
| 降级可用 | 主能力失败，但替代链路有直接证据 | 写明替代工具与未覆盖范围 |
| 待人工 | 自动能力无法触达真实 GUI、账号、设备或感官路径 | 生成可执行手动验证步骤 |
| 被阻塞 | 无可靠能力或缺少授权/必要输入 | 停止事实性结论，列解除条件 |

一次失败只证明该调用或链路失败，不自动证明仓库、产品或网络整体故障。例如本地代理端口停止时，应尝试已允许的直连或 GitHub 插件；成功则记“降级可用”，不能写成仓库冲突。能力记录最少包含：真实工具、探测动作、直接证据、状态、降级路径和未覆盖范围。

开始调用工具前，按以下顺序判断：

1. 当前是否已有直接能力，例如本地文件、GitHub、Computer Use、浏览器、数据库或文档工具。
2. 如果没有直接能力，是否有同类替代，例如日志替代部分桌面观察、本地 git 替代部分 GitHub 读取、人工验证文档替代无法自动化的真实设备路径。
3. 如果替代能力只能覆盖部分结论，明确标记“已验证范围”和“待验证范围”。
4. 如果没有任何可靠证据来源，停止给事实性通过结论，只输出取证计划。

常见降级顺序：

- 桌面 GUI：Computer Use + 日志/配置 -> 用户手动验证文档 + 日志/配置 -> 待验证。
- Web：浏览器/Playwright -> HTTP/日志/截图静态检查 -> 用户手动验证 -> 待验证。
- GitHub：GitHub 插件 -> 本地 git 与用户提供的 CI/PR 证据 -> 待验证远端状态。
- 代码评审：已授权的独立 OCR review -> 本地 OCR Delegation -> git diff + 语言检查器/定向测试 -> 待验证未覆盖范围。
- 数据库：只读数据库工具 -> schema/迁移/ORM/样本导出 -> 数据地图与待确认项。
- 竞品：公开一手资料 -> 用户提供截图/文档 -> 明确标注经验推断。

## 工具类型

| 工具/插件 | 适合做什么 | 常见入口 |
| --- | --- | --- |
| 本地文件与 shell | 读项目结构、配置、日志、测试、构建、版本号、数据库迁移 | `/review`、`/prd`、`/acceptance` |
| OpenCodeReview 或等价代码扫描器 | 选择 diff/commit/range、加载语言规则、生成候选 finding | `/review` 的 implementation 通路 |
| GitHub 插件 | 读仓库、Issue、PR、diff、review comments、CI、Release、里程碑 | `/idea`、`/review`、`/prd`、`/acceptance` |
| Computer Use | 操作 Windows 桌面软件、exe、托盘、菜单、弹窗、真实点击路径、截图 | `/review`、`/acceptance`，必要时 `/prd` |
| 浏览器 / Playwright / webapp-testing | 验证 Web 页面、交互、控制台、网络、响应式截图 | `/review`、`/acceptance`，必要时 `/prd` |
| Web 搜索 | 查竞品、市场信号、公开文档、同类产品做法 | `/idea`、必要时 `/prd` |
| 文档/PDF/图片/表格工具 | 读取 PRD、截图反馈、用户访谈、数据表、验收记录 | `/idea`、`/review`、`/prd`、`/acceptance` |
| 数据库/数据分析工具 | 读取 schema、样本数据、字段分布、指标口径、漏斗和错误率 | `/idea`、`/prd`、必要时 `/acceptance` |
| 图表/图解 Skill | 把已验证事实表达为图表或语义图解；探测六字段与外部资源 | 四入口按需 |
| UI/UX / frontend-design 类 skill | 组件规范、高保真原型、视觉精修、页面结构和交互状态 | `/prd`、`/review` |
| Lark/飞书工具 | 读取或写入协作文档、需求池、任务、会议纪要、表格、发布说明 | 四个入口均可按用户环境使用 |
| Vercel/Netlify/部署工具 | 检查部署、Preview、环境变量、发布状态、回滚 | `/acceptance`，必要时 `/review` |
| OpenAI/API 相关工具 | 检查 AI 功能配置、API key 环境、模型调用失败、评估样例 | AI 产品的 `/prd`、`/acceptance` |
| Basic Memory / `memory-*` skills | 保存长期产品决策、项目上下文、用户偏好、任务状态和下次继续点 | 四个入口、开发承接、线程结束 |

企业协作或外部数据取证不绑定具体插件。需要跨系统对齐对象或读取产品指标时，按需读取 `references/enterprise-adapters.md`：先生成只读证据信封，再把事实带回当前入口。插件已安装不代表对象可读；读取成功也不授权评论、建任务、改文档、推送或更新仪表盘。

正式出图读 `references/visual-delivery.md`，数值图再读 `chart-delivery.md`。diagram-design 最近缓存身份为 `2.5.5` / commit `29917724f832f0dff2faf4ec583c6c603bed11ba` / MIT，但 skill frontmatter 仍为 `2.4`；每轮必须重探实际缓存、当前可调用性与调用结果。Lieflat 为 PolyForm Noncommercial；商业任务无单独授权时禁用并降级，不复制模板。

## 四个入口的工具策略

### /idea：找证据，不做重验收

`/idea` 的工具目标是回答“这是真问题吗、值不值得继续、现在该不该做”。优先找需求证据，而不是做完整实现检查。

可使用：

- GitHub Issues、Discussions、PR 评论：看真实反馈、复现次数、已有痛点。
- Web 搜索或竞品页面：看同类产品是否有类似能力、是否是常见用户心智。
- 用户反馈文档、会议纪要、表格：整理来源、频率、人群和场景。
- 本地 review 结果：作为内部发现来源，但不能单独证明用户价值。

输出要求：

- 标注证据强度：强 / 中 / 弱 / 无。
- 如果证据主要来自内部 review 或个人直觉，必须进入压力测试。
- 不做实际通过/失败判断；那属于 `/acceptance`。

### /review：建立地图，再发现问题

`/review` 的工具目标是理解对象脉络：项目怎么运转、页面怎么走、PRD 怎么定义、实现怎么落地。

可使用：

- 本地文件与 shell：`rg`、文件树、README、入口文件、配置、日志、测试目录。
- OCR/代码扫描器：在锁定 diff、commit 或发布区间后做语言规则扫描；详细隐私、独立性、证据闭环和降级规则见 `references/code-review-scanner.md`。
- GitHub：仓库结构、PR 历史、Issue、CI、Release。
- Computer Use：桌面应用真实窗口、托盘、弹窗、右键菜单、点击路径。
- 浏览器/Playwright：Web 页面交互、响应式、控制台和网络错误。
- 文档/截图工具：PRD、页面截图、流程图、用户反馈。

输出要求：

- 先输出对象脉络和架构图/流程图，再列问题。
- 每个发现必须有中文证据状态：已确认 / 高度可能 / 待确认 / 主观判断。
- Review 发现只是候选点，进入 `/idea` 后再判断价值和优先级。

### /prd：补上下文，明确影响范围

`/prd` 的工具目标是让需求可开发、可测试、可验收。它不要求每次都跑项目，但必须在影响范围不清时补上下文。

可使用：

- 本地文件：确认模块、页面、配置、数据库字段、接口、状态、日志事件。
- GitHub：关联 Issue/PR、历史方案、已有约束、里程碑。
- 文档/图片：读取既有 PRD、原型、截图反馈。
- Mermaid/原型网页：表达流程、页面结构和状态。
- Computer Use 或浏览器：当用户要求基于现有 UI 写 PRD，或需要观察当前真实行为。

输出要求：

- 把工具发现写入“依据/影响范围”，不要混成拍脑袋结论。
- 如果没有检查到代码或真实界面，影响范围要标注“待开发确认”。
- 开发前验收目标、验收标准、日志/埋点/人工检查、通过标准、不通过处理仍由 `/prd` 制定。

### /acceptance：实际验证，证据优先

`/acceptance` 的工具目标是判断开发结果是否通过、发布是否可控、上线后看什么信号。它是四个入口中最依赖工具证据的入口。

遇到以下输入时，应优先实际检查：

- exe、桌面应用、托盘、菜单、Windows 原生能力：使用 Computer Use，并结合日志、配置和截图。
- Web URL、本地 dev server、页面改动：使用浏览器/Playwright/webapp-testing，并记录截图、控制台、网络或交互结果。
- GitHub PR/commit/CI：使用 GitHub 插件读取 diff、CI、review comments、release 信息。
- 日志路径、配置路径、构建产物：读取尾部日志、配置值、版本号、启动结果。
- 数据库/迁移/埋点：检查字段、事件名、触发时机、兼容性和失败处理。

输出要求：

- 必须列明“使用工具与证据来源”。
- 验收结论分为：通过 / 部分通过 / 未通过 / 待验证。
- 没有实际运行、日志、截图、测试、CI 或用户证据时，只能输出待验收清单，不能给通过结论。
- 如果 Computer Use、GitHub、浏览器或部署工具不可用，说明缺口，并给出用户或下一次 agent 需要补的证据。

## 工具选择决策

按输入类型选择：

| 输入线索 | 首选工具 | 入口倾向 |
| --- | --- | --- |
| 项目路径、代码库、配置、日志 | 本地文件 + shell | `/review`、`/acceptance` |
| 代码 diff、commit、PR、发布区间 | 本地 git + OCR/等价代码扫描器；MyP-M-A 复核 | `/review` implementation |
| GitHub 链接、PR、Issue、CI | GitHub 插件 | 四个入口 |
| exe、Windows 桌面、托盘、菜单 | Computer Use | `/review`、`/acceptance` |
| Web 页面、localhost、部署预览 | 浏览器 / Playwright | `/review`、`/acceptance` |
| 截图、UI 反馈 | 图片分析，必要时 Computer Use/浏览器 | `/review`、`/prd` |
| PRD、会议纪要、表格 | 文档/表格工具 | `/idea`、`/prd` |
| 数据库、schema、SQL、指标表、日志表 | 数据库/数据分析工具 + 本地 shell | `/idea`、`/prd` |
| UI polish、高保真原型、组件系统 | UI/UX / frontend-design skill，必要时浏览器验证 | `/prd`、`/review` |
| 竞品、市场、公开资料 | Web 搜索 | `/idea` |
| 发布、灰度、回滚 | GitHub/Vercel/Netlify/部署工具 + 日志 | `/acceptance` |
| 长期记忆、跨线程、下次继续、记住偏好/决策/项目状态 | Basic Memory / `memory-*` skills | 四个入口、开发承接 |
| 远端仓库、协作文档、任务系统与本地事实对齐 | 当前可用只读连接器 + `enterprise-adapters.md` | `/review`、`/acceptance`、`/prompt` |
| 外部指标、评测 JSON/CSV、查询结果与产品判断 | 数据能力 + `enterprise-adapters.md` | `/idea`、`/review`、`/acceptance` |

## 长期记忆工具策略

Basic Memory 是事件驱动的长期知识库能力，不是聊天记录器。MyP-M-A 默认使用克制的 `auto` 模式：只在已知项目的新线程恢复，以及形成稳定阶段结论后更新；用户可改为 `suggest` 或 `off`。具体规则见 `references/memory-integration.md`。

常见用法：

- `memory-continue`：新线程恢复旧项目上下文。
- `memory-notes`：记录稳定偏好、项目约定、产品决策、版本状态。
- `memory-tasks`：跟踪跨线程、跨版本的开发承接或发布收口任务。
- `memory-capture`：阶段结束时沉淀最终结论和下次继续点。
- `memory-reflect` / `memory-defrag` / `memory-schema`：周期性整理、去重和结构化。

使用边界：

- 不把完整聊天、临时过程、长日志或敏感信息写入记忆。
- 正式交付物仍保存在项目仓库；记忆只保存摘要、路径、决策和下次继续点。
- `auto` 模式下如果当前线程没有可用的 Basic Memory 工具，明确报告未恢复或未写入，不声称成功；只有 `suggest` 模式才默认输出可直接发送的 `memory-*` 提示词。

## 证据写法

推荐格式：

```markdown
## 使用工具与证据来源

- 本地文件：
- GitHub：
- Computer Use / 浏览器：
- 日志 / 配置：
- 用户提供材料：
- 未能验证：
```

在结论里使用：

- “已验证”：有直接工具证据。
- “有证据倾向”：有间接证据，但没有完整复现。
- “待验证”：材料或工具不足。
- “推断”：来自经验判断，需要后续证明。

## 不该调用工具的情况

- 用户只是要产品概念解释、命名建议、轻量头脑风暴。
- 用户明确要求先不要改项目、不要运行、不要联网。
- 当前阶段只需要草拟提问清单或文档骨架。
- 工具成本明显大于收益，例如早期想法还没有任何对象可验证。

即使不调用工具，也要说明判断依据来自用户描述、经验判断还是既有上下文。
