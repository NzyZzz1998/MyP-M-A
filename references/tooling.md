# 工具调用策略

本文件定义 MyP-M-A 四个入口如何使用外部工具、插件和本地验证能力。工具不是为了让输出显得复杂，而是为了让产品判断、评审、PRD 和验收更有证据。

## 总原则

- 先判断入口和阶段，再选择工具。
- 优先使用最小必要工具：能读文件解决的，不先打开桌面；能用日志确认的，不只靠肉眼截图。
- 事实结论必须绑定证据来源。证据可以来自代码、日志、截图、实际操作、CI、PR、用户反馈、数据表、文档或公开资料。
- 工具不可用时，不要伪造证据；把相关项标为“待验证”，并说明缺少什么工具或材料。
- 对个人项目默认轻量：优先本地文件、日志、截图、人工路径和少量关键测试。
- 涉及发布、验收、回滚、数据迁移、配置兼容时，工具检查优先于主观判断。

## 工具类型

| 工具/插件 | 适合做什么 | 常见入口 |
| --- | --- | --- |
| 本地文件与 shell | 读项目结构、配置、日志、测试、构建、版本号、数据库迁移 | `/review`、`/prd`、`/acceptance` |
| GitHub 插件 | 读仓库、Issue、PR、diff、review comments、CI、Release、里程碑 | `/idea`、`/review`、`/prd`、`/acceptance` |
| Computer Use | 操作 Windows 桌面软件、exe、托盘、菜单、弹窗、真实点击路径、截图 | `/review`、`/acceptance`，必要时 `/prd` |
| 浏览器 / Playwright / webapp-testing | 验证 Web 页面、交互、控制台、网络、响应式截图 | `/review`、`/acceptance`，必要时 `/prd` |
| Web 搜索 | 查竞品、市场信号、公开文档、同类产品做法 | `/idea`、必要时 `/prd` |
| 文档/PDF/图片/表格工具 | 读取 PRD、截图反馈、用户访谈、数据表、验收记录 | `/idea`、`/review`、`/prd`、`/acceptance` |
| Lark/飞书工具 | 读取或写入协作文档、需求池、任务、会议纪要、表格、发布说明 | 四个入口均可按用户环境使用 |
| Vercel/Netlify/部署工具 | 检查部署、Preview、环境变量、发布状态、回滚 | `/acceptance`，必要时 `/review` |
| OpenAI/API 相关工具 | 检查 AI 功能配置、API key 环境、模型调用失败、评估样例 | AI 产品的 `/prd`、`/acceptance` |

## 四个入口的工具策略

### /idea：找证据，不做重验收

`/idea` 的工具目标是回答“这是真问题吗、值不值得继续、现在该不该做”。优先找需求证据，而不是做完整实现检查。

可使用：

- GitHub Issues、Discussions、PR 评论：看真实反馈、复现次数、已有痛点。
- Web 搜索或竞品页面：看同类产品是否有类似能力、是否是常见用户心智。
- 用户反馈文档、会议纪要、表格：整理来源、频率、人群和场景。
- 本地 review 结果：作为内部发现来源，但不能单独证明用户价值。

输出要求：

- 标注证据强度：强 / 中 / 弱 / 无。
- 如果证据主要来自内部 review 或个人直觉，必须进入压力测试。
- 不做实际通过/失败判断；那属于 `/acceptance`。

### /review：建立地图，再发现问题

`/review` 的工具目标是理解对象脉络：项目怎么运转、页面怎么走、PRD 怎么定义、实现怎么落地。

可使用：

- 本地文件与 shell：`rg`、文件树、README、入口文件、配置、日志、测试目录。
- GitHub：仓库结构、PR 历史、Issue、CI、Release。
- Computer Use：桌面应用真实窗口、托盘、弹窗、右键菜单、点击路径。
- 浏览器/Playwright：Web 页面交互、响应式、控制台和网络错误。
- 文档/截图工具：PRD、页面截图、流程图、用户反馈。

输出要求：

- 先输出对象脉络和架构图/流程图，再列问题。
- 每个发现必须有证据状态：Confirmed / Likely / Unclear / Opinion。
- Review 发现只是候选点，进入 `/idea` 后再判断价值和优先级。

### /prd：补上下文，明确影响范围

`/prd` 的工具目标是让需求可开发、可测试、可验收。它不要求每次都跑项目，但必须在影响范围不清时补上下文。

可使用：

- 本地文件：确认模块、页面、配置、数据库字段、接口、状态、日志事件。
- GitHub：关联 Issue/PR、历史方案、已有约束、里程碑。
- 文档/图片：读取既有 PRD、原型、截图反馈。
- Mermaid/原型网页：表达流程、页面结构和状态。
- Computer Use 或浏览器：当用户要求基于现有 UI 写 PRD，或需要观察当前真实行为。

输出要求：

- 把工具发现写入“依据/影响范围”，不要混成拍脑袋结论。
- 如果没有检查到代码或真实界面，影响范围要标注“待开发确认”。
- 开发前验收目标、验收标准、日志/埋点/人工检查、通过标准、不通过处理仍由 `/prd` 制定。

### /acceptance：实际验证，证据优先

`/acceptance` 的工具目标是判断开发结果是否通过、发布是否可控、上线后看什么信号。它是四个入口中最依赖工具证据的入口。

遇到以下输入时，应优先实际检查：

- exe、桌面应用、托盘、菜单、Windows 原生能力：使用 Computer Use，并结合日志、配置和截图。
- Web URL、本地 dev server、页面改动：使用浏览器/Playwright/webapp-testing，并记录截图、控制台、网络或交互结果。
- GitHub PR/commit/CI：使用 GitHub 插件读取 diff、CI、review comments、release 信息。
- 日志路径、配置路径、构建产物：读取尾部日志、配置值、版本号、启动结果。
- 数据库/迁移/埋点：检查字段、事件名、触发时机、兼容性和失败处理。

输出要求：

- 必须列明“使用工具与证据来源”。
- 验收结论分为：通过 / 部分通过 / 未通过 / 待验证。
- 没有实际运行、日志、截图、测试、CI 或用户证据时，只能输出待验收清单，不能给通过结论。
- 如果 Computer Use、GitHub、浏览器或部署工具不可用，说明缺口，并给出用户或下一次 agent 需要补的证据。

## 工具选择决策

按输入类型选择：

| 输入线索 | 首选工具 | 入口倾向 |
| --- | --- | --- |
| 项目路径、代码库、配置、日志 | 本地文件 + shell | `/review`、`/acceptance` |
| GitHub 链接、PR、Issue、CI | GitHub 插件 | 四个入口 |
| exe、Windows 桌面、托盘、菜单 | Computer Use | `/review`、`/acceptance` |
| Web 页面、localhost、部署预览 | 浏览器 / Playwright | `/review`、`/acceptance` |
| 截图、UI 反馈 | 图片分析，必要时 Computer Use/浏览器 | `/review`、`/prd` |
| PRD、会议纪要、表格 | 文档/表格工具 | `/idea`、`/prd` |
| 竞品、市场、公开资料 | Web 搜索 | `/idea` |
| 发布、灰度、回滚 | GitHub/Vercel/Netlify/部署工具 + 日志 | `/acceptance` |

## 证据写法

推荐格式：

```markdown
## 使用工具与证据来源

- 本地文件：
- GitHub：
- Computer Use / 浏览器：
- 日志 / 配置：
- 用户提供材料：
- 未能验证：
```

在结论里使用：

- “已验证”：有直接工具证据。
- “有证据倾向”：有间接证据，但没有完整复现。
- “待验证”：材料或工具不足。
- “推断”：来自经验判断，需要后续证明。

## 不该调用工具的情况

- 用户只是要产品概念解释、命名建议、轻量头脑风暴。
- 用户明确要求先不要改项目、不要运行、不要联网。
- 当前阶段只需要草拟提问清单或文档骨架。
- 工具成本明显大于收益，例如早期想法还没有任何对象可验证。

即使不调用工具，也要说明判断依据来自用户描述、经验判断还是既有上下文。
