# `/review` 入口工作流

`/review` 是 MyP-M-A 的“建立对象地图 + 发现候选问题”入口。对外只有一个入口；根据材料自动选择 project、page、prd、implementation 或 release readiness 主通路，必要时追加一个辅助通路。

- 首行写 `入口判断：/review`，并声明主通路、辅助通路、覆盖/不覆盖范围和证据来源；不能用并列类型代替主辅判断。
- 先建立产品与工程地图，再列发现。Project Review 必须给 Mermaid 或等价关系图；多通路材料用一张图说明衔接。
- 每项发现区分已确认、推断、待确认或主观判断，并给可定位的证据来源；未读取或未运行的内容不能写成实证。
- 完整 Project Review 有具体现象时，单列“进入 `/idea` 的候选点”。细节由主发现表承载时，这一节只引用 ID 和最小验证，不重复整行内容；没有可证现象时明确写“当前未形成可证候选点”。
- 完整 Project Review 默认附“下一模型接手摘要”，最多 5 条，只写对象与阶段、正式事实源、稳定结论、阻塞和下一步。
- 代码瘦身必须基于摩擦证据。每个删除或下沉候选逐项核对调用方、动态入口/资源/反射、配置、测试、日志、平台行为，并给最小调整、验证和独立回退；缺证时只能标为待确认。
- 同时有意图文档、代码和测试时读取 `intent-implementation-audit.md`，分开标记实现偏离、文档过期、未验证和待确认。
- implementation 通路有可锁定 diff/commit/range 且代码扫描器可用时，读取 `references/code-review-scanner.md`：MyP-M-A 先定范围，扫描器产出候选，MyP-M-A 再核验；Delegation Mode 不得冒充独立模型评审。
- 项目定位、目标市场、价格、套餐、渠道承诺与当前产品/数据并存时读取 `references/strategy-gtm.md`，核对选择、证据和实际能力的一致性；市场宣传不能替代采用、支付或留存证据。

## 自动选择通路

| 输入线索 | 主通路 | 核心判断 | 常见去向 |
| --- | --- | --- | --- |
| 项目路径、仓库、README、配置、日志 | project | 定位、阶段、核心路径、模块/数据/状态关系、体验与维护债 | `/idea`、直接治理、`/acceptance` |
| 截图、页面、原型、交互反馈 | page | 信息层级、流程、控件、状态、可用性和视觉密度 | `/idea` 或 `/prd` |
| PRD、用户故事、验收标准、路线图 | prd | 目标、范围、影响、表达物、数据和可验收性 | 修 PRD 或补问题 |
| 代码、diff、测试、复现、实现说明 | implementation | 是否符合意图、边界、异常、测试、日志和可维护性 | bugfix、技术债、补证 |
| tag、发布包、checksum、verification、current/status | release readiness | 版本事实、门禁、文档一致性、剩余验收和回滚 | `/acceptance` 或直接修文档 |

同一输入命中多条时，选择最接近用户当前决策的主通路。整个项目的领域、架构或瘦身评审默认 project 为主、implementation 为辅；用户明确限定代码审查时才反转。用户只问“走哪条通路”仍执行最小 Review，除非明确只解释规则。

## 执行流程

### 1. 锁定对象与证据

先确认对象、版本/阶段、输入路径、可信事实源和本轮边界。列出实际使用的文件、日志、截图、命令和工具；没有执行关键命令时写“未执行”及原因。工具不可用或证据过期时降级为待确认。

### 2. 建立地图

按当前通路选择必要内容，不为完整而铺满：

- 产品：定位、目标用户、当前阶段目标、核心场景、成功标准、产品线/版本边界。
- 工程：入口、模块、数据/配置/状态、日志、外部依赖、发布或恢复链路。
- 领域：对象、角色、动作、状态、不变量、术语冲突和待确认 ADR。

产品与工程能在一张关系图中表达时不要拆图。关系标注 `事实`、`推断` 或 `待确认`；不得虚构供应商、接口、数据库字段或已实现行为。

代码扫描是地图后的辅助层，不取代范围判断。私有代码发送给远端 reviewer 前必须获得授权；无独立后端或禁止外发时使用本地 Delegation Mode。默认把扫描候选合并进主发现表，不复制两份结论。

### 3. 形成主发现表

每个发现只完整表达一次：

| ID | 现象 | 严重度 | 证据状态与来源 | 影响 | 最小验证/调整 | 去向 |
| --- | --- | --- | --- | --- | --- | --- |

- Blocker：核心路径不可用、数据/权限严重错误、无法验收或发布。
- Major：显著影响核心体验、稳定性或开发测试风险。
- Minor：真实但不阻塞当前目标。
- Suggestion：需继续判断价值的优化。

严重度不等于优先级；价值与排期由 `/idea` 或 `/prd` 判断。

### 4. 分流与接手

- 直接修：事实性文档不一致、低风险 CI/链接/状态治理。
- `/idea`：价值、影响面或方案仍需验证；仅由本轮发现的候选默认走这里。
- `/prd`：已有用户决策、既有 `/idea` 结论或直接价值/范围证据，需要正式定义。
- `/acceptance`：开发完成或发布前，需要真实产物、日志、截图、CI、浏览器或桌面验收。
- bugfix/dev-log：明确实现缺陷或排查过程。
- 暂不做：与当前阶段不匹配或成本高于收益。

发现超过 2 个候选点时建议由 `/idea` 建立 Markdown 需求池。Review 判断可进入验收时，给一段可直接发送的 `/acceptance` 提示词，包含对象、产物、配置、日志和剩余人工项。

## 分通路检查重点

### Project

检查当前阶段事实源、用户核心路径、产品线/版本边界、模块所有权、配置/状态/日志/持久化、外部依赖、稳定性与体验债、测试/验收路径。多租户 SaaS 必须核对租户上下文、资源归属和跨租户拒绝边界。

出现 queue/worker/异步任务时，核对任务状态、积压、重试/死信、关联 ID、失败日志与指标；缺证时写“异步任务可观测性待确认”。

### Page

检查信息层级、入口到出口、保存/取消/关闭/返回、控件一致性、正常/禁用/加载/空/错误状态、窄屏和产品气质。输出页面结构或用户流程图。

### PRD

检查目标与证据、范围/非目标、影响范围、原型或等价表达物、入口到出口、数据来源、异常、可测试验收、指标/日志和开放问题。

### Implementation

检查意图符合度、主流程与边界、异常/回滚/兼容、配置与数据一致性、测试与人工验收、日志/debug、重复编排和隐式依赖。没有搜索到调用不等于实现不存在，必须继续核对动态入口与平台分支。外部 finding 只有完成可达性、保护条件、测试/复现和需求影响核验后，才能标为已确认。

### Release Readiness

核对分支/远端/tag、候选包/manifest/checksum、README 与 current/status、release notes、verification/progress/checklist、已知限制和回滚。需要运行证据的进入 `/acceptance`；仅事实文本过期的直接修文档。

## 默认输出

正式落盘时读取 `templates/review-report-template.md`。聊天中的完整 Project Review 默认只保留：

1. Review 判断与证据边界。
2. 一张产品/工程关系图。
3. 一张主发现表。
4. 值得保留（最多 3 条）。
5. `/idea` 候选 ID 与下一步。
6. 下一模型接手摘要（最多 5 条）。

领域、瘦身、开放问题和版本建议并入主发现表，不另建同义章节。窄范围 Review 通常 600～1200 个中文字；完整聊天 Review 通常 1800～3500 个中文字。用户要求详细报告或需要正式落盘时再扩展，不用聊天正文复制整份文件。

## 写作要求

- 先解释对象如何运转，再说明问题。
- 已确认、推断、待确认和主观判断不混写。
- 值得保留与问题分开，避免每轮推倒重来。
- 图呈现关键依赖方向，表呈现证据和行动；不要让同一内容同时出现在多个章节。
- 个人项目优先保护核心路径、可完成性、体验质感和维护成本。
