# 交付物追踪规则

本文件用于正式、多阶段、跨线程或版本型项目。一次性轻量咨询不需要为了形式建立编号。

## 目标

让每个阶段都能回答：需求从哪里来、当前处于什么状态、由哪个文件承接、最终如何验收和发布。追踪信息只保存索引和状态，不复制正式文档正文。

## 编号建议

| 阶段 | 编号示例 | 含义 |
| --- | --- | --- |
| Review | `REV-001` | 评审发现、风险或值得保留项 |
| Idea | `IDEA-003` | 经过价值判断的候选需求 |
| PRD | `PRD-005` | 已定义的需求或版本范围 |
| 开发任务 | `DEV-M2.3` | dev plan/progress 中的最小执行项 |
| 验收 | `ACC-004` | 实际验收项 |
| 发布 | `REL-v0.6` | 发布状态、tag 或发布包 |

项目已有编号体系时沿用现有格式，不另造一套。

## 正式文档头部

正式需求池、PRD、开发承接和验收文档至少记录：

- 当前文档状态。
- 目标版本或功能版本。
- 上游来源 ID 与文件路径。
- 下游承接文件或下一阶段。
- 当前事实源。
- 最后更新时间。

推荐写法：

```markdown
## 追踪信息

- 当前状态：
- 目标版本：
- 上游来源：`REV-001` / `IDEA-003` / 文件路径
- 下游承接：
- 当前事实源：
- 最后更新：
```

## 阶段关联

### Review -> Idea

保留 Review ID、证据状态、影响、严重度和最小取证动作。进入 `/idea` 后，严重度不能直接替代价值或优先级。

### Idea -> PRD

保留 IDEA ID、证据等级、压力测试结论、版本主线、进入本版理由、延后项和非目标。

### PRD -> 开发承接

dev plan 建立 PRD 需求点到开发模块的对照；progress 中的每个任务可以追溯到 PRD 章节或需求 ID。开发承接不得静默增加 PRD 范围。

### 开发承接 -> Acceptance

Acceptance 把 PRD 验收标准和 DEV 任务映射到实际结果、证据和结论。未覆盖项必须保留原 ID，不用新的模糊描述替代。

### Acceptance -> Release / 下一版本

通过项进入发布事实源；遗留项分流为 bugfix、人工补证或下一版本 IDEA，并保留原验收 ID。

## 事实源规则

- 当前版本状态应只有一个事实源，例如 `current.md`、版本目录 README 或 progress。
- PRD 是需求范围事实源，dev plan 不能重定义产品范围。
- progress 是执行状态事实源，dev log 不是完成度事实源。
- acceptance 是发布前实际通过状态事实源，自动化测试通过不能覆盖其中的人工待验证项。
- Basic Memory 只保存摘要、路径和下次继续点，不成为正式状态事实源。

发现多个文件状态冲突时，先确认真实代码、分支、tag、发布物和验收证据，再更新过期文档；不要通过新增一份总结继续制造新的事实源。

## 跨材料同步

同一决定需同步方案、流程图、原型或汇报稿时，沿用已有需求/变更编号，在现有记录中保留 `决定与权威来源 | 目标材料及章节/节点/页 | 实际更新结果 | 回读/验证证据或未完成原因`。无既有编号的轻量任务可直接引用本轮决定，不另建事实源或强制编号。

只修改本轮要求或已有授权覆盖的材料及位置。被替换规则在受影响的现行材料中一致更新，未变规则、暂定项和后续范围保持；历史比较和归档保留原版本，不做跨文件全文替换。只授权一份时，可提示其他材料需同步，但不擅自扩改。

逐份区分未修改、已写入并回读、尚待适用验证；节点文本回读不等于图形已渲染，方案更新不证明 PPT 或原型已更新。缺文件、无权限或无法验证时保留具体缺口；交接继承逐份结果，不压成单一“完成”。
