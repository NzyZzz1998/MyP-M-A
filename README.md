# MyP-M-A

**一套面向团队协作与 Vibe Coding 的中文产品经理 Skill，把项目评审、价值判断、需求定义、开发承接和真实验收连接成可追溯的工作流。**

`v0.41.0 Stable（本地待提交）` · `中文优先` · `5 个入口` · `两种交付模式` · `证据驱动`

你可以直接给它项目路径、产品想法、PRD、截图、日志或构建产物。MyP-M-A 会先判断当前阶段，再交付该阶段真正需要的成果，而不是把所有问题都写成一份 PRD。

它始终围绕三个问题工作：

1. **现在需要做什么判断？**
2. **已有证据能支持到什么程度？**
3. **下一步怎样最小而可靠地推进？**

## 30 秒开始

MyP-M-A 使用标准 `SKILL.md` 目录结构，可安装到支持自定义 Agent Skills 的编码环境：

| 环境 | 个人安装位置 | 项目级安装位置 |
| --- | --- | --- |
| Codex | `<CODEX_HOME>/.agents/skills/mypm/` | 由当前 Codex 工作区配置决定 |
| Claude Code | `~/.claude/skills/mypm/` | `<PROJECT>/.claude/skills/mypm/` |

Claude Code 的个人与项目级目录来自其[官方 Agent Skills 说明](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)。不同宿主的工具、插件和 Computer Use 能力可能不同，MyP-M-A 会按实际可用能力降级，不把“已安装”写成“已验证可用”。

完整复制仓库目录并重新加载对应 Agent。系统可以按任务自动匹配 Skill，也可以直接点名 `mypm`；在 Codex 中还可显式选择 `MyP-M-A` 或使用 `$mypm`：

```text
使用 $mypm 深度评审当前项目。先建立产品和工程地图，再告诉我最值得解决的问题。
```

不需要先记住命令。显式入口适合你已经知道当前要做什么时使用：

```text
/idea 我想增加团队共享能力。判断它是不是真问题、值不值得做、现在是不是时机。
```

```text
/prd 基于已经确认的需求写完整 PRD。只追问会改变目标、范围或核心合同的问题。
```

```text
/acceptance 锁定当前构建产物，基于日志、截图、测试和人工补证判断是否可发布。
```

## 五个入口

| 入口 | 要回答的问题 | 主要交付物 |
| --- | --- | --- |
| `/review` | 项目现在是什么样，问题在哪里 | 产品/工程地图、证据化发现、影响与分流 |
| `/idea` | 这是真问题吗，值得现在做吗 | 需求池、证据等级、压力测试、最小实验 |
| `/prd` | 应该做成什么，怎样避免遗漏 | 完整需求、影响范围、数据/状态合同、原型、开发前验收 |
| `/acceptance` | 实际实现是否达到发布标准 | 产物身份、真实证据、缺口、人工验证、发布结论 |
| `/prompt` | 下一轮怎样交接得短而完整 | 带范围、证据、授权和停止条件的可执行提示词 |

`/prompt` 是辅助入口，不改变四个产品阶段。没有显式命令时，MyP-M-A 会根据目标和已有产物自动路由。

## 两种交付模式

入口不变，MyP-M-A 会先解析交付环境，再决定技术深度：

| 模式 | 适用场景 | 产品经理负责 | 下游角色负责 |
| --- | --- | --- | --- |
| 团队协作型（默认） | 公司项目、跨部门协作、只要求产品文档，或意图不明 | 用户、目标、范围、流程、业务规则、状态/权限语义、指标与验收 | 物理 API、表结构、代码、测试实现、CI 与部署方案 |
| Vibe Coding 全流程型 | 明确要求同一用户或 Agent 继续实现、测试和发布 | 完整产品合同 | 在产品合同之上继续补原型、逻辑 schema、开发计划、任务和验证接缝 |

模式只改变职责和工程深度，不改变已经确认的事实、数字、范围、状态与验收语义。显式指定优先；没有足够线索时默认团队协作型，不会因为仓库里存在代码或数据库就擅自升级为全流程开发。

## 它交付的是阶段成果

### Review 先建立共同理解

项目 Review 会先说明产品定位、用户、阶段、核心路径，以及模块、数据和状态之间的关系，再列有证据的发现。代码瘦身也必须有调用、测试、运行或所有权证据，不能只凭“看起来没用”。

### Idea 判断价值，不替愿望找理由

Idea 会回答问题真假、证据强弱、价值、时机和最小下一步。没有数据时只给采集或实验方案；评分不能替代证据，弱证据需求会进入压力测试而不是直接升级为版本范围。

### PRD 先定义完整产品合同

两种模式都覆盖入口到出口、状态与失败链路、保存/取消/关闭、权限、指标、影响范围和开发前验收。团队协作型不替研发猜物理表结构、端点、代码文件或测试脚本；UI 由产品定义信息层级、流程、状态与设计验收，设计角色承接最终稿。Vibe Coding 全流程型继续补齐可验证高保真原型和工程接缝。

Vibe Coding 模式或用户明确授权开发承接后，可以继续形成：

- `dev_plan_vx.x.md`：实施顺序、影响文件、风险与回退。
- `progress_vx.x.md`：最小可执行任务与状态看板。
- `dev_log_vx.x.md`：独立记录开发过程，不与进度混写。

### Acceptance 只认实际结果

Acceptance 会按对象锁定必要身份，例如分支、HEAD、候选产物、哈希、环境和证据时间。自动测试、日志、截图、GUI 操作和人工补证分别记录；无法执行的路径保持“待验证”。验收通过也不等于已经授权提交、推送、打 Tag 或发布。

## v0.41：产品边界不再等于技术变薄

v0.41 增加内部 `delivery_mode=auto|team_pm|vibe_coding` 合同和团队协作型 PRD 模板。团队模式删除的是未经确认的物理实现，不是业务细节；主流程、分支、失败、权限、指标、旧体验保护和验收出口仍须完整。

### v0.40：图表与图解不再混为一谈

v0.40 增加两条独立的视觉交付通路：

| 通路 | 适合表达 | 保真要求 |
| --- | --- | --- |
| 决策图表 | 冻结数值、比较、趋势、优先级 | 显示值逐项映射来源，不得改分母、单位或阈值 |
| 语义图解 | 节点、关系、状态、顺序、职责 | 每个节点和边都能回到原始事实，不能补造关系 |

正式视觉交付可以包含源 HTML、SVG/PNG、manifest、事实映射、桌面/窄屏验证、离线检查和重绘保真账本。外部绘图工具是可选实现，不是运行时硬依赖；工具不可用时降级，但不会伪装调用成功。

## 核心原则

- **正确性、证据、完整性优先**：更短、更快或更好看不能抵消关键事实错误。
- **未知保持未知**：不编造用户、阈值、接口、字段、状态或完成结果。
- **阶段不能越级**：Review 发现不是确认需求，方案收敛版不是完整 PRD，测试计划不是实际验收。
- **范围必须可追踪**：正式交付物引用上游 ID、版本、文件和证据，同时写清非目标与回退。
- **仓库是事实源**：Basic Memory 只负责跨线程续接，不能覆盖项目中的 PRD、进度和验收事实。
- **外部写入单独授权**：提交、推送、tag、Release、上传和可见性变更不会因为验收通过而自动执行。

Basic Memory 支持 `auto`、`suggest`、`off` 三种模式。默认只在已知项目的新线程上下文不足时恢复，并在稳定阶段结束时去重更新。

## 本地校验

在仓库根目录运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\validate-skill.ps1 -Strict
```

该命令检查 UTF-8、常见乱码、版本一致性、运行时引用、评测 schema、生命周期归属、本地 Markdown 链接和孤立资源。静态校验不能替代模型行为评测。

## 仓库结构

```text
mypm/
├─ SKILL.md       # 入口路由与常驻核心合同
├─ capabilities/  # 离线注册表与按需能力卡
├─ references/    # 按当前入口渐进加载的规则
├─ templates/     # PRD、验收、计划等正式模板
├─ evals/         # 稳定、挑战、触发与文件型用例
├─ examples/      # 公开案例准入规范与合成 dry-run
├─ scripts/       # 静态校验与评测治理工具
├─ assets/readme/ # GitHub README 的静态视觉资产
├─ notes/         # 路线图、评测历史与版本事实源
└─ agents/        # Agent 宿主展示与默认提示配置
```
