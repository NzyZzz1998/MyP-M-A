# MyP-M-A

**面向团队协作与 Vibe Coding 的中文产品经理 Skill：从问题判断到完整 PRD，再到有证据的验收。**

`中文优先` · `5 个入口` · `2 种交付模式` · `专项能力按需加载`

> **选择版本：** `main` / `v0.42.0` tag 是原 Stable；本页描述 `test` 维护候选，新增可选项目记忆、独立诊断日志和受控专项路由。2026-10-18，维护者接受已知问题并确认收口，仅授权提交和推送 `test`，**不晋升新 Stable、不更新 main 或 tag**。版本字段仍为 `0.42.0`，安装时请同时核对分支和 commit。详见[收口决定与已知问题](notes/maintenance-closeout-20261018.md)。

MyP-M-A 是安装在 Codex、Claude Code 等 Agent 宿主中的产品工作流，不是独立应用，也不自带模型。给它项目、想法、截图或反馈，它会按当前阶段组织事实、需求和交付物，不必从空白文档开始。

**公司协作时，交付完整的产品文档；自己做产品时，经确认后继续承接原型、开发计划和验收。** 不会仅因为项目里有代码，就把一份团队 PRD 扩写成工程实施手册。

**不绑定模型厂商，优先适配与推荐 GPT 系列。** 其他模型也可通过兼容宿主使用，但可加载不等于交付质量相同，详见[模型与宿主](#模型与宿主)。

**本轮的价值主要在可控交付和维护，不是更长的提示词或明显更高的总分。** 当前候选双模型全量 `490/490` 首次有效回答且评分齐备，仍有内容遗漏与证据不足，整体部分通过，没有跨模型、跨面板一致领先。正确性、证据和完整性始终优先于精炼。

## 模型与宿主

**GPT 系列是 MyP-M-A 的首选模型系列，也是目前适配投入与评测覆盖最充分的系列。** 提示规则优化、失败样本复核和版本比较主要围绕 GPT 展开；选模型时，建议优先从已验证的 GPT 配置开始。

| 模型范围 | 适配与验证情况 | 如何理解 |
| --- | --- | --- |
| GPT-6 Astra | 原 v0.42 专项适配对象；当前 test 已完成 medium 全量观察 | Stable 与维护候选分开看；不据单轮成绩宣称普遍领先 |
| GPT-6.1 Sol | 本次维护候选的另一完整验证配置，medium | 与 Astra 各 245 任务；不是此前 GPT-5.6 Sol 的同一模型 |
| GPT-5.6 Sol | 原 v0.42 的主要兼容控制，2026-09 已完成 medium 全量 | 主力可使用原 v0.42；没有用本次 GPT-6.1 成绩替代其新候选验证 |
| GPT-5.6 Terra / Luna | 原 v0.42 已有 medium 全量，当前 test 没有重新覆盖 | 既有稳定工作流可优先保留 v0.41；升级按实际任务验证 |
| Claude 及其他模型 | 运行时不设厂商绑定，可通过能够加载 Skill 的宿主尝试 | 目前没有与上述 GPT 配置同等覆盖的项目内验证，不承诺同等效果 |

这里的“GPT 优先”是**适配策略与使用推荐，不是所有模型横评后的胜出结论**。不同模型、推理强度和工具环境可能影响事实保真、文档完整度与指令执行；上述成绩也不代表所有 GPT 型号都已验证。详见[评测历史](notes/evaluation-history.md)与[本版适配记录](notes/v0.42-adaptation-verification.md)。

原 v0.42 是 GPT-6 Astra 专项优化版，发布时五入口和功能范围不变；当前 test 的可选维护模块属于后续增量。版本推荐是维护策略，不表示 v0.41 在所有 GPT-5.6 场景均优于 v0.42。各轮模型、快照和限制见[质量与验证边界](#质量与验证边界)。

**宿主和模型是两回事。** 宿主负责加载 Skill、读取文件及提供浏览器等工具，模型负责理解与执行。安装到 Claude Code 不等于 Claude 模型已获得同等验证；MyP-M-A 不负责切换模型、提供 API 或绕过宿主的模型限制。只做文档任务不要求具备全部工具，缺少实测能力时应明确保留待验证项。

## 开始使用

### 1. 安装到正在使用的宿主

使用标准 `SKILL.md` 目录结构，选择一种安装位置即可。以下为 PowerShell 个人级安装示例：

```powershell
# Codex：使用这一条
git clone https://github.com/NzyZzz1998/MyP-M-A.git "$HOME\.agents\skills\mypm"

# Claude Code：使用这一条
git clone https://github.com/NzyZzz1998/MyP-M-A.git "$HOME\.claude\skills\mypm"
```

仓库访问需具备相应权限。已经安装时，在现有目录更新，不要覆盖本地修改或再装同名副本。

**需要试用本页维护能力时**，新安装可在对应命令中使用 `git clone --branch test ...`。已有安装先确认工作区干净并保留本地修改，再选择目标分支；不要用覆盖目录或强制重置完成升级。

**可选依赖补装默认关闭。** 首次明确授权后，升级后的首次使用检查固定清单，仅补装缺失的两个 Matt pilot。不会覆盖已有 Skill、追随任意上游更新、安装 OCR/宿主插件、配置凭据或开启 Memory/日志。由当前 Agent 执行，不是后台更新服务；新增来源或包变化须重新确认。详见[授权范围与命令](references/provider-dependencies.md)。

上面的命令默认获取远端 `main`，当前为 `v0.42.0 Stable`；`test` 另含维护补丁，版本号相同不代表文件快照相同。固定版本可选择 `v0.42.0` tag，`v0.41.0` 保留为回退版本；历史快照见[版本标签索引](notes/version-tags.md)。安装时以实际分支、commit、tag 与文件版本为准。

### 2. 发出第一条任务

安装并让宿主加载技能后，把下面这段发给 Agent。它是对话任务文本，**不是终端命令**：

```text
mypm /review

评审当前项目，先说明用户、核心流程、模块关系和当前进度，
再列出有证据的问题与下一步建议。本轮只读，不修改代码。
```

不记入口也可以直接说“使用 MyP-M-A 帮我判断这个想法”。提供相关项目路径、文档或反馈即可；只有会影响当前判断的信息缺失时，才需要补充澄清。

## 选择交付方式

**同一份产品事实，两种交付深度。** 模式改变职责和工程深度，不改变已确认的范围、数字、状态或验收标准。

| | 团队协作型 `team_pm` | 全流程型 `vibe_coding` |
| --- | --- | --- |
| 适合谁 | 在公司与设计、研发、测试协作的产品经理 | 自己用 Agent 做产品、继续实现与验证的人 |
| 产品交付 | 目标、范围、流程、业务规则、权限、指标、影响与验收 | 同样完整的产品要求 |
| 原型责任 | 明确设计要求；交由设计承接，或按用户要求代做 | 正式 PRD 阶段更新或补齐高保真原型 |
| 技术深度 | 不擅自定义物理 API、数据库表、代码或部署方案 | 补充有依据的工程约束与接口、数据设计 |
| 停止位置 | 产品评审与角色交接点 | 按授权分阶段推进，不自动越过 PRD 确认点 |

默认 `delivery_mode=auto`：组织协作或意图不明时按团队协作型处理；明确要求同一 Agent 继续实现、测试或发布承接时采用全流程型。显式指定优先。

**写给团队的 PRD：**

```text
mypm /prd

delivery_mode=team_pm
依据当前需求材料，写一份供设计、研发和测试评审的完整 PRD。
说清业务流程、规则、影响范围和验收，不代替研发决定物理实现。
本轮停在 PRD 确认点。
```

**自己用 Agent 做产品：**

```text
mypm /prd

delivery_mode=vibe_coding
依据已确认需求完善 PRD，更新高保真原型并补齐工程承接所需约束。
后续由同一 Agent 实现；先让我确认 PRD，再生成开发计划与任务。
本轮不要进入业务代码实现。
```

## 五个入口

| 入口 | 核心问题 | 主要交付 | 明确不做 |
| --- | --- | --- | --- |
| `/review` | 项目现在是什么样，问题在哪里 | 产品/工程地图、证据化发现、影响与分流 | 不把发现直接升级成需求 |
| `/idea` | 这是真问题吗，值得现在做吗 | 需求池、证据等级、压力测试、最小实验 | 不用评分替代证据 |
| `/prd` | 应该做成什么，怎样避免遗漏 | 完整需求、影响范围、业务状态与数据口径、原型要求、开发前验收 | 不擅自扩大技术深度 |
| `/acceptance` | 实际实现是否达到发布标准 | 产物身份、真实证据、缺口、人工验证、发布结论 | 不用计划或代码阅读替代实测 |
| `/prompt` | 下一轮怎样交接得短而完整 | 带事实、范围、证据、授权和停止条件的提示词 | 不改写上游结论 |

可从任一入口开始，不必每次重走全流程。`/prompt` 负责阶段间交接，不是第五个产品阶段；这些入口由 Skill 解释，不保证在每个宿主中注册为同名斜杠菜单。

## 一份完整 PRD 包含什么

**减少越界，不减少需求细节。** 保存、取消、关闭、失败、恢复和旧体验保护，都是产品需求的一部分。

<details>
<summary><strong>展开完整 PRD 的十项检查</strong></summary>

1. 背景、问题、目标与非目标。
2. 用户、场景、前置条件和成功出口。
3. 范围、优先级、版本边界与依赖关系。
4. 从入口到出口的主流程、分支流程和取消/关闭行为。
5. 业务规则、状态、权限、异常、恢复与旧体验保护。
6. 数据口径、指标，以及有业务依据的审计与证据要求。
7. 前端、后端、数据、配置、发布、测试等影响范围。
8. 信息架构、交互状态、原型责任与设计验收要求。
9. 开发前验收目标、通过标准和不通过处理。
10. 未决问题、风险、假设与后续承接。

</details>

团队协作型由设计角色承接原型；用户要求代做或没有下游设计角色时才生成高保真原型。全流程型在正式 PRD 阶段补齐可验证的高保真原型，并在确认与授权后生成：

- `dev_plan_vx.x.md`：实施顺序、影响文件、风险与回退。
- `progress_vx.x.md`：最小可执行任务和状态看板。
- `dev_log_vx.x.md`：独立记录开发过程，不与进度混写。

## 专项路由如何工作

**MyP-M-A 负责主流程，专项 Skill 或工具只补当前缺口。** 先确定入口、问题、对象和授权，再探测真实能力；有输入且适用才调用，结果回到同一份 PRD、评审或验收记录。不会另起一套规格、任务或项目进度。

| 你遇到的问题 | 路由与实际状态 | 触发 / 不可用时 |
| --- | --- | --- |
| 业务术语多义、领域边界不清 | Matt `domain-modeling` 既有 pilot；文件适配与合成小样本已验证 | 用户明确选择后读取固定来源；缺失则用本地分析，注明未使用 Matt |
| 需要一份可交给知情者填写的问卷 | Matt `to-questionnaire` 既有 pilot；文件适配与小样本已验证 | 用户明确选择；复用已知答案，只生成、不代发 |
| 对代码改动做专项检查 | 默认本地 Alibaba OCR delegate；用户点名可用 Matt 两轴方法适配 | 仅代码评审触发；缺 CLI 保留本地 Git/规则审查，不冒称 OCR 已运行 |
| 数据质量、指标、市场规模或 KPI | 按需选择 `data-analytics` 对应能力 | 先有数据、口径或可引用来源；无数据只给补证与估算框架 |
| 访谈、JTBD、机会树、战略与 GTM | 优先使用随仓库提供的 Discovery / Strategy reference | 不要求安装整套 PM 技能包，也不叠加同类框架 |
| UI 原型、网页或桌面验收 | 现有设计系统、Figma/UI Skill、浏览器或 Computer Use | 按模式和实际宿主能力执行；文字方案不冒充截图或交互实测 |
| 数值图表、流程或架构图 | 决策图表与语义图解分流；`diagram-design` / Lieflat 为可选 pilot | 核对来源和许可；Lieflat 非商业限制保留，缺工具可用安全本地表达 |
| 工程实施、TDD、排障 | 沿用项目已经选择的方法或提供者，例如 Superpowers | 不因安装了 Matt 就重复编排；没有实现授权不进入工程执行 |

注册不等于安装，安装不等于宿主暴露接口，适配就绪也不等于调用或验收成功。当前 [provider 清单](capabilities/provider-registry.json)登记 **4 个提供者**：两个 Matt pilot、Matt 代码审查方法适配、OCR delegate；它不是所有宿主工具的完整安装清单。

**没有接入 Matt 整套总控流程。** `implement`、`triage`、`wayfinder`、`prototype`、`writing-for-agents` 等不能因为出现在上游目录就称已接通。完整取舍见[路由评审矩阵](notes/external-skill-routing-review-20261017.md)，可执行规则见[专项路由合同](references/external-provider-routing.md)。

### Matt + OCR 怎么审

- 冻结同一对象，分别覆盖已提交、暂存、未暂存和未跟踪改动，保留逐文件覆盖与跳过原因；不要求先提交来规避漏审。
- 单审只运行选定提供者；双审默认串行，先保留各自报告，再核证、去重并说明分歧。无规格只跳过规格一致性检查，不跳过代码检查。
- `dual-method` 是同上下文两种方法；`dual-isolated` 需要单独授权的 reviewer 预算与真实隔离证据，不能仅靠一个配置字段声称独立。
- 本机已验证 OCR v1.13.1 的真实 delegate 调用与同快照双方法链路。OCR 提供规则、当前宿主完成代码判断；不是 OCR CLI 自带独立模型完成评审，也不是已验证隔离双模型双审。
- 代码变化会使相关旧证据失效；无发现不等于测试、产品验收或发布通过。

默认子 Agent 预算为 **0**。安装、外部模型传输、凭据、远端写入与发布分别授权；获准的 Agent 完成后关闭。仅一次明确双审允许同类双提供者，其余按问题与快照复用，避免重复执行或嵌套循环。详见[代码适配](references/matt-code-review-adapter.md)与[真实链路证据](notes/ocr-live-verification-20261018.md)。

## 项目记忆与诊断日志

两者服务不同目标，分别授权，**默认都关闭**。

| 模块 | 用来做什么 | 不会自动做什么 |
| --- | --- | --- |
| 项目 Memory | 指定项目跨线程恢复事实、稳定阶段更新决策/状态/来源，写后回读；支持 `auto`、`suggest`、`off` | 不代替仓库事实，不跨项目采集，不存聊天全文，不因安装而开启 |
| Skill 诊断日志 | 本地记录入口、纠正、返工、交付和工具问题，帮助改进 MyP-M-A | 不复制记忆正文，不进入 RAG，不发送遥测或完整工具输出 |

自动维护是当前 Agent 遵循已授权合同，不是后台无限运行。记忆恢复与整理可能增加上下文和 Token；日志直接写本地 SQLite，连接用后关闭，不启动 Basic Memory 或额外模型。Memory 使用一次性 CLI，正常、异常或超时后释放本次自有进程；不按名称结束其他会话或宿主服务。

本机 Codex CLI 与桌面新会话恢复已有实证。首次免提醒阶段测试漏写记忆和日志，修复后一个新桌面会话完成写入、回读及双事件记录。**这是限定环境的一例流程通过，不是长期无遗漏、全部生命周期或所有宿主自动化保证。** 后续模型面板中的策略回答也不能替代服务端真实读写证据。

配置只放目标项目 `.mypm.local.json`，记忆与日志数据放仓库外；本地开关与 hooks 不随公开仓库提交，跨电脑重新映射和授权。关闭某模块不会删除旧数据，也不会自动开启另一个模块。详见[配置、授权、成本与关闭方式](references/local-memory-diagnostics.md)、[首次失败与补验](notes/local-maintenance-recheck-20261017.md)。

## 使用边界

- **正确性、证据、完整性优先**：更短、更快或更好看不能抵消关键事实错误。
- **未知保持未知**：不编造用户、阈值、接口、字段、状态或完成结果。
- **阶段不能越级**：Review 发现不是确认需求，方案收敛版不是完整 PRD，测试计划不是实际验收。
- **范围必须可追踪**：正式交付引用上游 ID、版本、文件和证据，写清非目标与回退。
- **查漏不等于擅自加要求**：发现遗漏风险时给出依据、影响和建议，交负责人确认；已证实违反既有合同则明确指出阻塞，不能因原清单漏列而放行。
- **仓库是事实源**：Basic Memory 只负责跨线程续接，不能覆盖项目中的 PRD、进度和验收事实。
- **外部写入单独授权**：提交、推送、Tag、Release、上传和可见性变更不会因验收通过而自动执行。

浏览器、Computer Use、GitHub、数据库、图表和 Basic Memory 均按需使用，**不是全部安装后才能开始**。工具由宿主提供；不可用时保留待验证项，不能将只读检查当成真实操作成功。
